Why can't a cheap model just do the implementation?

If the feature is planned upstream, why not let Haiku write the code? This page covers what the research says, what our own 720 runs show, and whether comments could make it safe.

Short answer: you can, for narrow, well-specified, well-tested edits. For general feature work in a codebase that keeps changing, the evidence supports your caution, but for a different reason than the one comments were meant to address.

Why: implementation isn't thinking-free. Every edit involves small design decisions: where code goes, whether to reuse or rewrite, which layer to change, what to keep. A plan made upstream doesn't anticipate them. Cheaper models make more of these decisions poorly, and tests catch few of them. On identical tasks, Haiku rewrote more code than needed far more often than Sonnet, with the same pass rate, and in one case silently changed behaviour inside an unrequested refactor.

Where this cuts against your hope: codebases erode under frontier models too, and they erode even when the agent wrote the code and can read all of it. That points to editing judgment, not missing knowledge, as the main cause. Comments supply knowledge. They can carry specific, local facts ("reuse this helper", "this layer owns that rule"), which do help weaker models, but they can't supply judgment.

What "implementation" actually contains

The idea of planning upstream and executing cheaply assumes a clean split between deciding and doing. Measured studies say the split leaks (R6, docs/research/planner-executor-split.md):

  • A plan helps, but doesn't close the gap. A plan written by Sonnet 4.5 lifted a small open model from 42.8% to 57.8% on SWE-bench Verified. Sonnet 4.5 alone scores about 77%. The plan closed about 40% of the gap. MEASURED
  • Knowing exactly where to edit isn't enough. Even with the exact files and lines given, GPT-5-mini still failed 40% of the time. MEASURED
  • A poor plan is worse than no plan. Wrong guidance actively misleads the executor. MEASURED
  • It wasn't cheaper either. In the one study that reported cost, "strong plans, weak codes" came to $0.34 per solved issue, against $0.25 for the strong model alone. That study used 2025 models and prices. ONE STUDY

The decisions that leak are the ones a plan can't see in advance: which existing helper to use, which layer owns a rule, which edge cases the current code already handles, and how to fit the change without disturbing what's there. That is exactly where tangle comes from.

What our own data shows

In round 1, Haiku 5.5 and Sonnet 5.5 did the same 20 tasks, 360 attempts each. For every attempt we rebuilt the final code, stripped comments, docstrings and formatting, and counted real code changes against the minimal reference change. Full method: docs/evaluation/churn-2026-11-07.md.

Across all arms that is 53 of 360 Haiku edits against 6 of 360 Sonnet edits. Repeated runs of a case are correlated, which overstates certainty, but a gap this size is not chance. The skills did not reliably reduce it (Haiku's best skill arm: 6/60 against 10/60, p = 0.42). Two examples, both of which passed every test:

1. Rebuilding instead of adapting

The task allowed Unicode usernames. The minimal change edits the existing regular expression. Haiku replaced it with a hand-written character checker:

-PATTERN = re.compile('\\w{3,20}')
+MIN_LENGTH = 3
+MAX_LENGTH = 20
+def _is_allowed(ch):
+    if ch == '_':
+        return True
+    category = unicodedata.category(ch)
+    return category[0] == 'L' or category == 'Nd'

2. An unrequested refactor that quietly changed behaviour

Haiku extracted a helper that nobody asked for. The original trimmed whitespace from names; the helper doesn't. The tests didn't notice. This happened in 2 of 3 independent runs:

+def _display_name(user):
+    name = user.get('name')
+    if name is None or not str(name).strip():
+        return user.get('username')
+    return name                      # no longer stripped
-    display_name = (user.get('name') or '').strip() or user['username']

Each of these is harmless today. Repeated across hundreds of changes, they become the mess you've described: structure reinvented in slightly different ways, and behaviour drifting without anyone noticing.

Limits of our data: these are single edits on small synthetic modules, not accumulation over many changes, and "excess" is a proxy (some refactoring is legitimate). It shows the per-edit tendency clearly. It doesn't measure how much that tendency costs later.

Would comments have prevented this?

Evidence that they could help

  1. Specific, location-tied facts help weaker models. In R6's studies, task-specific guidance improved weak executors, while general repository context did not. A comment like "reuse validate_name(); it owns this rule" is the specific kind.
  2. Cleaner surrounding code lowered break rates by 15–30% for mid-size open models (R6), so what the code around an edit says does affect weaker models.
  3. Comments sit where the decision happens. An upfront plan can't see every edit site, but a comment can say at that site "this regex is the canonical rule" or "callers rely on trimmed names".
  4. They're cheap: about +13% cost per sequence in our smoke run, against +73% for a docs folder.

Evidence that they won't be enough

  1. Agents erode code they wrote and can fully read (R5). The knowledge is right there, and the erosion happens anyway. That points to editing judgment.
  2. General context didn't help weak models; the authors say it "consistently failed to improve" them (R6). Most comments are general, not decision-specific.
  3. "Write clean code" instructions cut the starting mess by about a third but didn't slow how fast it built up, and cost 2.4–3.6 points of correctness (R5).
  4. Our skills didn't reduce Haiku's churn (10/60 to 6–10/60, not significant). In both examples above, no comment would have stopped the agent rewriting a working regex or dropping a trim.
  5. A stale comment works like a bad plan, and bad plans were worse than none (R6).

What does work, measured

The setups that kept strong-model quality at lower cost all kept the strong model involved during execution, not just before it (R6):

  • Advisor at checkpoints: a strong model consulted before starting and before declaring the work done. Opus advising Sonnet gave +2.7 points at 11.9% lower cost per task (vendor claim; no published coding result with a Haiku executor).
  • Routing: hard steps go to the strong model, easy ones to the cheap model. This matched strong-model quality at half the cost or less in the cited studies.
  • Strong drafts, weak finishes: the cheap model handles the mechanical part.
  • Executable guardrails: in one small study, a map from code to its tests cut regressions by 70%. Behaviour-preserving tests, duplication linters and architecture rules turn "don't drift" into something checked rather than hoped for.

Price changes the maths. Haiku 5.5 is about 20× cheaper per token than Sonnet 5.5; in our runs an attempt cost about $0.002 against $0.022. A setup where the strong model only reviews each cheap diff, rather than planning and solving, may now be much cheaper than the older studies found. That is a hypothesis, not a measurement.

Both sides of your question

The case for using a cheap implementer

  • Within a generation the gap is sometimes small: 46.4% vs 52.1% on FrontierCode.
  • Per-feature correctness looked the same in our runs.
  • It's 10–20× cheaper, which pays for reviews, retries and tests.
  • Frontier models also erode code, so "use Opus" doesn't by itself prevent tangle.
  • Narrow, mechanical, well-tested edits are where cheap models do well.

The case for your caution

  • Implementation carries design decisions that plans don't capture, and a plan closed only about 40% of the gap.
  • On identical tasks Haiku rewrote more code than needed about 9× as often as Sonnet, sometimes with silent behaviour changes that tests missed.
  • On hard agentic work the gap is large: 39.2% vs 70.6% on Terminal-Bench 4.0.
  • The erosion that tests miss is what accumulates, and per-feature checks won't show it until the codebase is already tangled.

What this means for Code Comments

Your hope was that comments would steer weaker agents through implementation. The evidence suggests a narrower role:

  • Comments can carry decisions to the point of edit: "this is the canonical rule; reuse it", "callers rely on this", "this layer owns X". That's the one form of context with support for helping weaker models, and the skill already leans this way.
  • Comments can't supply judgment. The tangle comes mostly from how agents edit (rewriting instead of adapting, restructuring unasked), which happens even with full knowledge.
  • So comments would be one layer among several: strong-model review at checkpoints, tests and lints that make drift visible, and comments that point at what to reuse and what not to break.

The experiment that answers your real question

Your real question isn't "do comments help one follow-up change?" (our smoke run). It's "does a cheap model stay clean over many changes, and what keeps it clean?" Answering that needs:

  1. Long sequences: five or more features on the same codebase, each arm building on its own code. Degradation is a trend over 4–8 steps, so two-step tests can't see it (R5).
  2. Arms:
    • Haiku plain;
    • Haiku with the comments skill;
    • Haiku with a "keep it clean, reuse helpers" instruction only, as a control any comment benefit must beat;
    • Haiku with a Sonnet plan;
    • Haiku with Sonnet review at checkpoints;
    • Sonnet plain, as the ceiling.
  3. Metrics: correctness per step; unnecessary churn, duplication and erosion per step; silent behaviour changes, caught by stricter hidden checks; total cost per successful step.
  4. A written prediction first: if the comments arm doesn't beat the instruction-only arm on churn and erosion, comments aren't the lever.

Haiku is cheap, so this is affordable. A pilot of 3 codebases × 5 steps × 6 arms × 2 reps is roughly 180 sessions, most of them Haiku. That is likely tens of dollars; the pilot would measure it before any larger run.

What I'd do in your workflow today

  1. Use Haiku for narrow, mechanical, well-tested edits: renames, wiring, filling a well-defined function, test scaffolding.
  2. Use a strong model for design-heavy steps, and as a reviewer of every cheap diff before merging. Ask it specifically: "Did this rewrite something that already existed? Did any behaviour change that the task didn't ask for?"
  3. Make drift checkable: behaviour-preserving tests, and lints for duplication and complexity, so tangle shows up as a failed check instead of a feeling months later.
  4. Use comments for the specific decisions: the canonical place for a rule, what callers rely on, and what not to reinvent. Don't expect them to substitute for review.
