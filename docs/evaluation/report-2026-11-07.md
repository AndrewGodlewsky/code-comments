## 1. The answer in one screen

**What we measured.** We tested whether a coding agent with the Code Comments skill
leaves the **right comments** when it edits code. That means:
- capturing the non-obvious *why* from the evidence it was given;
- fixing comments its change makes false;
- not inventing reasons;
- not touching valid comments;
- not adding clutter.

We graded the comments the agent left behind, against a hand-made answer key for
each case.

**What we ran.**
- **Writers:** two models, Sonnet 5.5 (frontier) and Haiku 5.5 (weaker).
- **Arms:** the five skill variants plus a no-skill control.
- **Cases:** 20 small synthetic Python cases, each run 3 times.
- **Volume:** 720 graded attempts, plus an 18-attempt pilot.
- **Spend:** $14.17 in total ($13.60 tournament, $0.57 pilot).
- **Errors:** zero harness errors.

**Is anything making a difference?**

| Question | Answer |
| --- | --- |
| Does any variant reliably improve the overall score? | **No, not beyond statistical noise on either model.** |
| Is there a consistent direction? | **Yes, for capturing the *why*.** On both models the skills raise `capture` from 0.60 (control) to as high as 0.93 (`lean`). The clearest single example: one case where the control *never* recorded the key reason (0 of 6 attempts) and *every* skill arm always did (30 of 30). |
| Any harm? | **On Haiku as writer, sometimes.** Skill arms sometimes rewrite still-valid comments during comment-only requests, and they add more comment lines. Part of Haiku's apparent loss comes from a case that conflicts with our own principles (§5.3). |
| Cost? | The skills raise cost per attempt by **26-87%**, roughly in proportion to skill length. |
| Code breakage or invented reasons? | **None.** No arm broke behaviour, and invented claims were essentially absent in every arm, *including the control*. These guardrails are not separating the arms. |

**What this does *not* tell us.** It doesn't tell us whether the comments help the
*next* agent, especially a weaker one, make correct changes compared with an
AI-maintained docs folder. That is the actual product question, and it is now the
primary experiment (#19), which has not run yet. We also have **not tested any real,
medium or large codebase**: every case is a 10-60-line synthetic module. See §6.

## 2. What the evals measure

### 2.1 The question, and its limits
`comment-edit` is a **writer eval**. An agent receives a small repository, a request
and supporting evidence (a ticket, an incident note, a changelog), and makes the
change. We then inspect the files it left behind. It answers:

> *When an agent edits code with this skill, does it leave the explanation true,
> sufficient and lean?*

It does **not** answer whether that explanation helps anyone later. Writing good
comments is necessary for the product goal but not sufficient. This is why, since
the 2026-11-07 rescope, `comment-edit` is a **guardrail** and the downstream reader
experiment (#19) is the **primary score**.

### 2.2 The four case families
| Family | What the agent faces | What "correct" means | Why it exists |
| --- | --- | --- | --- |
| `capture` | A code change whose *why* lives only in the evidence | Behaviour correct; each required fact explained in its owning scope; no invented reasons | Tests the skill's core purpose |
| `maintain` | Existing comments, some made false by the requested change | Behaviour correct; stale claims fixed; still-valid comments kept; new facts added | Tests "keep it true", the best-evidenced principle (P-01) |
| `restrain` | A routine change with nothing non-obvious to explain | Behaviour correct; no clutter added | Stops a "comment everything" skill from winning |
| `audit` | A comment-only refresh request | Code untouched; stale claims fixed; protected comments intact | Tests comment-only mode, where weaker writers struggled |

### 2.3 All 20 cases

| --- | --- | --- | ---: | --- |

All 20 are **synthetic, small (10-60 lines per file), Python, and written by agents
for this repository**. They exercise the knowledge types named in the evaluation
protocol. They are not real projects.

### 2.4 Metrics
Every attempt receives all seven metrics.

| Metric | Meaning |
| --- | --- |
| **`pass`** (headline) | All of the following hold |
| `behavior` | The hidden behaviour checks pass. For `audit`, the code is unchanged apart from comments |
| `recall` | Required facts explained within their owning scope, divided by required facts |
| `misplaced` | Required facts explained only in the wrong place |
| `bad_claims` | Stale or unsupported claims present (planted, plausible-but-refuted ideas included) |
| `preserved` | Protected comments (license headers, tool directives, still-valid rationale) still present |
| `noise_lines` | New comment lines that explain no required fact, against a per-case budget. Each fact excuses up to 4 lines; removing a stale line pays for one replacement line |

**How facts are detected.** Facts are matched with *anchor phrases*: every group of
keywords must appear in one comment. This is cheap and deterministic, but it can miss
a paraphrase, so every fact carries example paraphrases it must accept. Every
forbidden claim carries correct remarks it must *not* flag (for example "this is
*not* for dedup"). The self-test enforces both lists.

### 2.5 How one attempt runs
1. **Workspace.** A fresh temporary copy of the case's agent-visible files, outside the
   repository. The answer key never enters it.
2. **Agent.** Headless Claude Code (2.1.319) in `--restricted` mode: file tools only,
   no shell, no web, the user's plugins and hooks off, file access confined to the
   workspace.
3. **Skill.** The variant is loaded as a one-session plugin and invoked explicitly
   (`/cce:code-comments`). The control receives the same prompt without it. Every
   arm uses the identical skill description, so the eval measures *behaviour*, not
   *triggering*.
4. **Model.** Pinned and verified on every reply.
5. **Grading.** The end state is graded programmatically. The full transcript, token
   usage and cost are stored with every attempt.

### 2.6 Why the grader can be trusted (and where it couldn't)
- **Self-test.** Before any paid run, the reference answers must score 100% and an
  untouched workspace 0%, and three deliberately bad outputs (comments stripped,
  every line commented, false claims inserted) must each fail the metric they target.
  It passes.
- **Regrading.** Workspaces are deleted after grading, but each transcript stores the
  exact diff, so any run can be regraded offline at no model cost. Regrading with an
  unchanged grader reproduced **all 378 earlier grades exactly**.
- **Where it was wrong.** Reading failures after round 1 showed that 3 of the 4 cases
  failing in nearly every arm were grader or case mistakes. They were fixed, and all
  results were regraded. Both raw and regraded numbers are reported (§5.4). One fix
  favours the skill arms, and is labelled as such.

## 6. So: is anything making a difference?

**Established at this sample size:** nothing. No variant changes the overall pass
rate beyond noise for either writer model. The noise floor is about ±0.15-0.20 on 20
cases, so an effect smaller than about 15 points cannot be seen.

**Consistent across both models, but directional:**
1. **Skills make the agent record the *why* more often.** `capture` rises from 0.60 to
   0.73-0.93 on both models, and the ledger case is 30/30 against 0/6. This is the
   skill's core purpose, and it shows up.
2. **The cost is clutter and price.** Longer skills produce more comment lines and cost
   26-87% more per attempt. `lean` gets the capture gain at the lowest cost on both
   models.
3. **A weaker writer over-applies the skill** in comment-only mode, rewriting valid
   comments. The skill text needs a fix (P-13: "leave valid comments word for word",
   and stronger "don't narrate history").

**Not discriminating:** behaviour (never broken) and invented claims (essentially
never, even without a skill). These modern models already avoid them on cases this
small, so these guardrails need harder cases to mean anything.

**The bigger caveat.** Everything above concerns the comment *writer*. Whether these
comments help a later agent, and whether that beats your docs-folder practice, is
unmeasured. The research reports suggest where to look:
- value comes from knowledge the code doesn't contain, not from describing the code
  ([capability-gradient.md](../research/capability-gradient.md),
  [context-layers.md](../research/context-layers.md));
- separate docs drift ([human-maintenance-and-drift.md](../research/human-maintenance-and-drift.md),
  [docs-for-agents-practice.md](../research/docs-for-agents-practice.md)).

Neither has been tested in this repository yet.

## 7. Do we write a report every time?

**Yes, in two layers:**
1. **Every run: a generated numbers report.** It is automatic and cheap, and it
   contains no interpretation:
   `python -m evaluation.skill_eval.report <flow...> --out docs/evaluation/runs/<date>-<name>.md`.
   It records metadata, paired comparisons, family and case tables, failure reasons,
   cost, and raw vs regraded results. These reports are the record that lets anyone
   check a claim later.
2. **At decision points: a narrative report like this one.** Write one when a round
   ends, a design changes, or a claim is about to be made. It says what was learned,
   what changed, and what not to conclude.

Skipping the first makes results unverifiable. Writing the second after every run is
wasted effort.
