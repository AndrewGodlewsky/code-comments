All paper reviews / Documentation and understanding

PAPER REVIEW · FULL TEXT

Wrong comments hurt; correct comments widened test coverage

GPT-3.5 and GPT-4 generated less successful tests when Python functions carried documentation borrowed from unrelated functions. Correct comments did not significantly increase the test pass rate, but they did increase line coverage. That second result matters: this paper does not show that useful documentation is worthless.

William Macke and Michael Doyle · Testing the Effect of Code Documentation on Large Language Model Code Understanding · Findings of NAACL 2024, pp. 1044–1050

Read the local PDF · ACL publication record

Can a model predict what documented code does?

The researchers expected accurate documentation to help models understand code, with performance deteriorating as documentation became incomplete or incorrect. They operationalized understanding as predicting input–output relationships: give a model an existing implementation, ask it to generate unit tests, then execute those tests. This evaluates an observable consequence of understanding, rather than asking the model to explain itself. Tests were generated in one attempt, without iterative repair after failures. [§3–4, p. 2]

Every condition used the reference solutions for all 164 HumanEval problems: small, self-contained Python functions. The study therefore concerns tests for already-written code, not generating an implementation from a specification or repairing a repository. [p. 3]

Documentation changes and identifier changes were separate

The baseline retained the implementation without docstring comments. The accurate-documentation condition restored HumanEval comments and docstrings, which typically include descriptions and execution examples. The misleading condition attached a randomly selected comment or docstring from another HumanEval function. Separate experiments kept each original docstring line with probability 10%, 25%, 50%, or 75%. These are random deletions, not deliberately shortened documentation. [p. 3]

Two other conditions renamed variables and functions to animal names or random strings. Those interventions test identifier cues; they should not be treated as comment experiments. The pipeline removed imports that raised errors, combined generated tests with the reference implementation, and imposed a ten-second timeout. [p. 3]

Random documentation performed worse than every other condition, with significantly more failed tests and runtime errors under the authors’ bootstrap analysis at α = 0.05. It also produced significantly lower average line coverage. These percentages describe generated tests, not the share of 164 problems solved. [pp. 3–4, Figure 2]

Passing tests and covering code answer different questions.

Pass rate measures how often generated tests agree with the implementation. Line coverage measures how much implementation code the tests execute. Correct documentation did not significantly improve pass rate over the baseline, but achieved significantly greater average line coverage than every other condition for both models. A similar pass rate can therefore conceal a broader test suite. [pp. 4–5, Figure 4]

Partial-documentation results were mixed. GPT-3.5 initially produced more errors with sparse docstrings; GPT-4 had significantly fewer errors with full docstrings than with 10%, 25%, or 50% retained. Most coverage differences were insignificant. The authors declined to draw a general conclusion about partial comments. Animal-name substitutions slightly reduced success; random-string substitutions did not significantly change failures/errors. [p. 4]

Why the test counts and error categories matter

GPT-3.5 generated 1,323 baseline tests, 883 with correct documentation, and 892 with unrelated documentation; GPT-4 generated 3,832, 3,295, and 2,324 respectively. Conditions therefore differed in test quantity and likely difficulty. GPT-3.5 often produced standalone assertions instead of pytest tests, causing failed assertions to appear as runtime errors. Neither raw counts nor error-category differences alone establish greater understanding. [Table 1, p. 5] [p. 3]

A useful warning with a narrow experimental scope

Test generation is a proxy: success can reflect easy examples, while coverage does not establish strong assertions or fault detection. The authors recommend controlling coverage when comparing success rates. They also acknowledge possible HumanEval exposure during pretraining, which cannot be checked against undisclosed OpenAI training data. Memorization could compromise the interpretation. [§7, p. 5]

Only one language, one compact benchmark, and two model families were evaluated. Randomly mismatched docstrings are a blunt form of misinformation; subtly stale comments were not separately studied. Correct docstrings also contain examples, so their contribution cannot be isolated from prose explanations. The study establishes neither a universal rule for documentation nor effects on developer productivity or repository-scale maintenance.

What to carry into engineering practice

Practical inferences, not directly tested prescriptions

  • Resolve misleading comments before trusting generated tests. Check expected behavior against requirements and executable evidence.
  • Keep useful documentation. Coverage gains argue against interpreting unchanged pass rates as a reason to strip comments.
  • Evaluate test quality across several dimensions. Track correctness, coverage, and fault detection; a high pass rate can reward undemanding tests.
