Comments help repair when they describe the intended fix

Accurate explanatory comments improved two small, fine-tuned models’ ability to reproduce historical Java patches. The strongest results used comments generated from already-fixed code. Generating comments from the buggy code did not produce the same benefit.

Antonio Vitale, Emanuela Guglielmi, Simone Scalabrino and Rocco Oliveto · On the Impact of Code Comments for Automated Bug-Fixing: An Empirical Study · arXiv v1, January 30, 2026

Read the local PDF · Versioned arXiv record

The central qualification

This is evidence that useful information about intended behavior can help repair. It does not establish that automatically commenting a broken method before asking an assistant to fix it will help. The primary experiment supplied information derived from the answer. The authors explicitly describe this as an idealized test of their theory, not a deployable repair procedure. [p. 6]

A controlled comparison of training and input comments

The authors rebuilt a historical bug-fix dataset, removed original comments, and generated five one-sentence comments per fixed method: what it does, why it exists, how it works, how to use it, and its properties or conditions. The same generated comments were prepended to both buggy input and fixed output. Each model was trained with and without comments, then evaluated with and without them, creating four conditions per model. Generation used greedy decoding. [pp. 5–7]

The main metric, exact match (EM), asks whether generated output matches the reference fix. It is not a test-suite pass rate: alternative correct patches can fail this comparison. CodeBLEU measures structural and textual similarity, not executable correctness. Manual review of 400 sampled instances found 93% category coherence and median adequacy 4/5 for generated comments; this does not guarantee every comment was correct. [pp. 6–7] [p. 11]

Against the no-comments training/input baseline, comments in both phases increased CodeT5+ by 6.54 percentage points, approximately threefold, and DeepSeek-Coder by 7.20 points, approximately 2.29-fold. The best conditions yielded 1,141 and 1,486 exact matches respectively. These are gains in matching a known patch under idealized documentation conditions, not three times faster debugging or three times more production bugs resolved. [Table 3 and §5.2, p. 8]

Training with comments alone slightly reduced EM when inference lacked comments: a 0.48-point drop for each model. The paper calls the effects practically small, while reporting statistical significance. “No degradation” is therefore too strong. CodeBLEU also did not track EM uniformly: DeepSeek’s highest CodeBLEU, 86.40%, occurred with comments only at inference, rather than in its highest-EM condition. [p. 8]

The follow-up tests change the practical interpretation

Comments generated from buggy code did not help. Reusing the fine-tuned models with these alternative comments produced equal or slightly worse results. CodeT5+ fell from 3.26% to 2.92% without comment-based training, and from 2.78% to 2.67% with it. This follow-up changed inference comments; it did not retrain a complete pipeline on buggy-code comments. [p. 10]

Implementation explanations were useful, but not essential. SHAP attribution on successful predictions ranked “how” comments highest for both models. Retraining and testing CodeT5+ without that category still achieved EM 91% above the uncommented baseline. That is supporting evidence for the remaining comments, not an isolated causal estimate of any category. SHAP estimates token influence, examines only successes, and does not establish that adding a particular comment caused a repair. [pp. 7–10]

The larger-model check was encouraging but limited. GPT-4.1, without task fine-tuning, improved from 6.11% to 8.63% EM on the same test sets: +2.52 points, about 41% relatively. The paper provides little configuration detail for this supplementary experiment. [p. 11]

What remains uncertain

Single-method Java patches from older repositories do not represent repository-scale, multi-file agent work. Commit-message mining can misidentify repairs; pretraining contamination is possible. Original developer comments were replaced, so this does not measure the average value of real documentation. No execution-based verification, developer-time study, or comprehensive comparison of stale and accurate comments was reported. [pp. 10–11]

Dataset accounting caveat

Page 6 reports removing 6,163 overlength pairs and 110 malformed-comment pairs from 116,372, yet its stated split totals still sum to 116,372. The results above use the paper’s explicitly reported 11,637 test denominator. The text alone does not reconcile this inconsistency; checking the replication data would be needed. [p. 6]

Practical knowledge transfer

Interpretation for engineering practice, rather than directly tested prescriptions

  • Write down intended behavior that code cannot establish alone. Required notifications, error handling, ordering constraints, and postconditions can distinguish a valid repair from a plausible rewrite.
  • Review comments as evidence. When a comment merely restates buggy logic, use tests, requirements, and broader context to establish what should happen.
  • Preserve useful comments in repair inputs and evaluate locally. This study supports testing that choice; it does not justify blanket comment generation or a universal comment quota.
  • Verify the patch by running it. Measure executable correctness and regressions alongside similarity to a historical answer.
