Comment Traps: disabled code can become an active defect

In this controlled Python completion study, defective code preserved inside comments increased the recurrence of known defects across both tested coding assistants. The useful lesson concerns bad code examples in model context; ordinary explanatory comments were outside the study.

Yuan Huang, Yukang Zhou, Xiangping Chen and Zibin Zheng · December 2025 preprint · accepted for FSE 2026

58.17% relative increase ≠ 58.17% defective outputs

The largest increase was from 416 to 658 defective completions per 1,000: 41.6% to 65.8%, or 24.2 percentage points. It occurred with Copilot using Claude 3.5 Sonnet when the commented fragment appeared three lines below the completion point. Table 3, p. 10

What the researchers wanted to isolate

“Commented-out code” means executable statements disabled with comment syntax, such as an obsolete implementation kept nearby during debugging. The question is whether an assistant treats that fragment as an example and reconstructs its defect in newly executable code. Four research questions examine defective versus absent or harmless fragments; truncation and warning tags; an instruction to ignore the fragment; and surrounding whitespace or indentation. This is a study of completion behavior, not developer productivity or comment-writing style. Introduction, pp. 2–3

These are observations about those tool–model combinations. The publication date does not establish when the experiments ran, and the results do not measure today's assistants. Publication notice, p. 1; §4.3, p. 8

How the comparison works

The authors first surveyed 6,403 popular Python repositories, then built an experimental dataset of 1,000 samples from executable code with CodeQL-detected defects. For each sample they removed the offending snippet, retained the surrounding file, and marked its original location for completion. The extracted snippet became the defective comment. This construction provides a known target defect and matching context, but differs from sampling naturally occurring comments during live development. Only 207 samples were classified as vulnerabilities; the remainder included maintainability, reliability, correctness, modularity and other defects. §4.1, pp. 6–7

Each defective fragment was inserted at eleven positions: one to eight lines above or one to three lines below the completion point. That produces 11,000 prompts from the same 1,000 source cases, not 11,000 independent programs. The selected offsets covered 70.26% of positions in the authors' separate analysis of similar commented and executable snippets. §4.2, pp. 7–8

RandomInsertionSame placement design with randomly chosen, defect-free commented code of the same length: a control for inserting extra code-like material.

Generated code was scanned with the same CodeQL rules and matched against the original defect type and location. The outcome therefore measures reintroduction of a targeted detectable defect, rather than every possible bug or real-world exploit. §4.4–5.1, pp. 8–9

Every tested full-fragment placement increased defects over its Blank baseline. RandomInsertion produced fewer defects than FullInsertion, supporting an effect beyond simply adding tokens. However, random comments sometimes changed results relative to Blank, so they were not a completely neutral placebo. Copilot showed a pronounced below-cursor effect; Cursor did not show the same pattern. The authors suggest tool-specific context processing, including fill-in-the-middle, as an explanation, but do not inspect or experimentally isolate that mechanism. Table 3 and discussion, pp. 10–12

Deleting the final half of each fragment still left every condition above baseline. Adding <Vulnerable> tags also failed to eliminate the increase. This supports the narrower conclusion that complete verbatim copying is unnecessary; it does not establish the models' internal reasoning process. Tables 4–5, pp. 14–15

A single instruction to ignore commented-out code reduced defects by 4.93–21.84% relative to the corresponding full-fragment condition. This experiment used only the one-line-below placement. Cursor/GPT-4o fell from 499 to 390 defects, below its Blank baseline of 426; the other three combinations remained above baseline. Thus the prompt helped, sometimes substantially, while providing no guarantee of correct output. It is not a comprehensive test of prompting strategies. Table 6, p. 16

Finally, grouping existing prompts by adjacent blank lines and indentation associated more isolated fragments with more defects in Copilot, while Cursor varied by model. Because this grouped existing contexts rather than independently randomizing whitespace, it provides weaker causal evidence about formatting itself. §5.4 and Figure 9, p. 17

Where the evidence stops

CodeQL both selects the cases and judges the results, restricting the study to its detection capabilities. The authors acknowledge imperfect detection and report manual validation by defect category. Popular Python repositories, deliberately defective examples, and isolated single-turn completion also limit generalization to routine work, other languages and multi-turn agents. Repeated-generation uncertainty and confidence intervals are not reported. §6, p. 18

A further caution about the prevalence numbers

The survey reports commented-out code in 84.62% of repositories and 13.09% of files. Its often-repeated 21.19% defective figure concerns comment lines in a reduced analyzable subset after uncommenting and excluding syntax failures. Table 2 also reports more affected repositories than affected files, leaving a counting inconsistency unresolved. These figures motivate the experiment; they are not a reliable estimate of how often an arbitrary production comment causes a bug. Tables 1–2 and §2.3, pp. 3–4

What a development team can learn

Practical inference: review disabled code as part of the examples an assistant receives. Remove stale defective implementations from active context when history already preserves them, and test generated replacements against the intended behavior. Warning labels and “ignore this” instructions can supplement review; these experiments do not support treating either as a correctness boundary.

The paper supplies no evidence for deleting useful prose comments, avoiding documented constraints, or applying its percentages to current agent workflows. A team wanting a local estimate should compare its own completions with and without suspect fragments, retaining a clean baseline and checking actual failures.
