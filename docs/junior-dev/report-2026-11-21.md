# Junior-dev: evidence report

Date: 2026-11-21. Tracking issue: #52. This report answers the user's question: does a
junior developer's questioning make plans and diagrams written by cheaper models (Haiku 5.5,
Sonnet 5.5) clearer? The question is answered against the rules the user set
([design](design.md), "Decided by the user").

## The answer

- **Partly.** On fresh cases, the shipped Junior-dev loop does **not** beat plain SelfReview
  ("reread it and make it clear for a newcomer"). SelfReview is as clear or clearer, at about
  a fifteenth of the cost with Haiku and about 40% of it with Sonnet. The user's "useful" rule
  is not met.
- **The questions do help one case:** a thin draft, one that leaves the design implicit,
  written by Haiku. There the junior loop beats the same rewrite step without questions. On
  the 16 fresh cases, comprehension is +9.9 points (95% CI +2.5 to +17.5). The loop wins 88%
  of the holistic judge's clarity judgments (95% CI 0.72 to 1.00). Under the rubric judge it
  wins 66%, but that interval (0.47 to 0.81) includes a tie.
- **Against Opus alone,** Sonnet with Junior-dev is judged clearer by both judges (84% and 94%
  of judgments). Haiku with Junior-dev is judged clearer by the holistic judge (81%) and ties
  under the rubric judge (50%). Comprehension is level for both. But with a Sonnet junior
  it costs more than Opus alone, so the "worth it for saving tokens" rule fails on cost.
- **The biggest lever is the rewrite instruction,** not the questioning. Telling the author
  to rewrite once for a newcomer, keep every stated fact, say each thing once, and lay out
  each step the same way made the largest difference during the climb. Applied alone, it
  matches the full loop on comprehension almost everywhere, for about $0.004 a plan with Haiku.
- **On GitHub Copilot the plugin works.** It installs from the same files and triggered on
  8 of 8 plan prompts with both Haiku and Sonnet, and on none of 6 routine prompts. Every
  triggered loop produced a report: 14 of 16 ended on a correct teach-back, and 2 stopped at
  the 6-round cap, as the skill allows.

## What was built

- `plugins/junior-dev/`: a plugin for GitHub Copilot (CLI and VS Code) and Claude Code. Its
  parts:
  - a skill that runs the loop;
  - a helper that runs each junior turn as an isolated one-shot model call, through the
    Copilot CLI or the `claude` command;
  - hooks that remind the agent when it writes a plan or diagram file, and once before it
    stops.
- `evaluation/junior_dev/`: the test harness:
  - cases written and checked by Opus, each with a hidden quiz;
  - a tournament that runs each arm;
  - two blind pairwise judges;
  - a length-adjusted analysis;
  - headless Copilot and Claude Code runners.

## How it was measured

- **Cases.** 28 synthetic cases from Opus, each a brief plus, sometimes, files describing an
  existing system. They range from simple credential screens to multi-service architecture:
  - 12 for development;
  - 6 held out;
  - 10 fresh, generated for confirmation after the climb.

  Confirmation used only the 16 untouched cases.
- **Modes.**
  - *Natural:* the author drafts from the brief.
  - *Seeded-implicit:* the author starts from a thin draft whose relationships are left
    implicit.
- **Comprehension.** A hidden quiz of 11 or 12 questions, answered from the final file alone
  by a hurried Haiku reader and a Sonnet reader, and graded by Sonnet. Validation showed it
  detects missing and implicit information, but not layout.
- **Clarity.** Opus judges pairs blind, in both orders. Two judge prompts:
  - *rubric:* "understand faster and more correctly, step by step";
  - *holistic:* "which would you rather be handed", with no criteria.

  The rubric judge favours shorter files (in confirmation it picked the longer one 16 to 47%
  of the time against SelfReview). The holistic judge favours longer ones (82 to 87% in
  seeded mode). Results are given under both, and also adjusted to equal length by a
  logistic fit.
- **Cost.** Tokens priced at API list rates. On Copilot, AI credits as reported.

## The climb (development cases)

| Version | Change | What happened |
| --- | --- | --- |
| v0 (pilot) | The design as first written | Lost every clarity judgment to SelfReview and NoReview: answering every question piled on detail |
| v1–v2 | Main-flow focus, the simplest handling, a final simplify pass | Lost to SelfReview (Opus judge: 17% / 4% of wins) |
| v3–v4 | A newcomer layout for the final pass | 62% / 54% against SelfReview under the rubric judge, but a control with the same layout and no junior did as well. A second judge showed the rubric judge was rewarding its own wording |
| v5 | Rewrite once, before the teach-back | The teach-back now checks the file that ships. Haiku's comprehension dropped: the rewrite cut facts |
| v6 | Never cut a stated fact | Haiku brief items +7 points over v4, but repetitive |
| v7 (shipped) | Say each thing once | Comprehension level with rewrite-only. On thin drafts the questions add completeness (holistic, equal length 0.76) |

Two findings came from deliberate checks, not from the climb itself:

1. **The judge was partly measuring itself.** The first judge's criteria matched the layout
   the skill asked for, so a second judge with no criteria was added. The two agree on only
   about 63% of judgments.
2. **On thin drafts, most of the junior's apparent edge was a broken rewrite step.** A
   two-classifier diagnosis of 74 missed quiz items found only 4 answers lost in the rewrite.
   But Haiku's rewrite dropped facts the brief stated (−10 points on brief items). Fixing the
   rewrite instruction recovered most of the gap without questions.

## Confirmation (16 untouched cases, one run each)

Comprehension (Haiku / Sonnet):

| Arm | Natural | Seeded-implicit | Cost per plan (natural) |
| --- | --- | --- | --- |
| Junior-dev (shipped) | 0.899 / 0.906 | 0.780 / 0.774 | $0.126 / $0.411 |
| Rewrite only | 0.899 / 0.920 | 0.681 / 0.787 | $0.004 / $0.081 |
| SelfReview | 0.895 / 0.951 | 0.737 / 0.771 | $0.008 / $0.161 |
| Opus alone | 0.903 | | $0.074 |

Paired differences (bootstrap over cases):
- Seeded, Haiku, Junior-dev minus rewrite: +0.099 [0.025, 0.175].
- Natural, Sonnet, Junior-dev minus SelfReview: −0.045 [−0.094, 0.000].
- Every other interval spans zero.

Clarity, Junior-dev's share of judgments won (Haiku / Sonnet), with 95% intervals over cases
in the data:

| Junior-dev against | Mode | Rubric judge | Holistic judge |
| --- | --- | --- | --- |
| SelfReview | natural | 0.16 / 0.16 | 0.25 / 0.56 |
| SelfReview | seeded | 0.41 / 0.34 | 0.59 / 0.41 |
| Rewrite only | natural | 0.25 / 0.34 | 0.50 / 0.50 |
| Rewrite only | seeded | **0.66** / 0.34 | **0.88** / 0.44 |
| Opus alone | natural | 0.50 / **0.84** | **0.81 / 0.94** |

At equal length, pooled over both authors:
- Junior-dev against SelfReview: 0.23 (rubric) and 0.42 (holistic) in natural mode; 0.39 and
  0.35 in seeded mode.
- Junior-dev against Opus alone: 0.79 and 0.90.

**Decision rule.**
- **Useful** (≥65% of judgments against SelfReview, comprehension within 3 points, length
  within 1.5×): not met, for either author, in either mode.
- **Worth it** (≥45% against Opus alone, comprehension within 5 points, cheaper):
  - wins: met;
  - comprehension: met;
  - cost: not met. With the default Sonnet junior, Junior-dev costs more than Opus alone. A
    Haiku junior would cut the cost but is untested.

## GitHub Copilot

The research is in [copilot-compat-2026-11-19.md](copilot-compat-2026-11-19.md). The Copilot
CLI and VS Code read the plugin's Claude-format files as they are. The changes it needed:
- Copilot's tool names and hook payloads;
- PowerShell hook commands on Windows;
- a helper path that does not depend on `${CLAUDE_PLUGIN_ROOT}`;
- a Copilot backend for the isolated junior.

Live runs on the Copilot CLI, with the plugin installed into a throwaway config
(`evaluation/junior_dev/live-results/copilot/`):
- **Triggering:** 16 of 16 plan prompts (8 prompts × Haiku and Sonnet), 0 of 12 routine
  prompts.
- **Fidelity:** all 16 triggered loops ran start, question rounds, the rewrite and the report.
  14 ended on a correct teach-back, and 2 Haiku runs stopped at the 6-round cap before one, as
  the skill allows. 3 of 16 closing messages left out the changes and holes. After a wording fix, 4 of
  4 reruns included them.
- **Cost per review session:** Haiku 1.5–3.4 AI credits, Sonnet 16–39.
- **Friction:** the helper sits outside the project, so Copilot asks the user once to approve
  it.

Not tested:
- VS Code itself (its hooks are in preview);
- JetBrains;
- the cloud coding agent, which has no user-level plugins.

In Claude Code, the hooks trigger 8 of 8 (Haiku) and 5 of 5 (Sonnet); without them, the
description alone triggered 6 of 8 and 0 of 5.

## Limits

- Judges and graders are all Claude models. Opus judged its own family's writing.
- The cases are synthetic, written by Opus. Plans written for real projects may differ.
- Confirmation ran once per case per arm on 16 cases, so the intervals are wide. The plan
  called for 3 runs; weekly usage limits cut that.
- The tournament runs each role as a separate agent, not inside a real Copilot session. Only
  the live runs test the real harness.
- The junior's distinct output, the list of questions the author could not answer, was not
  measured as a benefit: too few cases plant deliberate gaps.

## Recommended default

1. **The cheapest proven gain:** have the author rewrite the file once for a newcomer, using
   the skill's step 6. Haiku does this for about $0.004 a plan, at Opus-level comprehension
   in natural mode.
2. **Keep the junior loop for thin drafts**, especially from Haiku. It is where the questions
   measurably add something, and it gives the user a list of open questions.
3. **If cost matters, run the junior on Haiku** (`--model haiku`) and measure it before
   relying on it. A Sonnet junior makes the loop dearer than Opus alone.

Which of these the plugin does by default is the user's decision. As shipped, it runs the
full loop (questions, rewrite, teach-back) every time a plan or diagram file is written.

## Blind pairs to rate

runs, labelled A and B at random, for the user to rate for themselves. The key is in a
