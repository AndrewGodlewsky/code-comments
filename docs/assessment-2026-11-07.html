Is the Code Comments thesis right?

An honest review of your theory against the evidence: the outside research, and the 778 graded agent runs ($15.29) we have done so far.

Short answer: the theory is not disproven. In its current form, though, it is probably wrong in three important ways and right in one.

Right: the problem is real. A separate docs folder drifts from the code. Agents and people both read code and nearby comments first. Wrong or stale explanation actively harms models. That is the best-supported finding in the whole project.

Probably wrong:

  1. Measured evidence that documentation makes agents more correct is weak.
  2. Today's "weaker" models already infer most of what they need from the code, and the strong ones already write good comments without being asked.
  3. The knowledge that matters most, "this affects that" across modules, is exactly the knowledge that is not at the point of edit.

Untested: the version of the claim that could still be true has not been tested yet: real, large, cross-module codebases over many changes. Our experiments never reached that regime.

Your thesis, claim by claim

Your theory bundles seven separate claims, and each has its own evidence. The evidence column cites the research reports in docs/research/ (R1-R4) and our own runs.

ClaimStatusWhat the evidence says
// T1
Large, changing codebases need three layers: decision memory, instructions and intent, and documentation of what the code does		 MIXED Real systems keep these stores, but they split knowledge by how long it lives and how much code it covers, not by "why" versus "what" (R4). The "what the code does" layer is the one capable models need least, because they read it from the code (R2).
// T2
A docs folder makes the AI less likely to get a future change wrong		 WEAK Widely reported by practitioners, but weakly measured. Two controlled studies of agent context files found no correctness gain. AI-generated context files gave no average gain and cost 20-23% more. One small preprint found about +9 points (R1). Your experience may be real, but it is not confirmed in general.
// T3
A docs folder becomes a second source of truth that drifts, and people won't keep it updated		 SUPPORTED Strongly supported. 82% of top projects had stale doc references at some point. Only 37% of agent pull requests that changed code also touched docs. Agents followed a stale instruction file over the code in 90% of convention conflicts (R1, R3).
// T4
Frontier models need documentation less; weaker models struggle without it		 REFINED Benefit tracks headroom and knowledge the code lacks, not model tier. The weakest models gain little because they can't use the context. Frontier models gain a lot when the context holds facts the code doesn't (R2). In our smoke run, Haiku 5.5 (our "weaker" reader) solved every task from the code alone.
// T5
Comments at the point of edit improve edit quality and prevent mistakes		 UNTESTED Not yet shown either way where it matters. Correct comments sometimes help models; wrong ones reliably hurt (ledger P-01, the only grade-A evidence). Our small sequences could not test it: a reader with no comments passed all 10.
// T6
People editing AI-written code will struggle without comments		 NOT SUPPORTED The one controlled trial (151 developers) found no penalty for editing AI-assisted code, though it did not vary comments. Comments raised people's confidence more than their accuracy (R3).
// T7
Context next to the code stays truer than a separate folder		 PARTLY Comments change together with code far more often than docs (90-97% of comment changes happen with a code change). They still lag at callers and interfaces, and stale comments turn up in maintained projects (R3).

What we actually ran, and what it showed

Research: 13 books and papers, 33 principles, four focused reports (R1-R4), and an independent citation audit —— The problem (drift) is well evidenced. The benefit (better agent edits from documentation) is weakly evidenced. No study compares maintained inline comments with a docs folder over many changes.

What these results do not mean. They don't show that comments are useless. They show that on small, self-contained code, modern models don't need extra context: the code already shows how things work. Your claim is about large, cross-module codebases, and we have not tested one yet.

The strongest case on each side

For continuing (the steelman)

  1. The problem is real and well evidenced. Two sources of truth drift, for people and for AI maintainers alike. Any practice that removes the second source removes a known failure.
  2. We haven't tested the right regime. Big repositories, edits whose effects land in files the agent never opens, long sequences of changes, and humans editing by hand. Small synthetic cases can't reproduce any of these.
  3. Avoiding harm is well supported. Wrong comments mislead models: that is the strongest LLM evidence in the project. A skill whose first duty is "fix the comment your change made false" has value even if added comments help little.
  4. Non-derivable knowledge is valuable and rarely recorded. Constraints and rejected alternatives almost never reach comments today (0.4% of rationale sentences, R4). When agents had the reason a change was rejected, they stopped re-proposing it (one study: 7 of 10 sessions without it, 0 of 10 with it).
  5. It's cheap. The lean skill added about 13% cost per sequence, against 73% for the docs folder, and nothing to maintain beyond the code itself.

Against continuing (the steelman)

  1. Models already do it. Sonnet 5.5 writes the why into comments 90% of the time with no skill. The skill's extra contribution over a strong default is small, and each model generation shrinks it.
  2. The premise is weak. Measured evidence that documentation of any kind makes agents more correct is thin. The docs folder you want to replace may help less than it feels like it does.
  3. The mechanism misses the most valuable case. Cross-module effects are exactly what you can't see at the point of edit. Inline-only works best for local knowledge, which is the kind models can most often recover from code anyway.
  4. Comments drift too. A stale comment right where someone edits may mislead more than a stale document nobody opens.
  5. Proving it is expensive. A 10-point effect needs roughly 160-240 paired reader steps per model tier, on real repositories in containers (R2). Effects are likely to be small, if they exist at all.

The core tension in the idea

Your strongest argument for the docs folder is that it explains relationships: "this code affects that." Your strongest argument for inline comments is that they're seen at the point of edit. These pull against each other. A relationship spans two places, and an edit happens in one of them.

An agent editing module A sees A's comments. If the fact that matters ("B sorts these names as strings, so keep the width fixed") is written only in B, the point of edit doesn't help. The fix within your design is a short pointer at the dependent site ("callers rely on this width: see compactor.py"). That puts the burden on the writer to know every place that depends on a fact. That is the same "which documents does this change affect?" problem you wanted to escape, moved into the code.

This doesn't kill the idea, but it means the thesis has to win on two things at once: local knowledge, where it is cheap but often redundant, and cross-module pointers, where it is valuable but hard to maintain. Only a test on real cross-module code can show which way it falls.

Mistakes I made along the way

  • I treated a stand-in score as the goal. The first eval measured how well the skill writes comments, and I recommended tuning against it before we had measured whether comments help anyone.
  • I put the weaker model in the wrong role. In the tournament Haiku was writing comments, but I described it as testing your weaker-reader claim.
  • I mislabelled the sequences. Seven were labelled "needs knowledge only from the old evidence". A no-context reader passed them all, because the knowledge was embodied in neighbouring code.
  • What survived: the infrastructure is sound and reusable. That includes the isolated runner, offline regrading, the paired analysis, the docs-folder arm, the leak guard, and now a no-context control that would have caught the mislabelling earlier.

Your options

Option A · recommended

One decisive test, then decide

Run the downstream test on 2-3 real repositories (cyclopts, narwhals, jsonargparse). Use containers and a vulnerability scan, and count a step only if a no-context reader fails it. Write the stop rules down first.

  • Pro: answers the actual claim, in the regime it is about
  • Pro: the infrastructure is built
  • Con: costs real money and effort; likely a small or null result
Roughly $30-80 in model spend at a capped budget, plus build time
Option B

Ship a modest hygiene skill

Release the lean variant as a "keep comments true, capture the non-obvious why" discipline. Make no claims of better agent outcomes.

  • Pro: cheap and low-risk; the harm-avoidance part is well supported
  • Pro: useful to people reading code
  • Con: unproven benefit; may add little over the model's default
Small: packaging and installation checks (#12)
Option C

Pivot to where evidence is stronger

Narrow the product to recording rejected alternatives and external constraints, plus a lint that flags comments mentioning code that no longer exists.

  • Pro: targets the best-evidenced gaps
  • Pro: the lint is mechanical and fully in-code
  • Con: a different, smaller product than you set out to build
Moderate: new design and eval cases
Option D

Park it

Stop here and keep the research and tools as a record. Revisit if model behaviour changes, or if you see the problem bite in a real large project.

  • Pro: no further cost
  • Pro: the result is honestly recorded
  • Con: leaves the central claim untested
None

What would settle it

Write these down before running Option A, so the result can't be rationalised afterwards:

  1. Does context matter at all? If fewer than about 1 in 5 real cross-module steps fail the no-context control, these agents rarely need added knowledge. Park the efficacy research.
  2. Does inline help? Measure on at least 100 paired reader steps with a weaker reader. If inline minus code-only is under 5 points, with the upper end of the interval under 10, record "no meaningful benefit" and choose B, C or D.
  3. Is inline better than docs? If the docs folder beats inline by 5 points or more, your placement claim is wrong. That is still worth knowing.
  4. The thesis survives if inline beats code-only by about 10 points on non-derivable steps for a weaker reader, at lower cost than the docs folder.

My recommendation

Do Option A once, capped at a budget you choose, with the stop rules above. Then take Option B regardless of the outcome, because the harm-avoidance part is supported and costs little. If Option A comes back null, stop the efficacy research there.

My honest prior is that the effect on agent correctness will be small or absent for current models on most code. That's because the strong ones already comment well, and both strong and weak ones read code well. The best chance of a real effect is in large codebases with cross-module constraints that aren't written anywhere else, and that is exactly the test still missing. Expecting a null result is no reason to skip the test. It's a reason to make it small, decisive and pre-registered.
