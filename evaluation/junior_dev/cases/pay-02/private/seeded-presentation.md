# Refunds

- [ ] Webhooks: the provider sends refund.succeeded / refund.failed whenever it gets around to it (can be days), and the signature has to be verified first (bad signature → 400, nothing changes), then we look up the reversal by metadata.refund_id rather than provider_refund_id because that one might never have been saved if the original call timed out, and in a single transaction we only allow pending→succeeded or pending→failed, so if the refund entry is already in a final state it's just a no-op, which also takes care of duplicates and out-of-order deliveries, and we return 200 for all valid deliveries including the no-ops so they stop redelivering, plus an audit line for the change.
- [ ] Admin submits amount (cents, defaults to the full headroom), reason, optional note; POST goes to our server, browser never calls the provider.
- [ ] Hourly reconciliation: anything pending > 1h, ask provider by metadata.refund_id. succeeded/failed → same as the webhook handling above; provider has no record → failed ("never reached provider"), audit, alert finance channel, admin can resubmit; still pending → try again next hour. (Keeps everything checked well inside 24h.)
- [ ] Available balance = captured_amount minus pending + succeeded refunds (failed not counted).
- [ ] Provider call (after commit!): create-refund with charge id, amount, idempotency key = the refund row's id, also metadata.refund_id = same id, 10 s timeout.
- [ ] Lock payment row FOR UPDATE, recompute the remaining under the lock. Too much → rollback, tell the admin the current remaining, nothing goes to the provider; otherwise insert the R-row as pending (its UUID = idempotency key), audit "refund requested" with admin/amount/reason/note, commit, and now the pending amount eats into the headroom. Two admins at once: the second one blocks on the lock until the first commits.
- [ ] On succeeded: order status recomputed from succeeded only (sum == captured → Refunded, else Partially refunded) and the customer email gets queued with the amount. This only happens on the one pending→succeeded transition, so one email per refund.
- [ ] Responses: 2xx means accepted only, so store provider_refund_id, it stays pending, audit; 4xx → failed, keep provider's message (admin sees it), audit, no retry, amount freed; timeout/5xx → retry x3 at 1/2/4 s, same key (so at most one refund at provider), and if all of them fail it stays pending and is audited "provider unreachable" since the provider might actually have it. Reconciliation sorts it out.
- [ ] Payment page: server loads payment + refunds, shows captured, each refund's status, remaining; refund form only if payment captured + admin has refund permission. Server re-checks permission/captured, amount > 0, reason in list; error → nothing stored.
- [ ] Tables: payments (charge id, captured_amount, status); refunds (id UUID, payment_id, amount, reason, note, admin_id, status pending/succeeded/failed, provider_refund_id, failure_message, timestamps); audit_log, one per request and status change. Provider keeps its own record linked via our id.
- [ ] After submit the admin sees Pending (or Failed + provider message) and the new remaining; no email, no order change yet.
- [ ] On failed (webhook or reconciliation): money back in the remaining, page shows Failed, no email, order unchanged.
