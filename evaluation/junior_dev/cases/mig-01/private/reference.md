# `users`: MySQL to Postgres migration checklist

**Terms used below**

- **`users.write_mode`** (string flag): how `UserRepository` writes. It reads the flag once at the start of each write. Values, in order of use: `mysql_only` (today) → `dual_mysql_primary` → `frozen` → `dual_pg_primary` → `pg_only`. A change reaches every instance within 30 s. **Confirmed** means `app_flag_value` shows the new value on every instance.
- **Write deadline**: a write that has not committed 5 s after it read `write_mode` is rolled back. So 5 s after a mode change is confirmed, no write in the old mode can still commit.
- **`users.read_from_pg`** (percentage flag, bucketed by user id): the share of reads served from Postgres. Until `pg_only`, a Postgres read that errors is served from the MySQL replica instead, so reads never fail.
- **Source of truth and secondary**: MySQL is the source of truth until step 8 sets `dual_pg_primary`, and Postgres from then on (unless rolled back). The other database is the secondary.
- **Safe copy**: the only way a row is written into the secondary (inline copy, backfill, sweeper). If the id is in that database's `users_tombstones`, skip it. If the id is absent, insert the row. If it is present, replace it only when the incoming `version` is higher.
- **Tombstone**: every delete removes the row and inserts its id into `users_tombstones` in the same transaction, in both databases. A copy and a delete of the same id cannot interleave: both first take a per-id lock (`pg_advisory_xact_lock(id)` in Postgres; a locking read of the id in `users_tombstones` in MySQL).
- **Pending tables**: `users_pg_pending` (in MySQL) and `users_mysql_pending` (in Postgres), with columns `(user_id, token, created_at)`. A row means "this user's copy in the other database may be behind". The source-of-truth write upserts it in the same transaction as the user change, with a new token each time; `created_at` keeps its first value. Because it commits with the change, it survives a crash right after the commit. Repair does not use `app.jobs`: an enqueue can fail after the commit, and a job that runs out of retries waits in `jobs:dead` for a person.
- **Sweepers**: the MySQL sweeper drains `users_pg_pending`, reading from the MySQL primary and writing to Postgres. The Postgres sweeper drains `users_mysql_pending` in the other direction. Every 10 s, each takes the rows whose `created_at` is more than 5 s old. For each row it notes the token, re-reads the user's current row from its source, and safe-copies it; if the row is gone, it deletes the user in the target and adds a tombstone. It then deletes the pending row only if the token is unchanged. A failed copy leaves the row for the next run.
- **Comparer**: a job that walks both databases 10,000 ids at a time and compares id, `version` and a hash of the other columns. It reads MySQL from the replica and pauses while `mysql_replica_lag_seconds` > 5. It re-checks each difference on the source-of-truth primary 5 s later. A difference that is still there is a mismatch: the comparer adds that id to the pending table in the source-of-truth database, and the sweeper repairs it. Each pass reports its mismatch count.

## Checklist

- [ ] **1. Create the new tables.**
  - *Starts:* a schema migration.
  - *Changes:* Postgres gets `users` (same columns; `id BIGINT GENERATED BY DEFAULT AS IDENTITY`; unique `email`), `users_tombstones`, `users_mysql_pending` and `users_backfill_progress` (one row: `last_copied_id`, `target_max_id`). MySQL gets `users_pg_pending` and `users_tombstones`.
  - *If it fails:* nothing uses these tables yet. Fix and re-run.

- [ ] **2. Deploy the new `UserRepository`, both sweepers and the comparer**, with `users.write_mode = mysql_only`.
  - *Starts:* a normal deploy.
  - *Changes:* nothing yet. Behaviour stays the same until the flag moves.
  - *If it fails:* roll the deploy back.

- [ ] **3. Turn on dual writes: set `users.write_mode = dual_mysql_primary`.**
  - *Starts:* a flag change.
  - *Changes:* each write now runs as follows.
    1. One MySQL transaction changes the user (a delete also adds the MySQL tombstone), reads back the full new row, and upserts `users_pg_pending`.
    2. That transaction commits. The write has now succeeded.
    3. The row is safe-copied into Postgres, with a 500 ms timeout. A delete removes the Postgres row and adds the Postgres tombstone in one transaction.
    4. If the copy succeeded, the pending row is deleted, provided its token is still ours.
  - New ids still come from MySQL AUTO_INCREMENT; Postgres receives them explicitly.
  - *Done when:* confirmed on every instance (up to 30 s).
  - *If the Postgres copy fails or times out:* the request still returns success. The pending row stays, and the MySQL sweeper repairs Postgres within about 15 s, or once Postgres is back if it is down (the pending table just grows).
  - *If Postgres errors or latency hurt requests:* set `mysql_only`. Once that is confirmed, plus 5 s, truncate the new tables in both databases and start again from this step.

- [ ] **4. Backfill existing rows.**
  - *Starts:* at least 1 minute after step 3 is confirmed on every instance. By then no write made under `mysql_only` can still commit (write deadline), and the replica, which the backfill reads only while its lag is 5 s or less, already holds every such write.
  - *Changes:* at start, it reads `target_max_id` = max(id) on the MySQL primary and stores it, with `last_copied_id = 0`, in `users_backfill_progress`. Higher ids are already dual-written. Then it loops:
    1. If replica lag is above 5 s, wait and check again.
    2. Read the next ≤ 2,000 rows with `last_copied_id < id ≤ target_max_id` from the MySQL replica, in id order.
    3. In one Postgres transaction, safe-copy the batch and set `last_copied_id` to its last id.
  - Stale replica rows lose to newer dual-written versions. Ids deleted meanwhile are blocked by tombstones.
  - *Done when:* a read finds no rows left at or below `target_max_id`.
  - *If it fails:* the batch's transaction rolls back, so progress and copied rows always agree. After a crash or restart, it continues from `last_copied_id`.

- [ ] **5. Verify.**
  - *Starts:* the backfill is done.
  - *Changes:* run full comparer passes. Mismatches go to `users_pg_pending`, and the MySQL sweeper repairs them. Repeat until one complete pass reports **0 mismatches**. From then on the comparer also runs nightly.
  - *If it fails:* a pass that keeps finding mismatches means a bug in the write path. Fix it and pass again. Reads do not move until a pass is clean.

- [ ] **6. Move reads: `users.read_from_pg` 1% → 10% → 50% → 100%.**
  - *Starts:* a clean pass from step 5.
  - *Changes:* the read flag goes up one level at a time. Hold each level for at least 1 h, as long as Postgres read errors and p99 latency stay within the MySQL baseline. MySQL remains the source of truth, and dual writes continue. Postgres read errors fall back to the MySQL replica.
  - *If it fails:* set the flag to 0. All reads are back on MySQL within 30 s.

- [ ] **7. Hold reads at 100% for at least 3 days.**
  - *Starts:* step 6 reaches 100%.
  - *Done when:* 3 days have passed and the latest nightly comparer pass shows 0 mismatches.
  - *If it fails:* use the step 6 rollback. The 3 days start again once reads are back at 100%.

- [ ] **8. Switch the source of truth (one write pause of at most 90 s).**
  - *Starts:* step 7's conditions are met. Pick a quiet time.
  - *Changes:*
    1. At T0, set `users.write_mode = frozen`. Frozen instances answer every write with a retryable 503. Reads keep working.
    2. Wait until `frozen` is confirmed (up to 30 s), plus 5 s for the write deadline. After this, no instance can be writing in the old mode while another writes in the new one.
    3. Wait until `users_pg_pending` is empty. The sweeper clears it in about 15 s.
    4. On the MySQL primary, read `n`, the `AUTO_INCREMENT` counter of `users`. The counter never goes down, so `n` is above every id MySQL has issued, including erased ids still listed in `users_tombstones`. In Postgres, run `ALTER TABLE users ALTER COLUMN id RESTART WITH n`. From now on Postgres assigns new ids with no collision.
    5. Set `users.write_mode = dual_pg_primary`. Each instance resumes writes when it picks this up (up to 30 s).
  - *If it fails:* if sub-steps 2 to 5 are not complete by T0 + 60 s, set `dual_mysql_primary` instead. MySQL stays the source of truth, and nothing needs undoing (Postgres still receives ids explicitly). Retry another day. Either way, the last instance resumes writes by T0 + 90 s.

- [ ] **9. Run with Postgres as the source of truth for at least 14 days.**
  - *Starts:* step 8 completes.
  - *Changes:* the write path is step 3 mirrored:
    1. A Postgres transaction changes the user (new ids come from the Postgres identity; a delete also adds the Postgres tombstone), reads back the row, and upserts `users_mysql_pending`.
    2. It commits. The write has now succeeded.
    3. The row is safe-copied into MySQL with its explicit id (500 ms timeout). Inserting an explicit id also moves MySQL's AUTO_INCREMENT past it.
    4. If the copy succeeded, the pending row is deleted, provided its token is still ours.
  - *If the MySQL copy fails:* the request still succeeds, and the Postgres sweeper repairs MySQL from Postgres.
  - Reads stay 100% on Postgres, with the MySQL replica as fallback. The nightly comparer now treats Postgres as the truth and sends mismatches to `users_mysql_pending`.
  - **Rollback** (allowed at any time in this step). It needs Postgres reachable, because `users_mysql_pending` is the only record of what MySQL may be missing.
    1. At T0, set `users.write_mode = frozen`. Wait until it is confirmed, plus 5 s.
    2. Wait until `users_mysql_pending` is empty.
    3. In MySQL, run `ALTER TABLE users AUTO_INCREMENT = <the Postgres identity's next value>`. MySQL then cannot reissue an id Postgres has used, such as one created and erased before its MySQL copy landed.
    4. Set `users.write_mode = dual_mysql_primary` and `users.read_from_pg = 0`.
    - *If the rollback runs long:* if sub-steps 1 to 4 are not complete by T0 + 60 s, set `users.write_mode = dual_pg_primary` again. Postgres stays the source of truth; retry later.
    - Either way, writes resume by T0 + 90 s. After a completed rollback MySQL has every write, and the plan continues from step 6.

- [ ] **10. Switch to Postgres only, then retire MySQL.**
  - *Starts:* at least 14 days in step 9 since the last switch, with no rollback, and a clean nightly comparer pass.
  - *Changes:*
    1. Set `users.write_mode = pg_only`. Writes go to Postgres alone, and reads no longer fall back to MySQL. **This is the point of no return:** from the first `pg_only` write, MySQL is missing data, so a lossless rollback is no longer possible.
    2. Once `pg_only` is confirmed, stop both sweepers and the comparer.
    3. Take a final MySQL backup of `users`.
    4. Drop MySQL `users`, `users_pg_pending` and `users_tombstones`, and Postgres `users_mysql_pending`, `users_tombstones` and `users_backfill_progress`. Remove the MySQL code paths in a later deploy.
  - *If it fails:* a failed backup or drop is simply retried. There is no going back to MySQL after `pg_only`.
