# Notifications -> own service

So, the overall idea before the steps (some steps repeat things from here, and some details only appear here): notif-svc takes over sending. It has its own database, which the monolith never touches, and in that DB is the send ledger, the `deliveries` table, keyed on notification_id (primary key) with type, email, payload, status (pending / sent / failed), attempts, next_attempt_at and created_at. The listener in notif-svc that takes broker messages does INSERT ... ON CONFLICT (notification_id) DO NOTHING with status pending, attempts 0 and next_attempt_at now(), then commits, then acks the message, so the ack is after the commit and before anything is sent. That means a crash before the commit gets the message redelivered after 30 s, because the broker is at-least-once and redelivers anything not acked within 30 s, possibly to another consumer instance. A crash between commit and ack means the redelivery's insert does nothing and it is just acked. The same happens when the forwarder publishes something twice, and nothing goes out again.

## Steps

1. Flip the flags, one type at a time: `shipping_update` first, then `order_confirmed`, then `password_reset`, each at least 3 days on the new service before the next, with password_reset gated (see 8). Before the first flip you want dashboards for publisher backlog, ledger pending/failed counts and enqueue-to-MailRelay latency (created_at to sent). Setting `notify.route.shipping_update = service` means new rows get route service within 10 s; older rows keep route monolith and the legacy loop finishes them, retries included. For 3 days, check each day that the service-routed rows in the monolith table equal the rows in the ledger and that failed isn't higher than on the old path. Rolling back is the flag going back to monolith. New rows after that go to the old worker, while the ones already routed to the service still go through the outbox thing and are sent by notif-svc, since the publisher and the service keep running and no row changes route, so nothing is lost or sent twice. This is the same for every type.

2. notif-svc sender: polls every 1 s, up to 50 rows with status pending and next_attempt_at <= now() using FOR UPDATE SKIP LOCKED, renders (templates live in the service now), calls `mailrelay.send(..., idempotency_key=notification_id)` and commits each row on its own. Success = sent. Error or timeout = attempts + 1 and next_attempt_at = now + 1, 2, 4 or 8 minutes (5 tries total), and on the 5th failure it's failed and on-call gets paged. If the process dies after MailRelay accepted but before the commit, the row is still pending and is sent again on the next pass; MailRelay drops the repeat (it remembers keys for 24 h) and returns success, and the row is marked sent, so one email.

3. Really the first thing to deploy, before everything: `_deliver` in the old worker passes `idempotency_key=row.id` (row.id = the UUID that `enqueue_notification` makes, which is the same notification_id used everywhere later). Then a batch left pending after a crash post-acceptance is re-sent with the same key, MailRelay drops it and says success, and the rows become sent, so the ~30 duplicates a week go away.

4. Then the route. Column `notifications.route`, 'monolith' or 'service', default 'monolith'. `enqueue_notification` is still called by business code inside its own transaction, unchanged; the monolith row is the first durable record and only exists if that transaction commits. It reads `flags.get("notify.route." + ntype)` within the caller's transaction and writes it into route, and the legacy poller's query gets `AND route = 'monolith'`. All flags start monolith. If reading the flag fails it writes monolith. The route is set once at enqueue and never changed, so there is one sender per notification: the old worker takes monolith rows and the publisher takes service rows. The flag takes up to 10 s to reach every instance, so rows in that window could go either way, but each still has exactly one route.

5. The relay (outbox publisher) in the monolith, deployed after notif-svc is live; with all flags at monolith it does nothing. Every 1 s, in one transaction: up to 100 rows with route = 'service' and status = 'pending', SKIP LOCKED, publish each to `notifications.requested`, wait for the broker's confirmation, set status published, commit. Broker down or no confirmation: the row stays pending and is tried again on the next poll, and an alert fires when the oldest one is over 60 s. Crash after publishing but before committing: published again, and the listener ignores the repeats. After published, the monolith is done with it; the publisher never sends email or retries sends. Message = notification_id, type, email, payload, created_at, which is all the service needs to render and send, since it can't read the monolith DB.

6. order_confirmed when shipping_update has had 3 days with the checks passing; same as 1; record its p99 latency over the 3 days.

7. Build notif-svc and its DB (the ledger above) after step 4 is live; it receives nothing at first.

8. password_reset only if order_confirmed has had 3 days on notif-svc AND its p99 is under 60 s; otherwise fix latency and don't flip. Alert at p99 60 s for password_reset, and roll back if it's breached.

9. Remove the old path when password_reset has had 7 days on the service and no route = 'monolith' rows are pending (if some are, wait for the old worker to finish them): delete `run_worker`, make `enqueue_notification` always write route 'service', and drop the flags. Keep the relay; it's the only path now.

Note on state: the notification, its route and pending -> published are in the monolith notifications table. The old path's pending -> sent/failed and attempts are also there (old worker, monolith route only). Messages in flight are in the broker. The service's status/attempts/next_attempt_at are in the ledger. The route per type is the monolith flag `notify.route.<type>`, which an operator sets.
