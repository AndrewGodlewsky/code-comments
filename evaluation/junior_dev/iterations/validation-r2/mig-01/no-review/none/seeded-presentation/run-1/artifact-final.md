# users migration (MySQL -> PG) - checklist

- [ ] Reads: ramp the read_from_pg percentage flag (bucketed per user id) through 1, 10, 50 and 100, holding at least an hour at each level as long as PG read errors and p99 stay within what MySQL does. If anything goes wrong, set it to 0, and within 30s everything reads MySQL again. When PG errors on a read, the repository just falls back to the MySQL replica, so reads never fail (this holds right up to pg_only). This is only allowed once the checker has done a full clean pass (0 mismatches), see the verification item further down. MySQL is still the primary the whole time and dual writes keep going.
- [ ] Tables. PG gets users (same columns, id is BIGINT GENERATED BY DEFAULT AS IDENTITY, email unique), users_tombstones, the PG-side outbox (users_mysql_pending) and users_backfill_progress (one row, last_copied_id and target_max_id). MySQL gets users_pg_pending and its own users_tombstones. Both outboxes have user_id, token and created_at columns; created_at keeps its first value and the token changes on every upsert. Do this first. Nothing reads these tables yet, so if it fails just fix and re-run.
- [ ] Cutover. Do this after reads have been 100% on Postgres for at least 3 days and last night's checker run was clean, at a quiet time. Note that the PG identity gets restarted in the middle of the cutover at n = the AUTO_INCREMENT counter of MySQL users, read on the primary, which never goes down and so is above every id MySQL ever handed out, erased ones (still sitting in users_tombstones) included, so PG can hand out ids without colliding. The cutover goes: set users.write_mode to frozen at T0 (instances in the write freeze return a retryable 503 on writes; reads are fine); wait for every instance to show frozen in app_flag_value (up to 30s), plus 5s more for the write deadline; wait until users_pg_pending (the outbox that lives in MySQL) is empty, which the catch-up worker clears within about 15s; run ALTER TABLE users ALTER COLUMN id RESTART WITH n in PG; then set write_mode=dual_pg_primary, and each instance resumes writes as it picks that up, within 30s. If you haven't finished by T0+60s, flip to dual_mysql_primary instead. Nothing needs undoing since PG is still given ids explicitly, so try again another day. The whole pause must stay at or under 90s, and with the 60s cutoff plus 30s of flag refresh it does. Because every instance is confirmed frozen first, you never get one instance writing MySQL-first while another writes PG-first.
- [ ] Backfill job: copies the existing rows from the MySQL replica into PG using the safe-copy rule, in id order, at most 2,000 rows a batch, and sleeps whenever mysql_replica_lag_seconds > 5. It writes last_copied_id to the progress table in the same PG transaction as each batch, so a crash or restart resumes from there, and a failed batch just rolls back together with its progress. When it starts it records target_max_id = max(id) read on the MySQL primary (last_copied_id = 0) and finishes when a read finds no rows left at or below it, since newer ids are dual-written anyway. Don't start it until EVERY instance is confirmed on dual_mysql_primary (flags take up to 30s), and then give it at least another minute, otherwise some mysql_only write could still commit or be missing from the replica. Stale replica rows lose against newer dual-written ones, and deleted ids get blocked by the tombstones.
- [ ] Deploy UserRepository, the two catch-up workers and the checker, with write_mode left at mysql_only, which behaves the same as today (roll back the deploy if it breaks). This happens right after the tables.
- [ ] 14+ days on PG primary (after cutover). Writes: a PG transaction with the user change (or delete plus PG tombstone; new ids come from the PG identity), reading the row back, plus a users_mysql_pending upsert, commit, then a safe copy to MySQL with the explicit id and a 500 ms timeout, which drags MySQL's AUTO_INCREMENT past it, then the outbox row is removed if the token still matches. If that MySQL copy fails, the request is still fine and the PG-side repair worker fixes MySQL from PG. Reads stay 100% on PG with the replica fallback. The checker still runs nightly, but now PG is the truth and its mismatches go to users_mysql_pending. To roll back during this time (PG has to be reachable, since users_mysql_pending is the only record of what MySQL might be missing): freeze at a new T0 the same way as the start of the cutover (frozen, confirmed, plus 5s), wait for users_mysql_pending to be empty, set MySQL's AUTO_INCREMENT to the PG identity's next value (ALTER TABLE users AUTO_INCREMENT = ...) so MySQL can't reissue an id PG gave out, e.g. one created and erased before its MySQL copy landed, then set write_mode=dual_mysql_primary and read_from_pg=0. If that isn't all done by T0+60s, put write_mode back to dual_pg_primary and try later; PG stays the truth. Either way the pause is at most 90s, and after a finished rollback MySQL has every write. After a rollback, pick the plan up again at the reads ramp.
- [ ] Dual writes on (write_mode = dual_mysql_primary), after the deploy. Per write: a single MySQL transaction does the change (or the delete plus a MySQL tombstone), reads the full row back and upserts users_pg_pending (user_id plus a fresh token). Then commit; that's when the write counts as done. Then copy into PG with the safe-copy rule, with a 500 ms timeout (a delete removes the row and writes a PG tombstone in one transaction). Then remove the outbox row, but only if the token is still ours. PG failing or timing out does NOT fail the request: the outbox row stays, and the sweeper fixes PG in about 15s, or once PG is back if it is down (the outbox just grows). Ids still come from MySQL AUTO_INCREMENT and are passed to PG. It counts as done once app_flag_value shows it on all instances (up to 30s). If PG hurts requests: go back to mysql_only, and once that's confirmed plus 5s, truncate the new tables in both databases and start over from here.
- [ ] Verification (after the backfill finishes): keep running full comparer passes. Mismatches land in users_pg_pending and the sweeper fixes them, until one whole pass reports zero. If it keeps finding things, there's a write-path bug: fix it and re-pass. It runs nightly from then on.
- [ ] Hold at 100% PG reads for 3 days and then check the nightly pass is at 0 before the cutover; if reads had to go back to 0, the 3 days start over once they're at 100% again.
- [ ] Retire MySQL once it has been at least 14 days since the cutover with no rollback and the nightly pass is clean: set write_mode=pg_only (writes only go to PG, no read fallback; this is the point of no return, from the first pg_only write MySQL is missing data and you can't go back losslessly), and once that's confirmed stop the catch-up workers and the checker, take a final backup, drop MySQL users, users_pg_pending and users_tombstones and PG users_mysql_pending, users_tombstones and users_backfill_progress, and remove the code in a later deploy. Backup or drop failures are just retried.

Notes (these apply to several items above):
- "Safe copy" means copying into whichever DB is currently secondary: skip ids in that DB's users_tombstones, insert if the id is missing, overwrite only when the incoming version is higher. Dual writes, the backfill and the sweepers all use it. Every delete writes its id into users_tombstones in both DBs, in the same transaction as removing the row, and a copy and a delete of one id can't interleave because both take a per-id lock first (pg_advisory_xact_lock(id) in PG, a locking read of the id in users_tombstones in MySQL).
- The repair workers (sweepers, catch-up jobs): the MySQL one drains users_pg_pending, re-reading the CURRENT row from the MySQL primary and copying into PG; the PG one drains users_mysql_pending the other way. They wake every 10s and grab outbox rows whose created_at is more than 5s old, note the token, safe-copy the row (or delete it in the target and add a tombstone if the row is gone), then delete the outbox row only if its token hasn't changed. A failed copy just leaves the row for the next run. The outboxes are written in the same transaction as the user change, so they survive a crash. app.jobs isn't used for this because an enqueue can fail after the commit and jobs:dead needs a human.
- checker = comparer: it goes through both DBs 10,000 ids at a time, comparing id, version and a hash of the other columns. It reads the MySQL replica (and pauses while lag > 5s), re-checks each difference against the source-of-truth primary 5s later, and pushes the ones that remain into the outbox in the source-of-truth DB. It reports a mismatch count per pass.
- write_mode values, in order: mysql_only, dual_mysql_primary, frozen, dual_pg_primary, pg_only. The repository reads it once at the start of each write, and any write that hasn't committed 5s after that is rolled back (the write deadline). MySQL is the source of truth until the cutover sets dual_pg_primary. read_from_pg is a percentage, per user id. Instances refresh flags every 30s.
