# orders-api secrets plan

1. Rotation (kick this off once the check in step 8 passes): the keys that are in the repo now (payments, mailer, geo) have been sitting in git for two years and nobody is going to rewrite history, so the only thing that makes them useless is rotating them at each vendor, one vendor at a time (payments, then mailer, then geo, each one only once the previous one is fully done): security on-call makes a new key at the vendor (the old one keeps working) and puts it straight into the vault themselves so no engineer ever sees it, which gets it a fresh version id, then wait — the workers re-poll every 5 minutes so allow 10 — and look at the health endpoint on every replica (anyone can, it only shows ids), and only when all 4 show the new version does security on-call kill the old key at the vendor; meanwhile the vault holds both versions and each replica's map flips to the new one at its next poll; if a replica is still stuck on the old version after 10 minutes don't revoke, check its logs for refresh warnings or restart it which forces a fresh startup load (the others keep serving), and if calls start failing with the new key security on-call writes the old value back as yet another version (old key still works, it isn't revoked) and the instances will pick it up inside 5 minutes, then fix it and start that vendor over from the new-key part.

2. The SecretCache. Per process, a dict of name -> (value, version id), in memory only; nothing goes to disk, env vars or logs (version ids are OK to log). Entries: payments_api_key, email_api_key, geocoding_api_key. The background refresher runs on a timer every 5 min after the startup load, re-reads all three, and when a version id changes it swaps that entry as one assignment so a request gets the old pair or the new pair and never a mix, and logs "<name> now at version <id>"; if the refresher's read fails, for the whole vault or for just one name, we keep the last good value for whatever couldn't be read, update the ones that could, warn (name + error only), and just try again on the next tick, without the app exiting or going unready.

3. Permissions — this is the very first thing, as soon as the plan is approved, before anything is written anywhere: orders-api-prod (the identity the 4 prod replicas run as) -> read-only on orders-api/prod/* and nothing else. Only security on-call writes prod. Engineers: read and write on orders-api/dev/* with their own login, no access at all on prod. Test it: an engineer reading a prod path and orders-api-prod reading a dev path must both be denied, and if either gets through, fix the policy and test again before moving on (nothing reads the store yet so no customer can notice). All of this lives in the store's access policies. Encryption is per-environment KMS (prod KMS key for the prod path, dev KMS key for the dev path), and every write to the secret store gets a new version id.

4. healthz: add secret_versions (ids, not values) to the JSON body, e.g. {"status": "ok", "secret_versions": {"payments_api_key": "<id>", ...}}. It's answered on every GET /healthz (the readiness probe, or a person poking pods during the rollout) straight out of the in-proc map and never calls the vault, so a vault outage after startup can't make a pod unready — the versions it shows just stay at the last good ones until a refresh works. This is what step 1 and step 8 check.

5. Startup: secrets.py runs in main at process start before the HTTP server comes up, which is why readiness can't pass until it's done; it picks the env from APP_ENV (prod/dev) and reads orders-api/<env>/* with whatever identity the process has (orders-api-prod in prod, the dev's own login locally), into the in-proc map. If the vault is down, access is denied or a name is missing — even if the other two came back fine, it never starts on a partial set — it retries the whole load three times with 2 s between tries and after that logs (names, never values) and exits with a non-zero code, so the pod never goes ready and — because deploys roll one pod at a time with maxUnavailable 0 and a new pod has to pass GET /healthz before an old one is stopped — the rollout just halts while the old replicas keep serving.

6. After the permissions in 3 pass their test: security on-call puts the current prod values into the store at orders-api/prod/* — first version of each — and an engineer makes sandbox keys at each vendor and writes them to orders-api/dev/*. At this point the prod values are in the store and also still in app.yaml and in the running images, which keep using them. Nothing reads the store yet so mistakes here are harmless, just re-write (that's a new version).

7. One merge for the code, once 6 is done (merging to main is what makes CI build the image and start the rolling deploy): secrets.py, the clients (PaymentsClient / mailer client / geo client) changed to call secrets.get(name) on every outgoing vendor call and put it in the Authorization header instead of copying the key in __init__ (so a refreshed key is used starting with the next request, no restart, and the map is the only copy), the healthz change from 4, delete the three api_key lines from config/app.yaml (non-secret stuff — URLs, timeouts, port — stays in the file, but the file is NOT a fallback for keys afterwards), make run sets APP_ENV=dev so local dev reads sandbox keys from the dev path with the dev's own login, and CI runs on every change and fails the build if config/app.yaml has an api_key entry in it, which blocks the merge. get() can't come back empty because startup needs all three and the refresher never deletes one; if a vendor rejects a key, e.g. a revoked one, that call fails like any vendor error today and the client logs the name and version id (no value) — which is exactly why step 1 never revokes early. While this rolls out, new pods hold keys in their map and the old pods still have their baked-in yaml keys until they're stopped (still valid, nothing revoked), so customers see no errors whichever way it goes; if a new pod can't load, it exits, the rollout halts, and you fix the vault or the access and re-run the deploy.

8. Then, once the rolling deploy has replaced all four, check all four instances report the first version for each of the three in healthz and that a payment/email/geocode call works; if anything is off, roll back by redeploying the previous image (its yaml keys still work since nothing's revoked yet), fix, and redo 7. Then go do step 1. And when the last old key (geo) has been revoked, update deploy.md so rollback only ever goes to images from the 7 merge or later, because any pre-migration image is dead (its baked-in keys no longer work); if one gets deployed anyway, its pods pass the old healthz (which only checks the server is listening) but every vendor call fails, so redeploy the current image straight away.

Background, for context: currently app.yaml is committed and baked into the image, config_loader reads it once at import and never again, and each client copies its key in at construction time; today's healthz says ok as soon as the server is listening; make run also uses the same file which means devs are on live keys. Open: Security hasn't decided yet whether there's a regular rotation schedule after this, or how often — this plan only does the one-time rotation (step 1 is the repeatable bit if they pick one).
