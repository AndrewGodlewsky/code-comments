# deploy checklist for catalog-web blue/green (notes)

- [ ] Flip the prod listener over to the candidate's target group. It's one change, the whole thing at once, nothing weighted. Stash the time in the run as `switched_at`. That's T, and the watch, the standby period and retiring the previous env are all counted off it. The previous env keeps running, so whatever requests were already in flight there just finish. Only do this once smoke has passed inside the gate deadline (see further down). If the flip call errors out, read the listener back. Still on the previous env means it's an abort, and nobody ever saw the new release. Actually on the candidate means the flip went through, so write T and carry on.
- [ ] Migrations. Before this, the build step's check throws out anything that drops, renames or changes the type of a column or table (pending = whatever isn't in the migration history table yet). Those go in some later release, after the release that still uses the thing has been retired, i.e. after its env got scaled down in the retire step of the deploy that replaced it. If the check fails, the run stops with nothing changed and goes to finish as failed. Then the pipeline runs a single `migrate` task out of the new image against the shared Postgres. Tables and columns all go in one transaction, which also writes their history rows. After that every new index gets built with CREATE INDEX CONCURRENTLY outside the transaction, so the live side's writes don't get blocked, and each one is recorded in the history table once it's done. Instances do NOT migrate when they boot, which is how it stays once per deploy. This all happens before any instance of the new release exists, and since it's all additive the live colour keeps working fine on the migrated schema. If the transaction blows up, it rolls back and the schema is unchanged. If an index build blows up, the task drops the invalid index it left, and the committed table/column stuff stays (additive, harmless). That index migration never got recorded, so the next deploy picks it up again. Either way the run stops, the new side never gets started, live keeps serving, and it's finish as failed.
- [ ] watch
  - 15 min from T
  - 5xx on the public listener, rolling 5 min window, threshold 1%
  - over threshold → rollback (the automatic kind, see "rollback" at the bottom)
  - an engineer can also kick off the pipeline's rollback job any time from T
  - old env is still up and nobody touches it
- [ ] Start of run: a merge to main kicks off the pipeline, which gets into the concurrency group (the deploy slot / lock, ours is called `deploy-catalog-web`). If someone else's deploy has it, you just queue. We hang on to it right through to finish, otherwise the next deploy could land its release on the colour we might still have to flip back to. If the run can't start or gets cancelled while queued, nothing's changed, and a re-run or the next merge starts over.
- [ ] Figure out who's live by looking at where the public listener forwards. That's literally the only lasting place it's recorded, there's no state file. The run just copies it into its run variables (`live_colour`, `new_colour`). Those, along with `gate_deadline` and `switched_at`, only exist while the run does. The other colour is the one we deploy into, and if it somehow still has instances (an earlier scale-down that didn't take), scale it to 0 here. If you can't reach the LB or it won't scale down, stop (users are fine) and finish as failed. (Do this right after getting the slot. The image build and the migration check come after it.)
- [ ] Build image.
- [ ] Bring up the candidate: 4 instances in its target group. Aim the internal test listener (8443, only reachable from CI) at that same target group, and set `gate_deadline` to now + 10 minutes. If those calls error, abort. Health: the LB pokes /healthz on each one every 10s, and all four have to pass 3 times in a row; anything that boots and then crashes just never gets there. Once health is through (after it, not at the same time), the smoke suite goes through the test listener, so it hits the new env while users are still on the old one. If health or smoke fails, or the deadline runs out first: abort.
- [ ] Retire: at T+30 (counted off `switched_at`), if nobody rolled back, scale the previous colour to 0. After that there's no quick flip back; a rollback is just a normal deploy of the previous release through all of this again. If the scale-down won't go, try 3 times a minute apart, then alert and finish as succeeded-with-a-warning. Users don't notice, since the listener is on the new side, and the next deploy's live-colour step scales it to 0 before using it.
- [ ] Between T+15 and T+30 the standby colour is still up and untouched. The auto watch is over, but if someone spots a problem an engineer can hit the pipeline's rollback job, same as the auto rollback.
- [ ] Finish (every stop above lands here): mark succeeded/failed and release the concurrency group (the run variables go away with the run), so whoever was queued carries on from figuring out who's live. Whatever side is at 0 instances is the one the next deploy goes into. If a run dies before getting here (lost runner, cancelled), CI fails it and lets go of the group on its own.

abort = only before the flip. Scale the candidate to 0 so it's idle and empty again and leave the prod listener alone (live keeps serving). Migrations stay applied, which is fine since they're additive. Finish as failed. If that scale-down fails, alert; the next deploy's live-colour step scales it to 0.

rollback = after the flip, up until retire. Point the front door back at the standby colour's target group, scale the new env to 0, alert. Don't touch migrations, ever; the schema stays as is. If repointing fails, keep retrying every 10 s and page on-call, and the run doesn't let go of the slot until the listener is back on the old side. Then finish as failed.
