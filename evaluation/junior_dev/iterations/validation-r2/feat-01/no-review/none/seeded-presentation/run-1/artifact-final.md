# CSV export plan

1. Worker side. The background export (also called the async export or big export below) loads its export entry by the `export_id` in the payload, and because the queue can hand over the same job more than once it looks at the status first: succeeded or failed means it's already over so it just returns, running with `object_key` already filled in means the file is done so it skips ahead to the mail part (see 8), and anything else means flip it to running, open a fresh multipart upload to `report-exports/{export_id}.csv` in the `exports` bucket, write the header and run the batch loop, 5,000 rows a go off the replica using `row_id > last ORDER BY row_id` plus the saved filters/cols, CSV-encoding into a buffer that goes up as the next part every time it hits 8 MB, leftover as the last part, then `complete_multipart` (that's the moment the file shows up at the key, before that nobody can see it) and then `object_key` gets written onto the row. If complete worked but writing object_key didn't, the next go just writes the file again and complete replaces it. Retries come after 60 s and then 300 s; attempts are numbered 1-3. If the row can't be read or updated, it raises and the queue retries.

2. Small reports. If `reports.row_count` (read off the replica) is 10,000 or less, the sync download happens: the export API returns 200 text/csv, header first, then pages over the replica 500 rows at a time and writes into the response, and the page turns that into a saved file. No job, no record, no storage. Note the count is the unfiltered total, so a big report with tight filters still goes the background way (more than 10,000 = background). The 60-second request limit is not a concern at 10k rows.

3. DB: new `report_exports` table (the "export record", "job row" or "exports row", same thing) in the primary DB, created by the release migration before any of the new code ships (if the migration fails the release stops and the page stays as it is today): id, user_id, report_id, filters, columns, status (queued, running, succeeded, failed; succeeded only once the mail is out), object_key (only set when the file is complete), error, created_at, finished_at. Rows are kept as history. Partial unique index on (user_id, report_id) WHERE status IN ('queued','running').

4. Polling: every 5 s on `GET /api/exports/{export_id}` while queued/running, stopping on succeeded or failed; if a poll errors it keeps the old label and tries again next tick. On page load it first calls `GET /api/reports/{report_id}/exports/latest` for the user's newest one. Labels: Queued, Running, "Done: we emailed you a download link", "Export failed. Click Download CSV to try again." Both endpoints 404 unless the export is the caller's own. The page doesn't remember anything except the id it's polling.

5. Failure stuff (various). Inline export: 503 if the replica dies before the first byte, a dropped connection if it dies mid-stream; the page shows the export-failed message and saves nothing, no automatic retry. Background: exception → `abort_multipart`, then re-raise for the queue; a crash or the 30-minute kill → the upload never completes so nothing is visible, and the bucket throws incomplete uploads away after 24 h; the next try begins again from row one with a new upload. After the 3rd attempt the queue's `on_final_failure` sets the job row to failed with error and finished_at first, then sends `report_export_failed`; if even that mail fails it's logged and that's it, the page says failed anyway. Since it's no longer queued/running, the user can click again and get a new row and job. Usually there's no file at that point because nothing finished uploading, but if the file got completed (object_key set) and it was only the link mail that kept failing, the row still goes to failed and the finished file just sits unused in the bucket until the 7-day rule removes it. If `enqueue` throws at request time, the record is set to failed ("could not queue") and the API gives 503 so the index won't block a retry click; the user sees the failed label right there. If the insert fails for any other reason it's a 503 and nothing is stored. No permission → 403 ("You can't export this report"), and if the count can't be read it's a 503. If the link mail fails, the attempt fails and the row stays running with object_key, so the retry only mails (see 1); a mail that went out before a failed status update just means a second mail with a fresh link.

6. The click: `POST /api/reports/{report_id}/exports` with the URL's filters and column order; `report.view` is checked first.

7. Over 10,000: insert the exports row as queued with the user, the report and the filters/columns (frozen from then on, so later changes on the page don't touch this export). If the unique index rejects it, there's already one going for this user+report, so return 200 with that one's id and status and start no new job. Otherwise `enqueue("report_export", {"export_id": id})` (just the id goes in the payload) and return 202 queued.

8. Done: `signed_url("exports", key, ttl_seconds=86400)` and `send_email(user_id, "report_export_ready", {report_name, url})`, and only then status succeeded + finished_at. The link dies after 24h and the file goes after 7 days via the bucket rule, so there's no cleanup.

Memory note: the worst case is one batch + one 8 MB buffer. ~2M rows ≈ 900 MB ≈ 115 parts (limit 10,000 parts), fine under 512 MB, and it should take a few minutes, inside the 30-minute timeout. Every path reads report rows from the replica only.
