### Holes
- Q10: Where does the run's state live while it waits up to 72 h for approval, or about 90 h for the window? If the CI job or runner is restarted during that time, does the run survive? (author: The run keeps no state of its own. The approval and its record live in CI, which the files say records who approved and when. The deploy state lives in the SSM values. The files do not say whether a CI run or runner survives a restart during the 72-hour approval wait or the window wait. This is listed as an open question. Every check after a wait reads SSM again, so the run does not depend on an earlier read.)
- Q11: What is the job that actually waits on the lock? Does it occupy a CI runner the whole time? What is a run's state when it is waiting on `staging` versus when it is waiting on `production-deploy`? (author: CI supports named locks, but the files do not say whether a job waiting on a lock holds a runner the whole time. While waiting on staging, the run has built and pushed the image and passed both suites, and nothing in SSM or the clusters has changed. While waiting on production-deploy, the approval is given and the run is inside the window, with no canary, and nothing in SSM or the clusters has changed. Whether the waiting job holds a runner is an open question.)
- Q20: During the canary the stable pods still run the old image. After promotion, how does the stable rollout happen (rolling, one pod at a time?), and what do users see during those up to 300 seconds? (author: The files do not give the stable deployment's update strategy, so it is not known whether pods are replaced one at a time. deploy.sh runs rollout status with a 300-second timeout. If the rollout is not done in time, the script exits before it writes SSM. What users see during the rollout is not in the files.)
- Q24: What happens to a run that is waiting for approval when a newer run for a later SHA passes staging? Does the older run's approval request stay open and can both be approved? (author: The files do not say whether CI closes an older approval request when a newer run starts, or whether both can be approved. The design keeps runs independent, so the older request stays open until someone approves it, rejects it, or 72 hours pass. If both are approved, the production check decides. The older SHA deploys only if it is still ahead of production's current_tag, and it is superseded if a newer SHA already reached production. If production is still behind, an older approved run can reach production while staging runs a newer SHA. This is a known risk. We also decided that the approval request names its SHA, so each approver sees what they approve.)
- Q27: The staging smoke tests: what do they check, and do they test the new image only through the staging URL? If the staging rollout succeeds but smoke fails, what do users of staging see during the rollback? (author: The files give the command, its length of about 3 minutes, and the staging URL it hits. They do not list what the smoke suite checks. It tests the new image only through that URL, so it sees whichever pods serve the staging URL. After a successful rollout that is stable running the SHA. What staging users see during a rollback is not in the files. Staging is internal only, so the users are internal.)
