# Plan: Refunds from the admin page

Today, support staff refund customers in the card provider's dashboard, so our database never learns about the refund. This plan lets admins issue full and partial refunds from our internal admin page. Our server reserves the amount in our database, asks the provider to refund, and records the result. The provider answers "accepted" at once, and the final result arrives later by webhook or by our own polling. We reserve first, and apply final results through one shared function, so two admins cannot over-refund and duplicate or out-of-order events do no harm.

## Terms

- **Provider**: the card provider. Only our server talks to it. The browser never does.
- **Captured**: a payment whose money has been taken. Only captured payments can be refunded.
- **Refund status**: `pending` (reserved or accepted, final result not known), `succeeded` or `failed`. Only pending refunds can change, and only once.
- **Cap**: for one payment, the sum of its pending and succeeded refunds must never exceed the captured amount. Failed refunds are not counted. Amounts are in cents.
- **Remaining amount**: captured amount minus the sum counted by the cap.
- **Idempotency key**: a UUID we generate once per refund and send with every create call. If the provider sees the same key again within 24 hours, it returns the original refund instead of making a new one. The brief does not say whether the 24 hours count from the first call or the latest one. We count from the refund's `created_at`, which is earlier than the first call, so our window is never longer than the real one.
- **Row lock** (`SELECT ... FOR UPDATE`): makes other transactions that lock the same row wait until this transaction ends.
- **Webhook**: an HTTP POST from the provider to our endpoint, carrying `refund.succeeded` or `refund.failed`. It can arrive days later, more than once, or out of order. It is signed with a shared secret.
- **Poller**: our scheduled job that asks the provider directly about pending refunds. It is the backstop for missing webhooks.
- **Outbox**: a table of emails still to send. A row is created in the same transaction that marks a refund succeeded, so the email is never lost or sent early.
- **Order refund label**: not stored. It is computed each time the order is read, from the succeeded refunds of its payment. Sum equal to the captured amount means "Refunded". Sum above 0 and below the captured amount means "Partially refunded". Otherwise there is no label.
- **Audit entry**: a row in `refund_audit` saying who did what and when. One is written for every refund request and every status change.

## Rules that apply to every step

- Only admins with refund permission can refund. The server checks this each time. Hiding the button is not enough.
- Every refund has a reason from a fixed list (duplicate, fraudulent, customer request, other) and may have a free-text note.
- The create call has a 10-second timeout. On a timeout or 5xx, retry up to 3 times with the same key (4 attempts in total). A 4xx means the provider rejected the refund: mark it failed, do not retry, and show the admin the provider's message.
- No refund may stay pending for more than 24 hours without the poller checking its status with the provider. Webhooks alone are not enough.
- The customer is emailed only after the refund has succeeded, and only once.

## Data model (new, stored in our database)

The existing `payments` table is unchanged. It already stores the provider's charge id, the captured amount and a status. There is no refund table yet.

- `refunds`
  - Columns: `id`, `payment_id`, `amount_cents`, `reason` (enum: duplicate, fraudulent, customer_request, other), `note`, `status` (`pending` | `succeeded` | `failed`), `idempotency_key`, `client_request_id`, `provider_refund_id`, `provider_message`, `requested_by`, `created_at`, `submitted_at`, `last_status_check_at`, `resolved_at`, `customer_emailed_at`.
  - Constraints: `idempotency_key` is unique and generated by our server when the row is created. `client_request_id` is unique. `amount_cents > 0`.
- `refund_audit`: append-only, with `id`, `refund_id`, `actor` (admin id, `system:webhook` or `system:poller`), `action`, `from_status`, `to_status`, `detail`, `at`. Application code can only insert into this table.
- `webhook_events`: `provider_event_id` (unique), `type`, `received_at`, `processed_at` (null until the event has been fully applied).
- `outbox`: `id`, `kind` (`refund_email`), `refund_id` (unique per kind), `claimed_at`, `sent_at`.

## Checklist

Steps 1 to 6 run when the admin submits. Steps 7 to 11 run later, in parallel.

- [ ] **1. Admin opens the payment page**
  - **Starts when:** an admin opens a payment in the internal admin page.
  - **Data moves:**
    - The server checks the admin's session and refund permission, then loads the payment and its refunds.
    - It returns the captured amount, the sum of pending and succeeded refunds, and the remaining amount.
    - It also returns each refund's status, reason, the provider message for any failed refund, and the order refund label.
  - **State stored:** nothing is written.
  - **On failure:**
    - If the admin lacks permission, return 403 and hide the refund button.
    - If the payment is not captured, show the page without refund controls.
    - The remaining amount shown here is only a hint. Step 3 re-checks it.

- [ ] **2. Admin submits the refund form**
  - **Starts when:** the admin enters an amount in cents (a "full" button fills in the remaining amount), picks a reason, optionally adds a note, and clicks submit.
  - **Data moves:** the browser sends `payment_id`, `amount_cents`, `reason`, `note` and a `client_request_id` (a random id made when the form loaded) to our server.
  - **State stored:** nothing yet.
  - **On failure:**
    - Re-check refund permission on the server.
    - Reject an amount that is not a positive integer, an unknown reason, or a note over the length limit, with a 400 and a field message.
    - Reusing a `client_request_id` returns the existing refund and its current state (pending, succeeded, or failed with the provider's message). It does not call the provider again and creates nothing. This protects against double-clicks and browser retries. Step 3 repeats this check under the lock.

- [ ] **3. Reserve the amount in a database transaction (concurrency guard)**
  - **Starts when:** the request passes step 2.
  - **Data moves:** in a single transaction, the server:
    1. Takes the row lock on the payment (`SELECT ... FROM payments WHERE id = ? FOR UPDATE`). This serializes all refund creation for one payment, so two admins refunding at once queue up. It also reads the charge id.
    2. Looks for a refund with this `client_request_id`. If one exists, it ends the transaction and returns that refund as in step 2. This is how two identical requests arriving together are handled: the second waits at the lock, then finds the first one's row and creates nothing.
    3. Confirms the payment status is `captured`.
    4. Sums `amount_cents` over this payment's pending and succeeded refunds.
    5. Requires `sum + requested <= captured_amount`.
    6. Inserts the refund row with `status=pending`, a fresh `idempotency_key`, the reason, the note and `requested_by`.
    7. Inserts an audit row (`requested`, null to pending, actor = admin).
    8. Commits.
  - **State stored:** the `refunds` row and the audit row, committed together. The pending row counts toward the cap immediately, before the provider is called.
  - **On failure:**
    - If the payment is not captured or the amount exceeds the remaining amount, roll back and return 409 with the current remaining amount. The admin page shows it, the admin lowers the amount, and the form gets a new `client_request_id` for the next submit. No refund row exists, so nothing is audited as a refund. Log the rejected attempt separately.
    - If the transaction fails, nothing is committed and the admin can retry.
    - If the app crashes after the commit but before step 4 starts, the pending row has no provider id. Step 8 picks it up within about 20 minutes and sends it.
    - Hold the lock only for this short transaction. Never hold it during the provider call.

- [ ] **4. Call the provider's create-refund API (server only)**
  - **Starts when:** step 3 commits. The call runs inline, in the same web request. The admin sees a "Submitting refund" spinner until it finishes. The worst case is about 45 seconds (4 attempts of 10 seconds plus backoff).
  - **Data moves:** the server sends the charge id (read from the payment row), `amount_cents` and the stored `idempotency_key` in the provider's idempotency header. Every attempt on this refund uses the same key.
  - **State stored:**
    - Set `submitted_at` when the first attempt starts.
    - Audit each attempt result (`provider_call_attempt`, with the attempt number and outcome).
  - **On failure:**
    - **Timeout or 5xx:** retry after a short backoff, up to the limit in the rules above. A timed-out call may have succeeded on the provider's side, and the key makes the repeat safe: the provider returns the original refund.
    - **Retries exhausted:** do not mark the refund failed, because the real outcome is unknown. Leave it `pending`, tell the admin "submitted, outcome unconfirmed", and let step 8 resolve it.
    - **4xx:** go to step 6. Do not retry.

- [ ] **5. Handle the provider's "accepted" response**
  - **Starts when:** the provider returns 2xx. This includes a repeated key returning the original refund. On the first call or a retry in step 4, this runs in the same web request, before the admin gets a response. The admin then sees "Refund pending".
  - **Data moves:** the provider's refund id and its initial status come back.
  - **State stored:**
    - Save `provider_refund_id` on the refund row, only if it is still null. Saving the same id twice is harmless, which matters when two sends overlap (see step 8).
    - Keep `status=pending`. "Accepted" is not success.
    - Audit `accepted_by_provider`.
  - **On failure:**
    - If saving `provider_refund_id` fails after the provider accepted, the refund stays pending without an id. Step 8 re-sends with the same key and gets the same refund back, so no duplicate is created, as long as this happens within 24 hours.
    - Refunds can take days to settle, so pending is the normal state. The admin sees the final state when the webhook or the poll reports it.
    - If the provider's immediate response already says a final status, do not act on it here. Final results for accepted refunds come only from step 7 or step 8 and are applied by step 9, so there is one path for them.

- [ ] **6. Handle a provider rejection (4xx)**
  - **Starts when:** the provider returns 4xx to a create call, in step 4 (same request) or step 8 (re-send). This is a direct rejection, separate from the later `refund.failed` webhook that step 9 handles.
  - **Data moves:** the provider's error message goes back to the admin. In step 4 it is the response to the same web request. In step 8 the admin sees it on the page later.
  - **State stored:** in one transaction, lock the refund row and, if it is still `pending`, set `status=failed`, store `provider_message` and `resolved_at`, and write an audit row (`rejected_by_provider`, pending to failed). A failed refund drops out of the cap sum, so the amount is available again.
  - **On failure:**
    - If this transaction fails, the refund stays pending and step 8 will find the same rejection when it re-sends with the same key.
    - Do not send email.

- [ ] **7. Receive the provider's webhook (`refund.succeeded` or `refund.failed`)**
  - **Starts when:** the provider POSTs to our webhook endpoint, possibly days later, possibly more than once or out of order.
  - **Data moves:**
    - Verify the signature against the raw request body with the shared secret before parsing. Reject invalid or stale signatures with 400.
    - Insert `provider_event_id` into `webhook_events` with `processed_at` null. If the row already exists and `processed_at` is set, return 200 and do nothing. If it exists with `processed_at` null (an earlier attempt did not finish), process it again.
    - Look up the refund by `provider_refund_id`.
    - Pass the new status and, for `refund.failed`, the provider's failure message to step 9.
  - **State stored:** the `webhook_events` row. The refund itself changes in step 9, which then sets `processed_at`.
  - **On failure:**
    - If the refund is not found, for example because the webhook arrived before step 5 saved the id, leave `processed_at` null and return a non-2xx status so the provider redelivers. The redelivery is processed because `processed_at` is still null. Step 8 will also resolve it.
    - If processing throws, return 5xx so the provider retries. Do not set `processed_at`.
    - Return 200 only after step 9 commits or the event is confirmed a duplicate.

- [ ] **8. Poll the provider for pending refunds (webhook backstop and recovery)**
  - **Starts when:** a scheduled job runs every 15 minutes.
  - **Data moves:**
    - **Refunds with a `provider_refund_id`:** it selects pending ones whose `last_status_check_at` is null and `created_at` is more than 1 hour ago, or whose `last_status_check_at` is more than 12 hours ago. This guarantees a direct check at least every 12 hours, well inside the 24-hour limit. It calls the provider's get-refund endpoint. A final result goes to step 9 as the new status plus, for a failed refund, the provider's message.
    - **Refunds with no `provider_refund_id`:** it selects pending ones created more than 5 minutes ago (so a request still in step 4 is left alone) and less than 24 hours ago. It re-sends the create call with the same key, using the step 4 retry rules.
    - Two sends for one refund can overlap, for example a request that outlives the 5 minutes, or a send racing the original after a crash. This is harmless: the same key makes the provider return the same refund, and step 5 saves the same id.
  - **State stored:**
    - Update `last_status_check_at` on every check.
    - A final status from the provider goes through step 9.
    - A pending status changes nothing except the timestamp and an audit row `status_checked`.
    - A 2xx on a re-send is handled by step 5, and a 4xx by step 6.
  - **On failure:**
    - If a provider error occurs, leave the refund pending and try again on the next run.
    - Alert if any refund has been pending for more than 18 hours without a successful check, or if the job has not run recently.
    - A refund with no provider id older than 24 hours cannot be safely re-sent, because the idempotency window has expired. Flag it for manual review (see open questions). It stays pending and keeps counting toward the cap.

- [ ] **9. Apply the final status (one shared function for webhook and poller)**
  - **Starts when:** step 7 or step 8 reports `succeeded` or `failed` for a refund, with the provider's message when it failed.
  - **Data moves:** inside one transaction:
    1. Lock the refund row (`FOR UPDATE`).
    2. If the status is not `pending`, do nothing except audit `duplicate_or_conflicting_event`. This makes duplicates harmless and stops a late event from reversing a final state. A conflicting result (succeeded after failed, or the reverse) also raises an alert.
    3. Otherwise set the new status and `resolved_at`. For `failed`, also store the provider's message in `provider_message`.
    4. Write an audit row with the old and new status. The actor is `system:webhook` or `system:poller`.
    5. On `succeeded`, insert the `outbox` row (`refund_email`, unique per refund).
    6. Commit, then set `processed_at` on the `webhook_events` row if the trigger was a webhook.
  - **State stored:** the refund status, audit row and outbox row, all committed together. The order label needs no write, because it is computed when read.
  - **On failure:**
    - If the transaction rolls back, nothing changes. The webhook returns 5xx, or the poller retries next run.
    - A `failed` result frees the amount, because failed refunds do not count toward the cap.

- [ ] **10. Email the customer, once, after success**
  - **Starts when:** a background worker in our app, checking once a minute, finds an `outbox` row with `sent_at` null. Such a row only exists after a refund has succeeded.
  - **Data moves:**
    - The worker claims the row with `UPDATE ... SET claimed_at = now() WHERE sent_at IS NULL AND (claimed_at IS NULL OR claimed_at < now() - interval '15 minutes')`. The second condition lets a worker take over a claim left by a crashed worker.
    - It re-checks that the refund status is `succeeded`, then sends the email with the amount and reason. Use the refund id as the mail provider's idempotency key if it supports one.
  - **State stored:** set `outbox.sent_at` and `refunds.customer_emailed_at`, and write audit `customer_emailed`.
  - **On failure:**
    - If sending fails, the same worker sets `claimed_at` back to null and retries with backoff. The refund state is unaffected.
    - If the worker crashes, nobody releases the claim. It becomes claimable again after 15 minutes.
    - A crash between sending and recording could cause a duplicate. The unique outbox row and the mail idempotency key keep this to a rare edge case.
    - Never email for pending or failed refunds.

- [ ] **11. Record the final outcome and show it to admins**
  - **Starts when:** the refund reaches `succeeded` or `failed` in step 6 or step 9.
  - **Data moves:** the admin page reads the refund list from our database each time it loads. It does not refresh itself, so the admin reloads to see a new outcome. It shows each refund's status, amount, reason, note, who requested it and when, the provider message for failures, and the order refund label. The audit trail is available for each refund.
  - **State stored:** nothing new. The final state is in `refunds` and `refund_audit`.
  - **On failure:**
    - If the page cannot load, it shows an error and nothing is lost, because all state is in the database.
    - Support staff never need the provider dashboard. Any refund made there outside our system is not recorded (see open questions).

## Open questions

- "Retry up to 3 times" is read as 1 initial attempt plus 3 retries, 4 attempts in total.
- We assume the provider's webhook payload and its get-refund response include its refund id, the final status and, for a failure, a message.
- A refund that never gets a provider id and passes 24 hours cannot be safely re-sent. Decide whether the provider can list refunds by charge id for reconciliation, or whether this goes to manual review. Until then it stays pending and keeps counting toward the cap, which is the safe side.
- Refunds made directly in the provider dashboard before or after launch are not known to us. Decide whether a one-time import or a reconciliation job is needed, because they affect the cap.
- Choose the admin role name for "refund permission" and the length limit for the note.
- The exact column name of the charge id on `payments` is not known to this plan. Use the existing one.
- The email worker interval (1 minute) and stale-claim time (15 minutes) are our own choices, not from the brief. Adjust if needed.
- Whether the provider's 24-hour key window counts from the first call or the latest one is not stated. The plan counts from `created_at`, which is safe either way.
