# Plan: Refunds from the admin page

Steps are in the order they happen. Steps 1 to 6 run when the admin submits. Steps 7 to 11 run later and in parallel.

**Data model (new, stored in our database)**

- `refunds`
  - Columns: `id`, `payment_id`, `amount_cents`, `reason` (enum: duplicate, fraudulent, customer_request, other), `note`, `status` (`pending` | `succeeded` | `failed`), `idempotency_key`, `client_request_id`, `provider_refund_id`, `provider_message`, `requested_by`, `created_at`, `submitted_at`, `last_status_check_at`, `resolved_at`, `customer_emailed_at`.
  - Constraints:
    - `idempotency_key` is unique and is generated by our server when the row is created.
    - `client_request_id` is unique.
    - `amount_cents > 0`.
- `refund_audit`: append-only, with `id`, `refund_id`, `actor` (admin id, `system:webhook` or `system:poller`), `action`, `from_status`, `to_status`, `detail`, `at`. Application code can only insert into this table.
- `webhook_events`: `provider_event_id` (unique), `type`, `received_at`, `processed_at`.
- `outbox`: `id`, `kind` (`refund_email`), `refund_id` (unique per kind), `claimed_at`, `sent_at`.
- Existing `payments` is unchanged. The order's displayed refund status is recomputed from succeeded refunds (step 9).

## Checklist

- [ ] **1. Admin opens the payment page**
  - **Starts when:** an admin opens a payment in the internal admin page.
  - **Data moves:**
    - The server checks the admin's session and refund permission, then loads the payment and its refunds.
    - It returns the captured amount, the sum of pending and succeeded refunds, and the remaining refundable amount.
    - It also returns each refund's status, reason and the provider message for any failed refund.
  - **State stored:** nothing is written.
  - **On failure:**
    - If the admin lacks permission, return 403 and hide the refund button.
    - If the payment is not captured, show the page without refund controls.
    - The remaining amount shown here is only a hint. Step 3 re-checks it.

- [ ] **2. Admin submits the refund form**
  - **Starts when:** the admin enters an amount in cents (a "full" button fills in the remaining amount), picks a reason from the fixed list, optionally adds a note, and clicks submit.
  - **Data moves:**
    - The browser sends `payment_id`, `amount_cents`, `reason`, `note` and a `client_request_id` (a random id made when the form loaded) to our server.
    - The browser never contacts the provider.
  - **State stored:** nothing yet.
  - **On failure:**
    - Re-check refund permission on the server. The UI check is not enough.
    - Reject an amount that is not a positive integer, an unknown reason, or a note over the length limit, with a 400 and a field message.
    - Reusing a `client_request_id` returns the existing refund instead of creating a second one. This protects against double-clicks and browser retries.

- [ ] **3. Reserve the amount in a database transaction (concurrency guard)**
  - **Starts when:** the request passes step 2.
  - **Data moves:** in a single transaction, the server:
    1. Runs `SELECT ... FROM payments WHERE id = ? FOR UPDATE`. This row lock serializes all refund creation for one payment, so two admins refunding at once queue up.
    2. Confirms the payment status is `captured`.
    3. Computes `SUM(amount_cents)` over this payment's refunds where status is `pending` or `succeeded`. Failed refunds are excluded.
    4. Requires `sum + requested <= captured_amount`.
    5. Inserts the refund row with `status=pending`, a fresh `idempotency_key` (UUID), the reason, the note and `requested_by`.
    6. Inserts an audit row (`requested`, null to pending, actor = admin).
    7. Commits.
  - **State stored:** the `refunds` row and the audit row, committed atomically. The pending row counts toward the cap immediately, before the provider is called.
  - **On failure:**
    - If the payment is not captured or the amount exceeds the remaining balance, roll back and return 409 with the current remaining amount. No refund row exists, so nothing is audited as a refund. Log the rejected attempt separately.
    - If the transaction fails or the app crashes, nothing is committed and the admin can retry.
    - Hold the lock only for this short transaction. Never hold it during the provider call.

- [ ] **4. Call the provider's create-refund API (server only)**
  - **Starts when:** step 3 commits. The call runs right after, in the same request or on a worker.
  - **Data moves:**
    - The server sends the charge id, `amount_cents` and the stored `idempotency_key` in the provider's idempotency header.
    - The call has a 10-second timeout.
    - The same key is used for every attempt on this refund.
  - **State stored:**
    - Set `submitted_at` when the first attempt starts.
    - Audit each attempt result (`provider_call_attempt`, with the attempt number and outcome).
  - **On failure:**
    - **Timeout or 5xx:** retry up to 3 more times (4 attempts in total), with a short backoff, using the same key. A timed-out call may have succeeded on the provider's side, and the idempotency key makes the repeat safe. It returns the original refund.
    - **Retries exhausted:** do not mark the refund failed, because the real outcome is unknown. Leave it `pending`, tell the admin "submitted, outcome unconfirmed", and let step 5 and step 8 resolve it.
    - **4xx:** go to step 6. Do not retry.

- [ ] **5. Handle the provider's "accepted" response**
  - **Starts when:** the provider returns 2xx. This includes a repeated key returning the original refund.
  - **Data moves:** the provider's refund id and its initial status come back.
  - **State stored:**
    - Save `provider_refund_id` on the refund row.
    - Keep `status=pending`. "Accepted" is not success.
    - Audit `accepted_by_provider`.
  - **On failure:**
    - If saving `provider_refund_id` fails after the provider accepted, the refund stays pending without an id. Step 8 re-sends with the same key and gets the same refund back, so no duplicate is created, as long as this happens within 24 hours.
    - The admin sees "Refund pending".
    - If the provider's immediate response already says a final status, still do not act on it here. Wait for the webhook or poll, so there is one path to a final state (step 9).

- [ ] **6. Handle a provider rejection (4xx)**
  - **Starts when:** the provider returns 4xx in step 4.
  - **Data moves:** the provider's error message goes back to the admin.
  - **State stored:** in one transaction, set `status=failed`, store `provider_message` and `resolved_at`, and write an audit row (`rejected_by_provider`, pending to failed). A failed refund drops out of the pending and succeeded sum, so the amount is available again.
  - **On failure:**
    - If this transaction fails, the refund stays pending and step 8 will find the same rejection when it re-sends with the same key.
    - Do not send email and do not change the order status.

- [ ] **7. Receive the provider's webhook (`refund.succeeded` or `refund.failed`)**
  - **Starts when:** the provider sends an HTTP POST to our webhook endpoint, possibly days later. It may arrive more than once or out of order.
  - **Data moves:**
    - Verify the signature against the raw request body with the shared secret before parsing. Reject invalid or stale signatures with 400.
    - Insert `provider_event_id` into `webhook_events`. If it already exists and is processed, return 200 and do nothing.
    - Look up the refund by `provider_refund_id`.
  - **State stored:** the `webhook_events` row. The refund itself changes in step 9.
  - **On failure:**
    - If the refund is not found, for example because the webhook arrived before step 5 saved the id, return a non-2xx status so the provider redelivers. Step 8 will also resolve it.
    - If processing throws, return 5xx so the provider retries. Do not mark the event processed.
    - Return 200 only after step 9 commits or the event is confirmed a duplicate.

- [ ] **8. Poll the provider for pending refunds (webhook backstop)**
  - **Starts when:** a scheduled job runs every 15 minutes.
  - **Data moves:**
    - It selects pending refunds whose `last_status_check_at` is null and older than 1 hour, or older than 12 hours. This guarantees a direct check at least every 12 hours, well inside the 24-hour limit.
    - For refunds that have a `provider_refund_id`, it calls the provider's get-refund endpoint.
    - For refunds with no `provider_refund_id` and created less than 24 hours ago, it re-sends the create call with the same key (step 4 rules).
  - **State stored:**
    - Update `last_status_check_at` on every check.
    - A final status from the provider goes through step 9.
    - A pending status changes nothing except the timestamp and an audit row `status_checked`.
  - **On failure:**
    - If a provider error occurs, leave the refund pending and try again on the next run.
    - Alert if any refund has been pending for more than 18 hours without a successful check, or if the job has not run recently.
    - A refund with no provider id older than 24 hours cannot be safely re-sent, because the idempotency window has expired. Flag it for manual review (see Open questions). It stays pending and keeps counting toward the cap.

- [ ] **9. Apply the final status (one shared function for webhook and poller)**
  - **Starts when:** step 7 or step 8 reports `succeeded` or `failed` for a refund.
  - **Data moves:** inside one transaction:
    1. Lock the refund row (`FOR UPDATE`).
    2. If the status is not `pending`, do nothing except audit `duplicate_or_conflicting_event`. This makes duplicates harmless and stops a late event from reversing a final state. A conflicting result (succeeded after failed, or the reverse) also raises an alert.
    3. Otherwise set the new status and `resolved_at`.
    4. Write an audit row with the old and new status. The actor is `system:webhook` or `system:poller`.
    5. On `succeeded`, recompute the order's refund status from succeeded refunds only. If the sum equals the captured amount, the order shows "Refunded". If the sum is more than 0 and less than the captured amount, it shows "Partially refunded". Otherwise it is unchanged.
    6. On `succeeded`, insert the `outbox` row (`refund_email`, unique per refund).
    7. Commit, then mark the `webhook_events` row processed if the trigger was a webhook.
  - **State stored:** the refund status, audit row, order refund status and outbox row, all committed together.
  - **On failure:**
    - If the transaction rolls back, nothing changes and the webhook returns 5xx or the poller retries next run.
    - A `failed` result frees the amount, because failed refunds do not count toward the cap.
    - An out-of-order `failed` or `succeeded` arriving after the other is handled by step 2 above.

- [ ] **10. Email the customer, once, after success**
  - **Starts when:** a worker finds an `outbox` row with `sent_at` null, which only exists after a refund has succeeded.
  - **Data moves:**
    - The worker claims the row (`UPDATE ... SET claimed_at = now() WHERE sent_at IS NULL AND claimed_at IS NULL`), re-checks that the refund status is `succeeded`, and sends the email with the amount and reason. Use the refund id as the mail provider's idempotency key if it supports one.
  - **State stored:** set `outbox.sent_at` and `refunds.customer_emailed_at`, and write audit `customer_emailed`.
  - **On failure:**
    - If sending fails, release the claim and retry with backoff. The refund state is unaffected.
    - A crash between sending and recording could cause a duplicate. The unique outbox row and the mail idempotency key keep this to a rare edge case. Reclaim claims that are stale for more than a set time.
    - Never email for pending or failed refunds.

- [ ] **11. Record the final outcome and show it to admins**
  - **Starts when:** the refund reaches `succeeded` or `failed` in step 6 or step 9.
  - **Data moves:** the admin page now reads the refund list from our database. It shows each refund's status, amount, reason, note, who requested it and when, the provider message for failures, and the order's "Partially refunded" or "Refunded" label. The audit trail is available for each refund.
  - **State stored:** nothing new. The final state is in `refunds`, `refund_audit` and the order's refund status.
  - **On failure:**
    - If the page cannot load, it shows an error and nothing is lost, because all state is in the database.
    - Support staff never need the provider dashboard. Any refund made there outside our system is not recorded (see Open questions).

## Assumptions and open questions

- "Retry up to 3 times" is read as 1 initial attempt plus 3 retries, 4 attempts in total.
- We assume the provider's webhook payload includes its refund id, and that its get-refund endpoint returns the final status.
- A refund that never gets a provider id and passes 24 hours cannot be safely re-sent. Decide whether the provider can list refunds by charge id for reconciliation, or whether this goes to manual review. Until then it stays pending and keeps counting toward the cap, which is the safe side.
- Refunds made directly in the provider dashboard before or after launch are not known to us. Decide whether a one-time import or a reconciliation job is needed, because they affect the cap.
- Choose the admin role name for "refund permission" and the length limit for the note.
