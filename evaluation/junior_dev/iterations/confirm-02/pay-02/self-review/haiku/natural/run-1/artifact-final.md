# Plan: refunds from the admin page

## What this plan does

Today, support staff refund customers in the card provider's own dashboard, so our database never learns that a refund happened. This plan lets admins issue full or partial refunds from our internal admin page. Our server calls the provider's refund API and keeps its own record of every refund. The browser never talks to the provider.

## Terms used below

- **Captured amount:** the part of a payment that the provider has actually taken, in cents. All refunds on a payment together can never add up to more than this.
- **Provider:** the card payment company. Its API creates and looks up refunds. It also sends **webhooks**: signed HTTP messages it posts to our server when a refund's final result is known.
- **Idempotency key:** a unique ID we send with each create call. If the provider gets the same key again within 24 hours, it returns the original refund instead of making a second one. This is what makes retries safe.
- **Transaction:** a group of database writes that either all happen or none of them do.
- **Row lock (`SELECT ... FOR UPDATE`):** the database makes any other writer wait until the current transaction finishes with that row.
- **HTTP status codes:** 2xx means the request succeeded. 4xx means the other side rejected the request. 5xx means the other side failed. A **timeout** means no answer arrived within 10 seconds.
- **Job queue:** a durable list of background tasks. An entry survives a crash, so the work is not lost.
- **Sweeper:** a scheduled job that resumes refunds stuck in `queued`.
- **Reconciler:** a scheduled job that asks the provider for the current status of refunds in `pending`.
- **Email worker:** a background job that sends customer emails from the outbox table.
- **Reserved amount (per payment):** the sum of `amount_cents` over the payment's refunds in state `queued`, `pending`, `needs_review` or `succeeded`. `failed` refunds are not counted. Reserved amount is the figure checked against the captured amount.

## Shared definitions

**Refund states**

- `queued`: saved in our database, and its amount is reserved. The provider has not yet accepted it.
- `pending`: the provider accepted the create call and returned a provider refund id. The final result is not known yet.
- `succeeded` (final): the provider confirmed that the money moved.
- `failed` (final): the provider rejected the refund (a 4xx response), or later reported that it failed.
- `needs_review` (not final): we could not confirm the result with the provider within 23 hours. A person must resolve it. The amount stays reserved meanwhile.

**Allowed transitions**

- `queued -> pending`, `queued -> succeeded`, `queued -> failed`
- `pending -> succeeded`, `pending -> failed`
- `queued -> needs_review`, `pending -> needs_review`
- `needs_review -> succeeded`, `needs_review -> failed` (set by an admin after checking, or by a late webhook)

`succeeded` and `failed` never change again. Every status change goes through one shared function (step 11), and every change is written to the audit log.

**Why 23 hours?** The provider remembers an idempotency key for 24 hours. We stop resubmitting at 23 hours, which leaves a one-hour margin. Past that point we can no longer be sure a retry would return the original refund, so we ask a person instead.

**Tables**

- `payments` (existing): charge id, captured amount in cents, and status. The order status is not stored. It is worked out from the refunds.
- `refunds`: `id`, `payment_id`, `amount_cents`, `reason` (enum), `note`, `status`, `provider_refund_id` (nullable), `idempotency_key` (unique, a UUID generated by our server), `request_token` (unique, created by the form), `attempts`, `last_attempt_at`, `last_error`, `failure_message` (the provider's text, shown to admins), `last_provider_check_at`, `created_by`, `created_at`, `updated_at`.
- `refund_webhook_events`: `provider_event_id` (unique), `type`, `refund_provider_id`, `raw_payload`, `received_at`, `processed_at`.
- `audit_log` (append-only: rows are added but never changed or deleted): `actor` (an admin id, `system:submitter`, `system:webhook` or `system:reconciler`), `action`, `payment_id`, `refund_id`, `from_status`, `to_status`, `details` (JSON), `created_at`.
- `email_outbox`: `refund_id`, `kind`, `status`, `attempts`, `sent_at`. Unique on (`refund_id`, `kind`), so each refund gets at most one email of each kind.

## Checklist: steps in order

- [ ] **1. Admin opens the payment page**
    - Starts: an admin opens a payment in the internal admin page.
    - Data shown: payment id, captured amount, payment status, the refund list, and the reserved total. The server computes all of these. The order status comes from succeeded refunds only.
    - Stored: nothing is written. The page only reads from `payments` and `refunds`.
    - On failure: if the admin lacks refund permission, the Refund button is hidden, and every refund endpoint still returns 403. If the payment is not `captured`, the button is disabled and the page shows why. If the read fails, the admin sees an error page and nothing is written.

- [ ] **2. Admin fills in the refund form**
    - Starts: the admin clicks Refund.
    - Data entered: the amount in whole cents, a reason (duplicate, fraudulent, customer request, or other), an optional note, and a `request_token` that the page creates when it is drawn.
    - Stored: only in the browser until submitted. On submit, the browser sends the form to our server. The browser never calls the provider.
    - On failure: checks in the browser are only a convenience. The server checks everything again in step 3.

- [ ] **3. Server checks the request**
    - Starts: the browser sends `POST /payments/{id}/refunds`.
    - Checks: the admin's session identity, their refund permission, the payment status, the amount, the reason, the note length (capped), and that `request_token` is present.
    - Stored: a rejected request writes an `audit_log` row (`refund.request_rejected`, with the reason). A valid request goes on to step 4.
    - On failure: 403 if the admin lacks permission. 422 for invalid input, a missing token, or a payment that is not captured. No refund row is created.

- [ ] **4. Reserve the amount in one database transaction**
    - Starts: step 3 passed.
    - Data: payment id, amount, reason, note, admin id, and `request_token`.
    - Inside one transaction, in this order:
        1. Lock the payment row with `SELECT ... FROM payments WHERE id = ? FOR UPDATE`. If a second admin refunds the same payment at the same moment, that request waits here until the first one finishes.
        2. Check `request_token`. If a refund already has this token, return that refund and insert nothing. This check runs before the amount check, so a double-click does not get a 409 caused by its own first request.
        3. Add up the reserved amount. If reserved + requested is more than captured, roll back and return 409 with the amount that can still be refunded.
        4. Insert the `refunds` row with status `queued`, a new server-generated `idempotency_key`, and `attempts = 0`. The key is saved before any provider call, so every retry reuses the same key.
        5. Insert the audit row `refund.requested`, including the key.
        6. Commit.
    - Stored: `refunds` and `audit_log`, written together in one transaction.
    - On failure: any database error rolls back, so nothing is reserved, and the admin sees a "try again" message. A deadlock or serialization error (two transactions blocking each other) is retried once. An audit row for a rejected request is written in its own transaction after the rollback, so the rollback cannot erase it.

- [ ] **5. Hand the refund to the submission job**
    - Starts: the step 4 transaction committed.
    - Data: the refund id only.
    - Stored: an entry in the job queue.
    - Response: the admin gets 202 with the refund id and status `queued`. The page shows "Submitting" and checks again later (step 8).
    - On failure: if adding the job to the queue fails, the sweeper (step 9) finds the row, because `last_attempt_at` is still empty. The HTTP request never waits for the provider. If it did, the admin would sit through the retry schedule, which can take about 47 seconds.

- [ ] **6. Submission job calls the provider's create-refund**
    - Starts: the job runs for a refund id.
    - Data sent to the provider: the charge id from `payments`, `amount_cents`, the `idempotency_key` header, and metadata with our refund id and reason. The free-text note is not sent.
    - Timeout: 10 seconds per attempt.
    - Stored: before each attempt, increment `attempts` and set `last_attempt_at`. If we crash during the call, the database still shows that an attempt started.
    - On failure: handled in step 7.

- [ ] **7. Interpret the provider's response**
    - Starts: the create call returns, or fails.
    - **2xx (accepted):** store `provider_refund_id` and set `last_provider_check_at`. Then apply `queued -> pending` through step 11. If the row is no longer `queued` (a webhook already moved it), the pending change is ignored and logged, but the id is still stored. Write `refund.pending` to the audit log.
    - **4xx (rejected):** apply `queued -> failed` through step 11 and store the provider's message in `failure_message`. Write `refund.failed` to the audit log. Do not retry. The admin sees the message (step 8). The amount no longer counts toward the reserved total.
    - **Timeout, 5xx or network error:** retry with the same `idempotency_key`. Wait 1 second, then 2, then 4 seconds. That makes at most 4 attempts in total, and each one has the 10-second timeout. If an earlier attempt did reach the provider, the provider returns the original refund instead of creating a second one.
    - **All attempts failed:** leave the row `queued`, store `last_error`, and do not mark it failed. The provider may already have created the refund. The sweeper (step 9) takes over.
    - On failure: the state is always saved in the database, so a crash in any branch is recovered by step 9.

- [ ] **8. Admin sees the result**
    - Starts: the admin's page checks again on a timer, or the admin reloads it.
    - Data shown: refund status, `failure_message` for failed refunds, and the order status.
    - Stored: nothing is written.
    - On failure: closing the page loses nothing, because the state is in the database.

- [ ] **9. Sweeper resumes stuck `queued` refunds**
    - Starts: a scheduled job runs every 5 minutes. It selects `queued` rows where `last_attempt_at` is empty or more than 5 minutes ago, and `created_at` is less than 23 hours ago.
    - Action: resubmit through step 6 with the stored key. Every resubmit happens within 23 hours of creation, so the key is always inside the provider's 24-hour window.
    - At 23 hours: the sweeper makes one final create call with the same key. If that call gives a clear answer, the result goes through step 7. If it does not, apply `queued -> needs_review` through step 11, write an audit row, and alert admins. The amount stays reserved until a person resolves it.
    - Resolving `needs_review`: an admin with refund permission can re-check the refund with the provider (step 12), or set it to `succeeded` or `failed`. Each action is audited and goes through step 11. An admin should re-check before marking a refund failed, because the provider may have created it.
    - On failure: if the sweeper stops running, alert on the age of the oldest `queued` row.

- [ ] **10. Provider webhook arrives (`refund.succeeded` or `refund.failed`)**
    - Starts: the provider posts to our webhook endpoint. The browser is not involved.
    - Verify: check the signature over the raw request body, using the webhook secret. Reject an invalid signature with 401 and write nothing. Reject a timestamp that is more than 5 minutes away from our clock, in either direction, to limit replay.
    - Dedupe: insert the `provider_event_id` into `refund_webhook_events`. The unique constraint means a repeated event returns 200 and does nothing else.
    - Match: find the refund by `provider_refund_id`. If none matches yet (the webhook arrived before step 7 saved the id), keep the event with `processed_at` empty. The reconciler (step 12) processes it later.
    - Apply: send the change through step 11. Set `processed_at` only after step 11 has applied it.
    - Respond: return 2xx only after the event row is committed. Return 500 if the database write fails, so the provider retries.
    - On failure: the provider's retries plus the dedupe key make this safe.

- [ ] **11. Apply the status change (one shared function)**
    - Starts: called from step 7 (create response), step 10 (webhook), step 9 (sweeper), step 12 (direct check), or an admin action.
    - Rules:
        - Apply the change as a conditional update, `UPDATE ... WHERE status = <expected status>`. The row changes only if it is still in the expected state, so only allowed transitions happen. If no row matches, the change is ignored and logged.
        - A duplicate or out-of-order event makes no change and is logged. For example, the create response arrives after a webhook has already set `succeeded`.
        - A conflicting final event, such as `failed` arriving after `succeeded`, does not change the state. Instead, it queues a direct check (step 12) and raises an alert.
    - In one transaction:
        1. Update the refund's status, timestamps and `provider_refund_id`.
        2. Write an audit row with the actor, from-status, to-status, and the provider event id or check id.
        3. If the new status is `succeeded`, insert an `email_outbox` row with `kind = refund_succeeded`. The unique key on (`refund_id`, `kind`) means exactly one email is ever queued.
    - Order status: worked out from succeeded refunds only. It is "Partially refunded" when the succeeded total is above 0 and below the captured amount. It is "Refunded" when the succeeded total equals the captured amount.
    - On failure: the transaction rolls back and nothing changes. The webhook returns 500, or the reconciler retries on its next run.

- [ ] **12. Direct provider status check (no pending refund goes 24 hours unchecked)**
    - Starts: the reconciler runs every 15 minutes. It selects `pending` refunds where `last_provider_check_at` is empty or more than 4 hours old. It also processes unmatched webhook events from step 10 and any direct checks queued by step 11.
    - Action: call the provider's retrieve-refund endpoint with the provider refund id. Use the 10-second timeout, with up to 3 retries on a timeout or 5xx. Send the result through step 11, then set `last_provider_check_at`.
    - Guarantee: each pending refund is checked at least every 4 hours, so none goes 24 hours without a direct check.
    - Escalation: a provider 404, or a conflict that cannot be resolved, moves the refund to `needs_review`. It is never automatically failed.
    - On failure: if the provider is unavailable, leave the refund `pending` and try again on the next run. Alert if a pending refund is older than 20 hours.

- [ ] **13. Customer email after success**
    - Starts: the email worker polls `email_outbox` for `pending` rows. Rows are created only in step 11, when a refund moves to `succeeded`.
    - Data: the customer's address from the payment's customer record, the refund amount, and the refund id. The internal reason and note are not included.
    - Idempotency: the outbox row id is passed to the email provider as its idempotency key, so retries never send the same email twice.
    - Stored: set `sent_at` on the outbox row and write `refund.customer_emailed` to the audit log.
    - On failure: retry with backoff. After a set number of attempts (to be decided), mark the row `failed` and alert. The refund status does not change. No email is ever sent for a refund in `pending`, `failed` or `needs_review`.

- [ ] **14. Final outcome recorded**
    - Starts: the refund reaches `succeeded` or `failed`, or `needs_review`. A `needs_review` refund ends only when a person resolves it.
    - Result:
        - The refund row has its final status and provider id.
        - The payment's order status is "Partially refunded", "Refunded", or unchanged (after a failure).
        - The audit log holds the full history: the request, each status change, and the email send.
    - Verification: an invariant check confirms that, for each payment, the reserved amount never exceeds the captured amount. Concurrency tests run two simultaneous requests against one payment and expect exactly one to succeed.
    - This is the end of the flow.

## Open decisions for the team

- **429 and 408 responses:** both are 4xx, so the rule above would mark them failed without retrying. Retrying them is usually correct. Confirm whether they should be treated as retryable.
- **Provider API assumptions:** this plan assumes the create call returns the refund id, that a retrieve-by-id endpoint exists, and that the webhook signs the raw body together with a timestamp. Confirm each against the provider's documentation.
- **`needs_review` owner:** who resolves these refunds, and what is the alert channel?
- **Note privacy:** the plan keeps the admin's free-text note off the provider. Confirm this is acceptable.
- **Email address source:** confirm the customer email comes from the payment's customer record and not from the card provider.
- **Email retry limit and unmatched-event alert:** choose the number of email attempts (step 13), and decide how long an unmatched webhook event may wait before someone is alerted (step 10).
