# Plan: refunds from the admin page

## Data this plan adds (referenced by the steps)

- **`refunds` table**
  - Columns: `id`, `payment_id`, `amount_cents` (>0), `reason` (enum: duplicate, fraudulent, customer_request, other), `note` (nullable), `status` (`pending` | `succeeded` | `failed`), `idempotency_key` (UUID, unique, generated by us), `request_token` (unique), `provider_refund_id` (nullable, unique), `provider_error` (nullable), `requested_by`, `created_at`, `submitted_at`, `last_checked_at`, `resolved_at`.
  - `pending` with a null `provider_refund_id` means the provider has not yet acknowledged the refund. It is not a separate status.
  - Terminal states (`succeeded`, `failed`) never change again.
- **`refund_webhook_events`**: `provider_event_id` (unique), type, payload, `received_at`, `processed_at`.
- **`refund_audit_log`**: append-only. Columns: `refund_id`, `actor` (admin id, `system:webhook`, or `system:sweeper`), `action`, `from_status`, `to_status`, `detail`, `at`. Rows are never updated or deleted.
- **`email_outbox`**: `refund_id` (unique), `status`, `sent_at`.
- **Existing `payments` / order**: the payment's charge id, captured amount and status are read. The order's refund display status is derived from succeeded refunds.

## Checklist

### A. Admin opens the payment

- [ ] **1. Admin opens the payment detail page.**
  - **Starts it:** the admin navigates to the payment in the admin page.
  - **Data moves:** the server loads the payment and its refunds, and computes `refundable = captured_amount − sum(amount_cents of refunds where status in pending, succeeded)`.
  - **State stored:** none. The page shows a one-time `request_token` (UUID) in the refund form.
  - **Server checks:**
    - The admin has refund permission. Without it, the refund form is not rendered and the server returns 403 on direct access.
    - The payment status is `captured`. Otherwise the form is hidden.
  - **On failure:** a permission failure returns 403. A payment that is not captured shows "not refundable". A load error shows an error page and changes nothing.

### B. Admin submits a refund

- [ ] **2. Admin submits the form.**
  - **Starts it:** the admin clicks "Refund".
  - **Data moves:** browser to our server only: `payment_id`, `amount_cents` (full refund = the current refundable amount), `reason`, optional `note`, `request_token`. The browser never contacts the provider.
  - **State stored:** none yet.
  - **On failure:** if the network fails, the admin can resubmit. The same `request_token` makes the resubmit safe (step 3).

- [ ] **3. Server validates the request and reserves the amount in one database transaction.**
  - **Starts it:** step 2 arrives at the server.
  - **Checks (server side, never trusting the page):**
    1. The session is valid and the admin has refund permission.
    2. `reason` is in the fixed list. `note` is length-limited.
    3. `amount_cents` is an integer greater than 0.
    4. If a refund with this `request_token` already exists, return that refund and do nothing else. This stops double clicks and retried requests from creating duplicate refunds.
  - **Concurrency control:**
    1. Begin a transaction.
    2. Run `SELECT ... FROM payments WHERE id = ? FOR UPDATE`. This takes a row lock, so two admins refunding the same payment are processed one after the other.
    3. Re-check that the payment status is `captured`.
    4. Compute `sum(amount_cents)` over this payment's refunds where status is `pending` or `succeeded`. Failed refunds are excluded.
    5. If `sum + amount_cents > captured_amount`, roll back and return "exceeds refundable amount (X cents left)".
    6. Otherwise insert the refund with `status = pending`, `provider_refund_id = null`, a freshly generated `idempotency_key`, the `request_token` and `requested_by`.
    7. Insert an audit row (`requested`, actor = admin, amount, reason) in the same transaction.
    8. Commit and release the lock.
  - **Data moves:** the validated request goes into `refunds` and `refund_audit_log`.
  - **State stored:** the `refunds` row and the audit row. The row is committed before any provider call. The reservation counts toward the cap from this moment, and the `idempotency_key` is saved so every later retry reuses it.
  - **On failure:** any error rolls back everything, so nothing is reserved and the admin sees the error. If the transaction fails after the lock, the lock is released with it. If the second admin's request arrives while the first holds the lock, it waits, then sees the updated sum and may be rejected with the "exceeds refundable amount" message.

### C. Call the provider

- [ ] **4. Server calls the provider's create-refund API.**
  - **Starts it:** the commit in step 3. The call runs right away in the same request, and the sweeper (step 11) picks it up if this process dies.
  - **Data moves:** our server to the provider only: charge id (from the payment), `amount_cents`, `reason`, our refund id as metadata, and the stored `idempotency_key`. The reason is mapped to the provider's reason values where the provider has them. The call has a 10-second timeout.
  - **Outcomes:**
    - **2xx (accepted):** go to step 5.
    - **4xx:** the provider rejected the refund. Do not retry. In one transaction, set `status = failed` only if the row is still `pending`, store the provider's message in `provider_error`, set `resolved_at`, and write an audit row (`pending → failed`, provider message). Return the provider's message to the admin. The failed refund no longer counts toward the cap, so the amount is available again.
    - **Timeout or 5xx:** go to step 4a.
  - **State stored:** `submitted_at` is set before the first attempt, and `last_checked_at` is set on every attempt.
  - **On failure:** a crash before the call leaves a `pending` row with no `provider_refund_id`. The sweeper handles it (step 11).

- [ ] **4a. Retry on timeout or 5xx.**
  - **Starts it:** a timeout or a 5xx response in step 4.
  - **Data moves:** the same request with the same `idempotency_key`. Retry up to 3 times, with short backoff between attempts. Each attempt uses a 10-second timeout.
  - **Why it is safe:** a timed-out call may have created the refund. Repeating it with the same key within 24 hours returns the original refund instead of a second one.
  - **State stored:** an audit row for each failed attempt (`attempt n of 4 failed: timeout/5xx`). The refund stays `pending`.
  - **On success:** go to step 5. A 4xx on any retry goes to the 4xx branch in step 4.
  - **On failure after the 3rd retry:** do not mark the refund failed, because the provider may have created it. Leave it `pending` with `provider_refund_id = null`. Show the admin "submitted, awaiting provider confirmation". The sweeper keeps trying with the same key (step 11).

- [ ] **5. Record the provider's acceptance.**
  - **Starts it:** a 2xx response from step 4 or 4a.
  - **Data moves:** the provider's refund id and status come back to our server.
  - **State stored:** in one transaction, set `provider_refund_id`, set `last_checked_at`, and add an audit row (`accepted by provider`). The status stays `pending`, because "accepted" is not the final result.
  - **If the provider already reports a final status** in this response, apply it through the shared transition (step 8) instead.
  - **On failure:** if this write fails, the refund stays `pending` with no `provider_refund_id`. The provider has it, so the sweeper or the webhook will fill in the id later (steps 7 and 11). The admin sees "submitted, awaiting provider confirmation".

- [ ] **6. Show the admin the result so far.**
  - **Starts it:** the end of steps 4 to 5.
  - **Data moves:** the server returns the refund row: pending, failed with the provider's message, or an error.
  - **State stored:** none.
  - **On failure:** if the page fails to render, the refund still exists and appears in the payment's refund list.
  - **Order status:** it does not change here. "Partially refunded" and "Refunded" depend on succeeded refunds only.

### D. The final result arrives (webhook)

- [ ] **7. Receive the provider's webhook.**
  - **Starts it:** the provider posts `refund.succeeded` or `refund.failed` to our webhook endpoint, possibly minutes or days later, possibly more than once, possibly out of order.
  - **Data moves:** provider to server: event id, type, provider refund id, status, and our refund id (from the metadata).
  - **Steps:**
    1. Verify the signature against the raw request body with the shared secret. If it is invalid, return 400 and store nothing.
    2. Insert the event into `refund_webhook_events`. The unique `provider_event_id` stops duplicate processing: if the insert conflicts, return 200 and stop.
    3. Find the refund by `provider_refund_id`, or by our refund id from the metadata. This covers events that arrive before step 5 stored the id.
    4. If no refund is found, return a non-2xx status so the provider redelivers later. Do not drop the event.
    5. Call the shared transition (step 8).
    6. Set `processed_at` and return 200.
  - **State stored:** the event row, plus whatever step 8 stores.
  - **On failure:** if processing fails, return 5xx so the provider redelivers. Because of the unique event id, a redelivery is safe.

- [ ] **8. Apply the status change with one shared transition function.**
  - **Starts it:** step 7 (webhook), step 5 (immediate final status), or step 11 (sweeper). All three call this same function.
  - **Data moves:** the new status from the provider (`succeeded` or `failed`), the source, and any provider message.
  - **Rules (in one transaction):**
    1. Run a conditional update: `UPDATE refunds SET status = ?, resolved_at = now() WHERE id = ? AND status = 'pending'`. If zero rows change, the refund is already final. Do nothing else, except that an event that contradicts a final state (for example `failed` after `succeeded`) gets an audit row (`conflicting event ignored`) and an alert. This makes duplicate and out-of-order events harmless.
    2. If the status is `failed`, store the provider's message and write an audit row (`pending → failed`, actor = `system:webhook`, `system:sweeper`, etc.). The amount is released automatically, because failed refunds are not counted.
    3. If the status is `succeeded`, write an audit row (`pending → succeeded`) and go to step 9 inside the same transaction.
    4. Fill in `provider_refund_id` if it was missing.
  - **State stored:** the refund status, the audit row, and (for success) the order status and the email outbox row.
  - **On failure:** the transaction rolls back and the refund stays `pending`. The webhook is redelivered, or the sweeper tries again.

- [ ] **9. On success, update the order status and queue the email, in the same transaction as step 8.**
  - **Starts it:** step 8 set a refund to `succeeded`.
  - **Order status:** compute `sum(amount_cents)` of succeeded refunds for the payment. If it equals the captured amount, the order shows "Refunded". If it is greater than 0 but smaller, it shows "Partially refunded". Pending and failed refunds are ignored.
  - **Email:** insert one row into `email_outbox` for this refund. The unique `refund_id` guarantees at most one row per refund, even if the success event is processed twice.
  - **State stored:** the order's refund status and the outbox row, both committed together with the refund status.
  - **On failure:** the whole transaction rolls back, so no refund is marked succeeded without its order update and outbox row.

- [ ] **10. Send the customer email from the outbox.**
  - **Starts it:** a worker polls `email_outbox` for rows with status `queued`, or is triggered right after step 9 commits.
  - **Data moves:** server to the email service: the customer address, the refund amount and the order reference.
  - **Steps:**
    1. Claim the row by setting it to `sending` with a conditional update, so two workers cannot send the same email.
    2. Send the email, passing the `refund_id` as the email service's idempotency key if it supports one.
    3. On success, mark the row `sent` with `sent_at` and write an audit row.
  - **State stored:** the outbox row status.
  - **On failure:** a send error returns the row to `queued` and it is retried with backoff. Failed refunds never get an outbox row, so no email goes out for them. If a worker crashes after sending but before marking `sent`, a resend is possible. This is a small residual risk, and the email service's idempotency key reduces it.

### E. The refund is never left waiting (sweeper)

- [ ] **11. Scheduled sweeper checks pending refunds with the provider directly.**
  - **Starts it:** a scheduled job, every 15 minutes.
  - **Selects:** all refunds with `status = pending` where `last_checked_at` is null or older than 6 hours (well inside the 24-hour limit), or where `provider_refund_id` is null and no attempt has been made recently.
  - **Data moves:** server to provider only.
    - If `provider_refund_id` is set, fetch that refund's current status from the provider.
    - If it is null and the refund is under 24 hours old, repeat the create call with the stored `idempotency_key`. The provider returns the original refund if it exists, so this cannot create a duplicate.
    - If it is null and the refund is over 24 hours old, the key may have expired. Look the refund up by charge id and our refund id metadata, and do not create a new refund. If the provider has no matching refund, mark it `failed` with an audit note and an alert, since nothing was created. If the lookup itself fails, leave it `pending` and alert.
  - **Result:** pass any final status to the shared transition (step 8) with actor `system:sweeper`. If the provider still says pending, only `last_checked_at` is updated and an audit row is written.
  - **State stored:** `last_checked_at`, and whatever step 8 stores.
  - **On failure:** a provider error leaves the refund `pending`, and the next run retries it. An alert fires if any pending refund is more than 20 hours old without a successful check, so the 24-hour rule is never silently missed.

### F. Final outcome

- [ ] **12. The final outcome is recorded.**
  - **Starts it:** step 8 completes for a refund.
  - **Data moves:** none further.
  - **State stored (the complete record):**
    - the refund's final status (`succeeded` or `failed`), `provider_refund_id`, `provider_error` if any, and `resolved_at`
    - the audit trail: the request, each attempt, acceptance, every status change and who or what caused it
    - for success: the order's "Partially refunded" or "Refunded" status and a single sent email
    - for failure: the freed refundable amount and the stored reason
  - **Admin view:** the payment page shows each refund with its status, reason, note, amount and history, and the order shows the derived status.
  - **On failure:** a refund that cannot be resolved stays `pending`, and the sweeper and the alerts in step 11 keep working on it until it is resolved.

## Requirements covered

| Requirement | Where |
|---|---|
| Captured payments only, admins with permission only | Steps 1, 3 |
| Total of pending and succeeded never exceeds captured; concurrent admins | Step 3 (row lock plus sum check) |
| Amounts in cents, several partial refunds | Data section, step 3 |
| Reason list and free-text note | Steps 2, 3 |
| Only the server talks to the provider | Steps 2, 4, 11 |
| Idempotency key, 10 s timeout, 3 retries, 4xx not retried | Steps 3, 4, 4a |
| Webhooks duplicated or out of order | Steps 7, 8 |
| No pending refund unchecked for 24 hours | Step 11 |
| Email only after success, only once | Steps 9, 10 |
| Order status from succeeded refunds only | Step 9 |
| Audit of every request and status change | Steps 3, 4a, 5, 8, 10, 11 |
