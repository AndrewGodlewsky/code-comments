# Plan: refunds from the admin page

Today, support staff refund customers in the card provider's dashboard, so our database never learns that a refund happened. This plan lets admins issue full and partial refunds from our own admin page. Our server reserves the amount in our database, calls the provider's refund API, and then learns the final result from a signed webhook, or from a scheduled check if the webhook never comes. Every step is recorded in our own tables.

We already store payments with the provider's charge id, the captured amount and a status. There is no refund table yet.

## Terms

- **Captured:** the payment status meaning the money has been taken, so it can be refunded.
- **Pending refund:** a refund we created that has no final result yet. The provider's first reply only means "accepted", so a refund stays pending until a webhook or a status check says `succeeded` or `failed`.
- **Idempotency key:** a UUID we generate and send with the create-refund call. If the call is repeated with the same key within 24 hours, the provider returns the original refund instead of creating a new one.
- **Request token:** a one-time UUID placed in the refund form. It lets us recognise a resubmitted form and not create a second refund.
- **Webhook:** a signed message the provider posts to our endpoint (`refund.succeeded` or `refund.failed`). It can arrive more than once, out of order, and days later.
- **Row lock (`SELECT ... FOR UPDATE`):** a database lock on one payment row. A second transaction that wants the same row waits until the first finishes.
- **Outbox:** a table of emails waiting to be sent. We write the email there in the same transaction as the status change, and a worker sends it later.
- **Sweeper:** a scheduled job that asks the provider directly about refunds that are still pending.
- **Shared transition:** the single function that moves a pending refund to its final status. Webhooks, the provider's immediate reply and the sweeper all use it.

## Rules that apply to every step

- Amounts are in cents. A payment can have several partial refunds.
- The total of pending and succeeded refunds on a payment must never exceed its captured amount. Failed refunds do not count. This holds even when two admins refund the same payment at once.
- Only admins with refund permission can refund, and only captured payments can be refunded.
- Every refund has a reason from a fixed list (duplicate, fraudulent, customer request, other) and may have a free-text note.
- Only our server talks to the provider. The browser never does.
- A refund never stays pending more than 24 hours without our system checking its status with the provider directly. Webhooks alone are not enough.
- Every refund request and every status change writes an audit entry (who, what, when).
- The order shows "Partially refunded" or "Refunded" based on succeeded refunds only.
- The customer is emailed only after the refund has succeeded, and only once per refund.
- `succeeded` and `failed` are final. A refund never leaves them.

## Data this plan adds

- **`refunds`**: `id`, `payment_id`, `amount_cents` (>0), `reason` (duplicate, fraudulent, customer_request, other), `note` (nullable), `status` (`pending`, `succeeded`, `failed`), `idempotency_key` (unique, generated by us), `request_token` (unique), `provider_refund_id` (nullable, unique), `provider_error` (nullable), `requested_by`, `created_at`, `submitted_at`, `last_checked_at`, `resolved_at`. A `pending` refund with a null `provider_refund_id` means the provider has not yet confirmed it. That is not a separate status.
- **`refund_webhook_events`**: `provider_event_id` (unique), type, payload, `received_at`, `processed_at`.
- **`refund_audit_log`**: append-only, never updated or deleted. Columns: `refund_id`, `actor` (admin id, `system:webhook` or `system:sweeper`), `action`, `from_status`, `to_status`, `detail`, `at`.
- **`email_outbox`**: `refund_id` (unique), `status` (`queued`, `sending`, `sent`), `sent_at`.
- **Existing payments and orders:** we read the charge id, captured amount and status. The order's refund display status is derived from succeeded refunds.

## Steps

### A. Admin opens the payment

- [ ] **1. Admin opens the payment page.**
  - **Starts it:** the admin navigates to the payment.
  - **Data moves:** the server loads the payment and its refunds and computes `refundable = captured amount − sum of amount_cents of pending and succeeded refunds`.
  - **State stored:** none. The refund form carries a fresh request token.
  - **Checks:** the admin has refund permission and the payment is `captured`. Otherwise the form is not shown.
  - **On failure:** direct access without permission gets 403. A payment that is not captured shows "not refundable". A load error shows an error page and changes nothing.

### B. Admin submits a refund

- [ ] **2. Admin submits the form.**
  - **Starts it:** the admin clicks "Refund".
  - **Data moves:** browser to our server only: `payment_id`, `amount_cents` (a full refund is the current refundable amount), `reason`, optional `note`, request token.
  - **State stored:** none yet.
  - **On failure:** if the network fails, the admin can resubmit. The request token makes that safe.

- [ ] **3. Server validates and reserves the amount in one transaction.**
  - **Starts it:** the request from step 2 arrives.
  - **Checks, on the server, never trusting the page:**
    1. The session is valid and the admin has refund permission.
    2. `reason` is in the list, `note` is length-limited, `amount_cents` is an integer greater than 0.
    3. If a refund with this request token already exists, return it and do nothing else. This stops double clicks and retries from creating duplicates.
  - **Reservation:**
    1. Begin a transaction and lock the payment row (`SELECT ... FOR UPDATE`). Two admins refunding the same payment now run one after the other.
    2. Re-check the payment is `captured`.
    3. Sum `amount_cents` of this payment's pending and succeeded refunds.
    4. If that sum plus the new amount exceeds the captured amount, roll back and tell the admin "exceeds refundable amount (X cents left)". This is what the second of two simultaneous admins may see.
    5. Otherwise insert the refund as `pending` with no `provider_refund_id`, a new `idempotency_key`, the request token and `requested_by`, and insert an audit row (`requested`, actor, amount, reason).
    6. Commit, which releases the lock.
  - **State stored:** the refund row and audit row, committed before any provider call. The amount counts toward the cap from this moment, and the saved idempotency key is reused by every later retry.
  - **On failure:** any error rolls back everything and the admin sees the error. Nothing is reserved and the lock is released.

### C. Call the provider

- [ ] **4. Server calls the provider's create-refund API.**
  - **Starts it:** the commit in step 3, in the same request. If this process dies first, the sweeper (step 11) picks the refund up.
  - **Data moves:** our server to the provider only: charge id (from the payment), `amount_cents`, our refund id as metadata, the stored idempotency key, and the reason mapped to the provider's reason values where they exist. The call has a 10-second timeout.
  - **State stored:** `submitted_at` is set before the first attempt. `last_checked_at` is set on every attempt.
  - **Outcomes:**
    - **2xx (accepted):** go to step 6.
    - **4xx:** the provider rejected the refund. Do not retry. In one transaction, set `status = failed` only if it is still `pending`, store the provider's message in `provider_error`, set `resolved_at`, and write an audit row (`pending → failed`, provider message). Show the admin the provider's message. The refund no longer counts toward the cap, so the amount is available again.
    - **Timeout or 5xx:** go to step 5.
  - **On failure:** a crash before the call leaves a pending refund with no `provider_refund_id`, which the sweeper handles.

- [ ] **5. Retry on timeout or 5xx.**
  - **Starts it:** a timeout or 5xx in step 4.
  - **Data moves:** the same request with the same idempotency key, up to 3 retries (4 attempts in all), with short backoff and a 10-second timeout each. This is safe because a timed-out call may have created the refund, and repeating the key within 24 hours returns that refund instead of a second one.
  - **State stored:** an audit row for each failed attempt (`attempt n of 4 failed: timeout/5xx`). The refund stays pending.
  - **On success:** go to step 6. A 4xx on any retry follows the 4xx outcome in step 4.
  - **On failure after the last retry:** do not mark the refund failed, because the provider may have created it. Leave it pending with no `provider_refund_id`, and show the admin "submitted, awaiting provider confirmation". The sweeper keeps trying with the same key.

- [ ] **6. Record the provider's acceptance.**
  - **Starts it:** a 2xx from step 4 or 5.
  - **Data moves:** the provider's refund id and status come back.
  - **State stored:** in one transaction, set `provider_refund_id` and `last_checked_at` and add an audit row (`accepted by provider`). The status stays pending, because "accepted" is not the final result. If the response already carries a final status, apply it through the shared transition (step 8) as well.
  - **On failure:** the refund stays pending without the id. The provider has it, so a webhook or the sweeper fills the id in later. The admin sees "submitted, awaiting provider confirmation".

- [ ] **7. Show the admin the result so far.**
  - **Starts it:** the end of step 4, 5 or 6.
  - **Data moves:** the server returns the refund: pending, failed with the provider's message, or an error.
  - **State stored:** none. The order status does not change here, because only succeeded refunds affect it.
  - **On failure:** if the page fails to render, the refund still exists and appears in the payment's refund list.

### D. The final result arrives

- [ ] **8. Apply the final status with the shared transition.**
  - **Starts it:** the webhook handler (step 9), an immediate final status in step 6, or the sweeper (step 11).
  - **Data moves:** the new status (`succeeded` or `failed`), the source, any provider message.
  - **Rules, in one transaction:**
    1. Run `UPDATE refunds SET status = ?, resolved_at = now() WHERE id = ? AND status = 'pending'`. If no row changes, the refund is already final: do nothing more. If the event contradicts the final state (for example `failed` after `succeeded`), also write an audit row (`conflicting event ignored`) and raise an alert. This makes duplicate and out-of-order events harmless.
    2. Fill in `provider_refund_id` if it was missing.
    3. For `failed`: store the provider's message and write an audit row (`pending → failed`, actor `system:webhook`, `system:sweeper` or the admin). The amount is released automatically, because failed refunds are not counted.
    4. For `succeeded`: write an audit row (`pending → succeeded`), then do step 10 in the same transaction.
  - **State stored:** the refund status, the audit row, and for success the order status and the outbox row.
  - **On failure:** the transaction rolls back and the refund stays pending. The webhook is redelivered or the sweeper tries again.

- [ ] **9. Receive the provider's webhook.**
  - **Starts it:** the provider posts `refund.succeeded` or `refund.failed` to our endpoint, perhaps days later, perhaps repeated or out of order.
  - **Data moves:** provider to server: event id, type, provider refund id, status, and our refund id (from the metadata).
  - **Steps:**
    1. Verify the signature against the raw body with the shared secret. If invalid, return 400 and store nothing.
    2. Insert the event into `refund_webhook_events`. The unique `provider_event_id` stops duplicates: on conflict, return 200 and stop.
    3. Find the refund by `provider_refund_id`, or by our refund id from the metadata (this covers events that arrive before step 6 stored the id). If none is found, return a non-2xx status so the provider redelivers.
    4. Call the shared transition (step 8), set `processed_at` and return 200.
  - **State stored:** the event row, plus what step 8 stores.
  - **On failure:** return 5xx so the provider redelivers. A redelivery is safe because of the unique event id and the conditional update.

- [ ] **10. On success, update the order and queue the email, inside step 8's transaction.**
  - **Starts it:** step 8 set a refund to `succeeded`.
  - **Order status:** sum `amount_cents` of the payment's succeeded refunds. Equal to the captured amount means "Refunded". Above 0 but less means "Partially refunded". Pending and failed refunds are ignored.
  - **Email:** insert one `email_outbox` row for the refund. The unique `refund_id` allows at most one row per refund, even if the success event is processed twice.
  - **State stored:** the order status and the outbox row, committed with the refund status.
  - **On failure:** the whole transaction rolls back, so no refund is `succeeded` without its order update and outbox row.

- [ ] **11. Send the customer email from the outbox.**
  - **Starts it:** a worker polls `email_outbox` for `queued` rows, or is triggered after step 10 commits.
  - **Data moves:** server to the email service: customer address, refund amount, order reference.
  - **Steps:**
    1. Claim the row by setting it to `sending` with a conditional update, so two workers cannot send the same email.
    2. Send, passing the refund id as the email service's idempotency key if it supports one.
    3. Mark the row `sent` with `sent_at` and write an audit row.
  - **On failure:** a send error returns the row to `queued` and it is retried with backoff. Failed refunds never get an outbox row, so they send no email. If a worker crashes after sending but before marking `sent`, a resend is possible. This small risk is reduced by the email service's idempotency key.

### E. The sweeper

- [ ] **12. The sweeper checks pending refunds with the provider directly.**
  - **Starts it:** a scheduled job every 15 minutes.
  - **Selects:** pending refunds whose `last_checked_at` is null or older than 6 hours (well inside the 24-hour limit), or whose `provider_refund_id` is null and have had no recent attempt.
  - **Data moves:** server to provider only.
    - With a `provider_refund_id`: fetch the refund's current status.
    - Without one, under 24 hours old: repeat the create call with the stored idempotency key. The provider returns the original refund if it exists, so no duplicate is made.
    - Without one, over 24 hours old: the key may have expired, so look the refund up by charge id and our refund id metadata, and never create a new one. If the provider has no matching refund, mark ours `failed` with an audit note and an alert, since nothing was created. If the lookup itself fails, leave it pending and alert.
  - **Result:** pass any final status to the shared transition (step 8) with actor `system:sweeper`. If the provider still says pending, update only `last_checked_at` and write an audit row.
  - **State stored:** `last_checked_at`, plus what step 8 stores.
  - **On failure:** a provider error leaves the refund pending and the next run retries. An alert fires when any pending refund is more than 20 hours old without a successful check, so the 24-hour rule is never silently missed.

### F. Final outcome

- [ ] **13. The final outcome is recorded.**
  - **Starts it:** step 8 completes for a refund.
  - **State stored (the complete record):**
    - the final status, `provider_refund_id`, `provider_error` if any, and `resolved_at`
    - the audit trail: the request, each attempt, acceptance, every status change and who or what caused it
    - on success: the order's "Partially refunded" or "Refunded" status and a single sent email
    - on failure: the freed refundable amount and the stored reason
  - **Admin view:** the payment page lists each refund with status, reason, note, amount and history. The order shows the derived status.
  - **On failure:** a refund that cannot be resolved stays pending, and the sweeper and its alerts keep working on it.

## What happens when things fail

| Where | What happens |
|---|---|
| Reservation transaction (step 3) | Rolls back. Nothing reserved. Admin sees the error. |
| Process dies before the provider call | Pending refund without provider id. Sweeper repeats the call with the same key. |
| Provider returns 4xx | Marked failed, message shown, amount freed. No retry. |
| Timeout or 5xx after all retries | Stays pending. Admin sees "awaiting provider confirmation". Sweeper retries. |
| Writing the acceptance fails (step 6) | Stays pending without id. Webhook or sweeper fills it in. |
| Duplicate or out-of-order webhook | Conditional update changes nothing. Contradictions are audited and alerted. |
| Webhook for an unknown refund | Non-2xx, so the provider redelivers. |
| Transition transaction fails | Rolls back. Refund stays pending. Webhook redelivery or sweeper retries. |
| Email send fails | Row returns to `queued` and is retried. |
| Pending refund unchecked for 20 hours | Alert fires. |

## Open questions

- The brief does not say whether the email service supports an idempotency key. Until that is known, a rare duplicate email is possible after a worker crash.
- The backoff timing between retries and the note length limit are not specified and are left to implementation.
