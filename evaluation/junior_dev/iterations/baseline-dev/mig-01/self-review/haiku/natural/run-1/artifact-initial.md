# Move `users` from MySQL 8 to Postgres 16

## Design decisions

- **Outbox in the source database.** Every write to `users` inserts one row into `users_outbox` in the same MySQL transaction. The row holds only the user id. The repairer owns every copy that did not succeed immediately. Enqueueing through `app.jobs` is rejected for two reasons. Enqueue can raise when Redis is down, so it cannot sit on the request path. A failed job stops after about 15 minutes in `jobs:dead`, which nothing reads, so repair would not be automatic.
- **One guarded copy for every write into a store.** Dual writes, repair, backfill, verification fixes and the mirror all call the same operation on the target store. It takes a per-id lock, skips the id if a tombstone exists, inserts the row if it is missing, and replaces it only if the stored `version` is lower.
  - Postgres: `pg_advisory_xact_lock(id)`, then `INSERT ... ON CONFLICT (id) DO UPDATE ... WHERE users.version < EXCLUDED.version`.
  - MySQL: a locking read on the tombstone key, then `INSERT ... ON DUPLICATE KEY UPDATE col = IF(version < VALUES(version), VALUES(col), col)` for each column.
  - Erase: the same lock, then write the tombstone and delete the row in one transaction. Tombstones are kept permanently. They hold ids only.
- **Repair copies current state, not events.** The repairer reads the row from the source primary after the outbox row has committed, so its copy is at least as new as the write. Ids are never reused, so a missing source row means the user was erased. Events never need ordering.
- **Control state lives in one row, `users_control`.** Each store has one row: `source`, `epoch`, `write_paused`, `switch_step`, `mirror`. Every write reads its own store's row in its own transaction, with a shared lock. Flags are not used for the pause. Flags refresh every 30 s, so a pause, a switch and an unpause could take up to 90 s with no margin.
- **Ids.** Postgres uses `GENERATED BY DEFAULT AS IDENTITY`, which accepts explicit ids while mirroring. At every change of source, the new source's sequence is set above the largest id seen in either store, plus 1,000,000.
- **Timestamps.** Verify the MySQL server time zone is UTC before backfill, because `NOW(3)` follows the session time zone. Store `updated_at` in Postgres as `timestamp(3)` in UTC. The verifier compares it.

## Switch procedure S

Every change of source of truth uses this procedure. Later steps refer to it by name.

1. **Pause.** On the current source, set `write_paused = 1` in its `users_control` row. Record `max_outbox_id`, the largest id in its outbox. New writes get `503` with `Retry-After`. Writes already past the check finish and commit.
2. **Drain.** Wait until the current source's outbox has no row with id at or below `max_outbox_id`. The repairer copies those ids to the other store. Limit: 45 s.
3. **Prepare the new source.** Set its identity sequence (or check its AUTO_INCREMENT) above the largest id in either store plus 1,000,000. Make sure its control row exists with `write_paused = 1`.
4. **Commit point.** In the new source, set `source = new`, `epoch = epoch + 1`, `switch_step = 4`. It stays paused.
5. **Fence the old source.** In the old source, set `source = new` and `epoch = epoch + 1`. Any write that reaches it now is refused with 503.
6. **Unpause.** In the new source, set `write_paused = 0`.

Each step writes `switch_step` to the control row, so a crash resumes at the next step. Before step 4 commits, aborting means setting the old source's `write_paused = 0`. Nothing else has changed and no data has moved. After step 4 the procedure always rolls forward.

**Write check.** A write refuses with 503 unless its own store's control row says `source = this store`, `write_paused = 0`, and the `epoch` matches the instance's cached value. Each instance refreshes its cached control every 1 s. The old source's row names the new source, so a stale instance finds the new source from either store.

**Pause budget.** Steps 1 to 6 take at most 45 s for the drain, plus about 1 s for each commit and 1 s for cache refresh. The hard limit is 90 s, so the 45 s drain bound leaves margin.

## Checklist

- [ ] **0. Create schemas, control rows and monitoring**
  - **Starts when:** the migration owner starts it. `pg-core` is already provisioned.
  - **Does:**
    - In `pg-core`: `users` (`id BIGINT` identity primary key, `email VARCHAR(320)` unique, `name`, `plan`, `version INT`, `updated_at timestamp(3)`), `users_tombstones`, `users_outbox`, `users_control`.
    - In MySQL primary, additive only: `users_outbox` (`id` AUTO_INCREMENT, `user_id`, `enqueued_at`, `claimed_until`, `attempts`, `next_attempt_at`, `last_error`; indexes on `user_id` and `next_attempt_at`), `users_tombstones`, `users_control`, `users_migration_state` (`backfill_last_id`, `backfill_status`, `lease_owner`, `lease_until`, `read_100_since`, `last_clean_pass_at`), `users_verify_mismatch` (`user_id`, `found_at`).
    - Insert the control row in both stores: `source = mysql`, `epoch = 1`, `write_paused = 0`, `switch_step = 0`, `mirror = on`.
    - Add the repairer, backfill and verifier modules to review as part of the `users` boundary. They read `users`, so they must be exempt from `no-raw-users-sql` by name, not by pattern.
    - Set up monitoring: outbox count and oldest `enqueued_at` per store, PG write error rate, verifier mismatches, backfill `last_id` and its age, replica lag, and `app_flag_value` for each flag.
  - **State:** the new tables in both databases.
  - **If it fails:** nothing user-facing changes. Creating the tables is idempotent, so rerun it.

- [ ] **1. Deploy the migration build with dual writes off**
  - **Starts when:** a normal deploy. Flag `users_dual_write` is off.
  - **Does:** the write path checks the control row. The outbox insert and the Postgres copy run only when the flag is on. The repairer runs on every instance (or one leased instance) and is idle while the outbox is empty. Reads still use the MySQL replica.
  - **State:** MySQL control row (source MySQL) and outbox.
  - **If it fails:** roll back the deploy. The new tables and the control row do no harm.

- [ ] **2. Turn on dual writes**
  - **Starts when:** the operator sets `users_dual_write` to 100% after step 1 is live on every instance.
  - **Does:** each write runs as follows.
    1. Begin a MySQL transaction. Check the control row (shared lock). Apply the write. Read the row back. Insert the outbox row. Commit.
    2. After commit, run a guarded copy to Postgres with a 500 ms timeout, using the read-back row. On success, delete this write's own outbox row.
    3. Return the response.
    - Any Postgres error is caught, logged and counted. The request still succeeds. The repairer handles what is left.
    - Erasure uses the same path. A delete writes an outbox row, and the guarded delete runs after commit. The erasure job must treat 503 as retryable.
  - **State:** MySQL outbox. The Postgres copy is idempotent.
  - **If it fails:** Postgres down means the outbox grows and requests still succeed. Alert on outbox age. Do not turn the flag off once step 4 has started. Writes made with the flag off are seen by neither Postgres nor the outbox.

- [ ] **3. Gate: every instance is dual-writing**
  - **Starts when:** every deployed instance reports `app_flag_value{flag="users_dual_write"} = on`, and the count of reporting instances equals the deployed count. Old builds that do not export the metric count as not ready. Then wait a further 60 s. That is longer than any write transaction plus the 5 s replica-lag bound.
  - **State:** none. This is a check.
  - **If it fails:** keep waiting. Redeploy any stuck instance first.

- [ ] **4. Backfill from the replica**
  - **Starts when:** step 3 passes and the operator sets `users_backfill_enabled`. It runs in a dedicated worker. One worker is active at a time, holding a lease in `users_migration_state` (60 s, renewed each batch). It is not a web instance and not a jobs-queue job.
  - **Does:** for each batch, the worker does the following.
    1. If the lease is lost, stop.
    2. Read `mysql_replica_lag_seconds`. If it is above 5 s, sleep 1 s and check again, without reading.
    3. Read `SELECT * FROM users WHERE id > :last_id ORDER BY id LIMIT 2000` from the replica.
    4. If the batch is empty, mark the backfill complete.
    5. Run one Postgres transaction with a guarded copy of each row, in ascending id order.
    6. In MySQL primary, set `backfill_last_id` to the batch's largest id.
  - **State:** `backfill_last_id` and the lease in MySQL primary.
  - **If it fails:** a crash between steps 5 and 6 re-reads and re-copies the batch, which is safe because the copy is idempotent. Replica lag above 5 s pauses the worker. Postgres errors retry with backoff and lose no progress. Alert if `last_id` has not moved for 10 minutes. Erased ids are blocked by tombstones.

- [ ] **5. Verify until a pass is clean**
  - **Starts when:** step 4 completes. The verifier then runs continuously.
  - **Does:** it walks both tables in primary-key order by merge-join. The MySQL side is read from the replica. It compares `id`, `email`, `name`, `plan`, `version` and `updated_at`. It also finds Postgres rows that have no MySQL row. Each mismatched id is rechecked after its outbox rows are gone, comparing MySQL primary with Postgres. If it still differs, the verifier inserts an outbox row. The repairer then fixes it, with no manual step. A tombstoned id found in Postgres is removed.
  - **Clean pass:** a full walk that ends with no unresolved mismatches. Record `last_clean_pass_at`.
  - **State:** `users_verify_mismatch` and `users_migration_state`.
  - **If it fails:** an unfinished pass is not clean and is retried. A mismatch that repeats after its recheck blocks the next gate. It does not stop the verifier.

- [ ] **6. Ramp reads to Postgres**
  - **Starts when:** `last_clean_pass_at` is set after step 4 completes. The operator sets `users_read_source` to 1%, then 10%, then 50%, then 100%. The flag is keyed on `user_id`, so each user always reads from the same store.
  - **Does:** a read tries Postgres with a 200 ms timeout. Before the switch, it also checks `users_outbox` on the MySQL primary for that user id. If a pending row exists, the read goes to the MySQL primary. If Postgres errors or times out, the read falls back to the MySQL replica. Reads never fail.
  - **State:** the flag, and the pending check reads MySQL.
  - **If it fails:** a mismatch or Postgres read errors set `users_read_source` back to 0. Reads return to MySQL within about 30 s, with no outage. Instances can disagree on the flag for up to 30 s. That is harmless, because both stores are verified equal.

- [ ] **7. Soak for three days at 100% Postgres reads**
  - **Starts when:** every instance reports `users_read_source = 100%`. The clock `read_100_since` is set automatically.
  - **Does:** nothing beyond the verifier and monitoring. Any read served from MySQL resets the clock. This includes fallbacks and pending-write reads. Those are rare in normal operation, but a Postgres outage will delay the switch. That is the intended strictness.
  - **State:** `read_100_since` in MySQL.
  - **If it fails:** the clock resets to zero. Mismatches found during the soak are repaired and logged. A repeating mismatch blocks step 8.

- [ ] **8. Switch: Postgres becomes the source of truth**
  - **Starts when:** the operator runs procedure S, with old source MySQL and new source Postgres. Gates before step 1: `now - read_100_since >= 72 h`; `last_clean_pass_at` is under 24 h old with no open mismatches; the outbox count is below its threshold and the oldest row is under 60 s old; Postgres is healthy; replica lag is normal; no backfill lease is held; the operator approves.
  - **Does:** procedure S. Afterwards, writes commit to Postgres first. The outbox lives in Postgres, and the repairer mirrors writes to MySQL.
  - **State:** control rows in both stores. `users_migration_state.source_changed_at` is set at step 6.
  - **If it fails:** before step 4, abort (see procedure S). After step 4, roll forward.

- [ ] **9. Mirror to MySQL while Postgres is the source (at least 14 days)**
  - **Starts when:** step 8 is complete. This runs automatically.
  - **Does:** writes go to Postgres with the control check and an outbox row in Postgres, then to a guarded copy into MySQL. The repairer copies Postgres outbox rows to MySQL. The verifier keeps comparing the MySQL mirror with the source. Reads go to Postgres. If Postgres errors, reads fall back to the MySQL replica. That mirror may be stale, and the fallback is logged.
  - **State:** Postgres outbox and control row. The mirror in MySQL is the rollback target.
  - **If it fails:** MySQL down means writes still succeed on Postgres, and the mirror backlog grows in the Postgres outbox. Rollback is blocked until that backlog drains.

- [ ] **10. Rollback to MySQL (possible only during step 9)**
  - **Starts when:** the operator runs procedure S with old source Postgres and new source MySQL. Gates: the mirror outbox is drained or can be drained within the pause; the last clean pass is after step 8 and under 24 h old; MySQL is reachable. At the start, set `users_read_source` to MySQL. The flag skew is harmless.
  - **Does:** procedure S. Before unpausing, check that MySQL's AUTO_INCREMENT is above the largest id, which InnoDB advances when the mirror inserts explicit ids.
  - **State:** control rows.
  - **If it fails:** a drain that does not finish within 45 s aborts before step 4, and Postgres stays the source. Nothing is lost, because the Postgres outbox still holds every unmirrored write.

- [ ] **11. Postgres-only writes (no earlier than 14 days after step 8)**
  - **Starts when:** at least 14 days have passed since step 8 unpaused, as recorded in `source_changed_at`. The mirror outbox is empty. Postgres is healthy. The operator approves.
  - **Does:** procedure S with old and new source both Postgres. Step 3 and step 5 are skipped. Step 4 sets `mirror = off`. From this point MySQL receives no writes, and rollback to MySQL is no longer possible. The MySQL copy is stale from here on.
  - **State:** Postgres control row.
  - **If it fails:** before step 4, abort. Afterwards, roll forward. Postgres errors now fail writes with a retryable 503, because there is no other store to write to.

- [ ] **12. Drop the MySQL `users` table**
  - **Starts when:** step 11 has been in effect, a final logical dump of `users` has been taken and stored, and the change has been reviewed on its own. This is not part of the migration deploy. We recommend a further wait of 7 days after step 11. That number is our suggestion, not part of the brief.
  - **Does:** drop `users` and the mirror tables in MySQL, and remove the MySQL code paths.
  - **State:** the dump is the only copy of the old data.
  - **If it fails:** the drop cannot be reversed. Restore from the dump.

## Open questions and assumptions

- **Reads after step 11.** Postgres is then the only store. Reads "never fail" can only hold through a stale MySQL fallback, or through accepting a Postgres outage as a read outage. The brief does not settle this. Decide before step 11.
- **Outbox load.** Each write adds an outbox insert and delete in MySQL, about 800 extra statements per second at peak. Each read during step 6 adds an indexed primary lookup, about 3,000 per second at peak. Check primary capacity before step 2.
- **Email uniqueness.** A copy can collide with a changed row's old email if the copies arrive out of order. On a unique violation, the repairer re-reads the conflicting holder from the source, copies both rows, and retries them in one target transaction in id order. Retry with backoff. Alert on repeats.
- **Id margin.** The 1,000,000-id margin is our assumption. It must be larger than any gap the sequence can create during a pause.
- **Erasure job.** It must treat 503 as retryable, or erasures fail silently during pauses.
- **Verifier scope.** Its comparison runs on the replica, so it can report false mismatches for rows changing right now. The primary recheck exists for this reason.
