# Migration plan: `users` from MySQL 8 to Postgres 16

## Design decisions

- **Flags only choose a direction. They never decide safety.** Instances can disagree for 30 seconds, so every write transaction also takes a share lock on a one-row fence table in the database it writes to. The switcher closes a fence with an `UPDATE`. That `UPDATE` waits for in-flight writes to finish, and from then on no write can commit there, whatever an instance's cached flag says.
- **Repair uses a durable outbox, not Redis jobs.** `jobs.enqueue` can raise when Redis is down, and a job is dead-lettered after about 15 minutes with nothing processing `jobs:dead`. That cannot give "fixed automatically". Instead, the write transaction on the source-of-truth (SoT) database also inserts a row into `users_sync_outbox` in the same transaction. A failed copy therefore cannot be lost, and a drainer retries it forever.
- **The drainer copies the current row, not a payload.** It reads the user's current row from the SoT primary, never a replica, and applies it with the version rule. If the row is gone, it writes a tombstone and deletes the copy. Replays are idempotent.
- **Tombstones enforce "never reappears".** The table `users_erased(id)` exists on both sides. Every copy statement skips ids that have a tombstone. Delete handling inserts the tombstone and deletes the row in one transaction. A stale replica read in the backfill cannot resurrect a row. MySQL never reuses ids, so a tombstone cannot hit a new user.
- **Version rule.** Every copy into the follower is `INSERT … ON CONFLICT (id) DO UPDATE … WHERE users.version < EXCLUDED.version`. The MySQL equivalent is used for reverse copies. It is guarded by `NOT EXISTS (tombstone)` and applies to dual writes, backfill and repair alike.
- **Flags** (all in `app.flags`):
  - `users.dual_write` (bool)
  - `users.backfill_enabled` (bool)
  - `users.read_pg_pct` (percentage, bucketed on `user_id`)
  - `users.sot` (`mysql` or `pg`)
  - `users.mirror` (`both`, `deletes_only` or `off`)
- **"Every instance" includes the job workers.** The erasure job calls `UserRepository.delete`, so workers must export `app_flag_value` too. "All confirmed" means the number of `app_flag_value{flag=X}` series with the new value equals the number of running web and worker processes, and no process on an old build remains.
- **New ids after the switch** come from a Postgres identity column declared `GENERATED BY DEFAULT AS IDENTITY`. MySQL ids are inserted explicitly until the switch. During the switch, the sequence is set past every id in either database.

## Checklist

### Phase A: Prepare (no behaviour change)

- [ ] **1. Create schema on both databases.**
  - **Starts:** a manual DDL change, applied before any deploy.
  - **Changes:**
    - Postgres:
      - `users` (same columns, `id` as identity BY DEFAULT, unique `email`)
      - `users_erased(id)`
      - `users_sync_outbox(seq, user_id, attempts, next_attempt_at)`
      - `migration_fence(state)`, created **closed**
      - `backfill_state(last_id, lease_holder, lease_expires, updated_at)`, with one row, `last_id=0`
    - MySQL: `users_sync_outbox`, `users_erased` and `migration_fence`, created **open**. These are new tables only, so `users` is not locked.
  - **State:** the database itself.
  - **If it fails:** the DDL is idempotent (`IF NOT EXISTS`). Nothing reads these tables yet, so fix it and rerun.

- [ ] **2. Deploy the code with every flag off.**
  - **Starts:** a normal deploy of web and workers, plus a new worker process, the *drainer*.
  - **Changes:** `UserRepository` gets these new paths, all dormant:
    - fence check
    - outbox insert
    - inline copy
    - fallback reads
    - tombstone-aware copy
  - **State:** none yet.
  - **If it fails:** roll the deploy back. With all flags off, behaviour is identical to today.
  - **Done when:** the rollout is complete and every process exports `app_flag_value`.
  - **Drainer:**
    - It polls the MySQL outbox every second, claims rows in `seq` order with `FOR UPDATE SKIP LOCKED`, and applies them as described above.
    - On success it deletes that user's outbox rows with `seq <=` the claimed `seq`.
    - On failure it increments `attempts` and backs off up to 60 seconds. It never dead-letters.
    - It alerts when the oldest row is older than 5 minutes.

### Phase B: Dual writes (MySQL is SoT)

- [ ] **3. Turn on dual write.**
  - **Starts:** flag `users.dual_write=true`.
  - **Changes:**
    - Each write takes a share lock on the MySQL fence and requires `open`.
    - Each write inserts an outbox row in the same MySQL transaction.
    - After commit, the request makes one best-effort inline copy to Postgres. It re-reads the row from the primary and uses a 100 ms timeout. A circuit breaker opens after 5 consecutive failures and stays open for 10 seconds. Any error is swallowed and counted, and the request still succeeds. If the inline copy works, it deletes the outbox rows it covered. Otherwise the drainer repairs the row within seconds.
  - **State:** the MySQL outbox. It is durable and committed atomically with the write.
  - **If it fails:**
    - Postgres down: the outbox grows and drains on recovery, and users see nothing.
    - MySQL down: the write fails, exactly as today.
    - Bad behaviour in general: set the flag false. Rows already in the outbox still drain.

- [ ] **4. Confirm every instance is dual-writing.**
  - **Starts:** the condition that the series count for `users.dual_write=true` equals the running process count, then a further 2-minute settle.
  - **Changes:** nothing.
  - **State:** none.
  - **If it fails:** wait or investigate the missing process. The backfill must not start until this holds. The settle also covers a replica read that is a few seconds stale relative to a delete by the last instance to switch.

- [ ] **5. Backfill.**
  - **Starts:** step 4 satisfied, then `users.backfill_enabled=true`.
  - **Changes:** a single backfill runner takes a lease row in `backfill_state` and loops:
    1. Fail closed: if `mysql_replica_lag_seconds` is above 5, or the metric is missing, sleep 10 seconds and recheck. Check before every batch.
    2. Read at most 1,000 rows (under the 2,000 cap) with `id > last_id ORDER BY id` from `mysql.replica`.
    3. In one Postgres transaction, upsert the batch with the version rule and the tombstone guard, **and** `UPDATE backfill_state SET last_id = <max id read> WHERE last_id < <that>`.
    4. Stop when the read returns no rows.
  - **State:** `backfill_state.last_id` in Postgres. It is atomic with the batch, so after a crash the runner resumes after the last completed batch, never from the start. The lease prevents two runners. Replica lag, redis and a flag are not used for progress.
  - **If it fails:**
    - Crash: restart and resume from `last_id`.
    - An email unique-violation on a row: retry the batch row by row, then insert an outbox row for that id so the drainer retries it with backoff.
    - Stale rows: the version rule and tombstones make replays and stale replica reads harmless.
    - Rows written after the cursor passes or while the replica lags are covered by dual write.
    - Flag off: pauses it.

- [ ] **6. Full comparison.**
  - **Starts:** the backfill is finished and the outbox age is under 5 seconds. A job then walks both tables in id order, merged.
  - **Changes:** it classifies every id as missing in Postgres, extra in Postgres, or a version or field difference. Each difference is rechecked against the MySQL primary and the outbox. It counts as a mismatch only if it persists and no outbox row is pending for that id. It heals each one by inserting an outbox row, and for an "extra in Postgres" id the drainer writes the tombstone and deletes it.
  - **State:** a result row (counts, started, ended) in Postgres.
  - **If it fails:** a pass with any mismatch is not a pass. Repair, then rerun until one full pass reports 0. Equal version with different content should be impossible, so it pages a human.
  - **Gate:** this pass reporting 0 is the only condition for step 7.

### Phase C: Move reads

- [ ] **7. Ramp reads.**
  - **Starts:** step 6 reports 0 mismatches. Flag `users.read_pg_pct` is raised through 1, 10, 50 and 100, holding each level until the p99 and error rates are healthy.
  - **Changes:** `get` reads Postgres when `flags.enabled_for("users.read_pg_pct", user_id)` is true. A Postgres error or timeout falls back to the MySQL replica in the same call, so reads never fail. Reads may trail a write by the drain lag, which is similar to today's replica lag. A stale read followed by `update` raises `StaleWrite`, which callers already handle.
  - **State:** the flag.
  - **If it fails:** lower the percentage. No data is touched.

- [ ] **8. Soak at 100% reads for at least 3 days.**
  - **Starts:** every instance exports `read_pg_pct=100`. That moment starts the 3-day clock.
  - **Changes:** nothing. The comparison reruns daily.
  - **State:** the clock start is recorded in the migration log.
  - **If it fails:** any drop below 100%, or a nonzero comparison, resets the clock.

### Phase D: Switch the source of truth

- [ ] **9. Prepare and run the switch.** This is the only planned write pause. Run it as a scripted, resumable state machine, with its state in a Postgres `switch_state` row.
  - **Starts:** a manual script launch once these hold:
    - at least 3 days at 100% reads
    - the latest comparison reports 0 mismatches
    - the outbox is idle
    - the reverse outbox, MySQL tombstones and fence tables exist
  - **Changes**, in order:
    1. **Close the MySQL fence** (`UPDATE migration_fence SET state='closed'`). The update waits for in-flight writes. From then on every SoT write (create, update, delete, including the erasure job) gets a retryable 503. This is the start of the pause and starts a 60-second deadline for the next steps.
    2. **Drain** the forward outbox to zero, **and** verify a delta compare of rows touched since the last full pass.
    3. Set the Postgres sequence to `greatest(MySQL max(id) read from the primary, Postgres max(id)) + 1000`.
    4. **Open the Postgres fence.**
    5. Set `users.sot=pg` and `users.mirror=both`.
  - **Effects after the flag flips:**
    - A write commits to Postgres first, with the outbox in the same transaction, then a best-effort inline copy to MySQL. This is the same mechanism run in reverse, with the drainer reading from the Postgres primary and writing to MySQL with the version rule and tombstones.
    - Instances that still hold the old flag hit the closed MySQL fence and return 503. They pick up the flag within 30 seconds.
    - Postgres creates use the identity sequence.
  - **Pause length:** drain (about 10 seconds) plus up to 30 seconds of flag refresh, so well under 90 seconds. Reads are unaffected throughout.
  - **State:** the fence rows, the flag and `switch_state`.
  - **If it fails:**
    - Drain or verify not finished by the 60-second deadline: reopen the MySQL fence. Nothing has been written to Postgres, so this is a clean abort.
    - Script crash before the Postgres fence opens: a watchdog reopens the MySQL fence after 75 seconds.
    - Crash after that point: resume forward from `switch_state`. A resumed switch ends with the Postgres fence open.

### Phase E: Soak with rollback available

- [ ] **10. Soak for at least 14 days.**
  - **Starts:** step 9 completes. The 14-day clock starts there.
  - **Changes:** nothing. MySQL is kept current by the reverse mirror. The comparison reruns daily in both directions, with "MySQL behind" tolerated only while the reverse outbox is pending.
  - **State:** the Postgres outbox, plus tombstones on both sides.
  - **If it fails:** a MySQL outage only grows the reverse outbox. Postgres writes continue and nothing is lost.

- [ ] **10R. Rollback (any time before step 11).**
  - **Starts:** a manual script launch. This is the same state machine mirrored, and it is a second pause of up to 90 seconds.
  - **Changes**, in order:
    1. Close the Postgres fence (503 for writes).
    2. Drain the reverse outbox to zero.
    3. `ALTER TABLE users AUTO_INCREMENT = max(id) + 1000`.
    4. Open the MySQL fence.
    5. Set `users.sot=mysql` and mirror to Postgres again.
  - **Why no write is lost:** every write already lives in MySQL via the reverse mirror, and the drain in step 2 finishes whatever was pending. Deletes use tombstones, so erased users stay erased.
  - **If it fails:**
    - MySQL unreachable: the drain cannot finish, so the script aborts and reopens the Postgres fence. Writes continue on Postgres.
    - Past the deadline: abort the same way.

### Phase F: Retire MySQL

- [ ] **11. Stop mirroring writes.**
  - **Starts:** all of these hold:
    - at least 14 days since step 9
    - no rollback is wanted
    - the reverse outbox is empty
    - the final comparison reports 0
  - **Changes:** set `users.mirror=deletes_only`. Writes go to Postgres only. Deletes are still mirrored to MySQL so that erased users do not linger in the stale table. This is the point of no return for rollback.
  - **State:** the flag.
  - **If it fails:** set `mirror=both`, which is valid only until the first write that was not mirrored. Verify the reverse outbox drains to zero before doing so.

- [ ] **12. Archive MySQL, remove the code, then drop the table.**
  - **Starts:** step 11 has run, and a deploy follows it.
  - **Changes:**
    1. Take a final dump of MySQL `users`. Give it a short retention, because it contains data that the erasure job no longer purges.
    2. Deploy code with the MySQL paths, outbox and fences removed.
    3. After 7 days with no connections to the table, drop MySQL `users` and its outbox, tombstone and fence tables.
  - **State:** the dump.
  - **If it fails:** roll back the deploy. The MySQL table is untouched until step 12.3, which is the only irreversible action.
