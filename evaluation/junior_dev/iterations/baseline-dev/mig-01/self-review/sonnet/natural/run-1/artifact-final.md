# Migration plan: `users` from MySQL 8 to Postgres 16

## How it works, in short

All reads and writes of `users` go through `UserRepository`, so all migration logic lives there. One mechanism is used in both directions. The **source of truth (SoT)** database takes every write first. The other database, the **follower**, is updated afterwards. Today MySQL is the SoT and Postgres is the follower. At the switch the roles swap, and the same mechanism now runs in reverse. That reverse flow is what makes rollback to MySQL possible without losing writes.

Every write has three parts:

1. **Commit.** The write commits in the SoT database. In the same transaction it inserts a row into that database's *outbox*, a to-do list of copies the follower is still owed. Because both rows commit together, a pending copy cannot be lost.
2. **Quick copy.** After the commit, the request makes one best-effort copy to the follower. If it fails, the error is swallowed and the request still succeeds.
3. **Repair.** A background worker, the *drainer*, works through the outbox and repeats any copy that did not happen, until the follower is correct.

## Terms

- **Outbox:** table `users_sync_outbox(seq, user_id, attempts, next_attempt_at)` in the SoT database. One row means "this user's row must be copied to the follower".
- **Drainer:** a new worker process that reads the outbox and copies each listed user to the follower, retrying forever. This is the automatic repair.
- **Tombstone:** a row in table `users_erased(id)`, which exists in both databases. It records that a user was erased. Every copy statement skips ids that have a tombstone, so an erased user never comes back.
- **Version rule:** every copy into either database may only insert a missing row or replace a row whose `version` is lower than the incoming one. Nothing else is allowed. In Postgres this is `INSERT ... ON CONFLICT (id) DO UPDATE ... WHERE users.version < EXCLUDED.version`; MySQL gets the equivalent statement for reverse copies. Each copy also has a `NOT EXISTS (tombstone)` guard. The rule applies to dual writes, backfill and repair alike, so replaying any copy is harmless.
- **Fence:** a one-row table `migration_fence(state)` in each database, where `state` is `open` or `closed`. It is the hard stop for writes during a switch.
  - Every user write (create, update or delete, but not a follower copy) first takes a shared lock on the fence row in the SoT database. If the state is `closed`, the write fails with a retryable 503.
  - To close a fence, the switcher runs `UPDATE migration_fence SET state='closed'`. This needs an exclusive lock, so it waits until in-flight writes finish.
  - Once that update returns, no write can commit in that database, whatever any instance's cached flag says.
- **Flags:** feature flags in `app.flags`. Each instance caches all flags and refreshes them every 30 seconds, so instances can disagree for up to 30 seconds after a change. Each instance exports the values it is using as the metric `app_flag_value{flag=...}`.

## Design decisions

- **Flags choose a direction; fences guarantee safety.** Because instances can disagree about a flag, a flag alone cannot be trusted to stop writes. The fence can.
- **Repair uses the outbox, not Redis jobs.** `jobs.enqueue` raises if Redis is down, and a failed job is dead-lettered after about 15 minutes into `jobs:dead`, which nothing processes. That cannot meet "fixed automatically". The outbox lives in the same database transaction as the write, so it cannot be lost.
- **The drainer copies the current row, not a payload.** It reads the user's current row from the SoT primary (never a replica) and applies it with the version rule. If the row no longer exists, it writes a tombstone on the follower and deletes the copy there.
- **Deleting** inserts the tombstone and deletes the row in one transaction. A stale replica read in the backfill therefore cannot resurrect a row. MySQL does not reuse ids, so a tombstone cannot match a new user.
- **Flags used** (all in `app.flags`):
  - `users.dual_write` (bool): turns the migration write path on.
  - `users.backfill_enabled` (bool): lets the backfill run.
  - `users.read_pg_pct` (percentage, bucketed on `user_id`): share of reads served from Postgres.
  - `users.sot` (`mysql` or `pg`): which database is the SoT.
  - `users.mirror` (`both`, `deletes_only` or `off`): which writes are copied to the follower.
- **"Every instance" includes job workers.** The GDPR erasure job calls `UserRepository.delete`, so workers must export `app_flag_value` too. "All instances confirmed" means both of these hold: the number of `app_flag_value{flag=X}` series showing the new value equals the number of running web and worker processes, and no process on an old build remains.
- **New ids after the switch** come from a Postgres identity column declared `GENERATED BY DEFAULT AS IDENTITY`. Until the switch, MySQL assigns ids (AUTO_INCREMENT) and they are inserted into Postgres explicitly. At the switch, the Postgres sequence is set past every id in either database.

## Checklist

### Phase A: Prepare (no behaviour change)

- [ ] **1. Create schema on both databases.**
  - **Starts:** a manual DDL change, applied before any deploy.
  - **Changes:**
    - Postgres:
      - `users` (same columns as MySQL, `id` as identity BY DEFAULT, unique `email`)
      - `users_erased(id)`
      - `users_sync_outbox`
      - `migration_fence(state)`, created **closed**
      - `backfill_state(last_id, lease_holder, lease_expires, updated_at)`, with one row, `last_id=0`
      - `switch_state` (used in step 9)
    - MySQL: `users_sync_outbox`, `users_erased` and `migration_fence` (created **open**). These are new tables, so `users` is not locked.
  - **State:** the databases themselves.
  - **If it fails:** the DDL is idempotent (`IF NOT EXISTS`) and nothing reads these tables yet. Fix it and rerun.

- [ ] **2. Deploy the code with every flag off.**
  - **Starts:** a normal deploy of web and workers, plus a new worker process, the drainer.
  - **Changes:** `UserRepository` gains these paths, all dormant: fence check, outbox insert, quick copy, fallback reads, tombstone-aware copy, and their reverse-direction versions. Workers and web instances all export `app_flag_value`.
  - **Drainer behaviour:**
    - Every second it polls the outbox of the current SoT database and claims rows in `seq` order with `FOR UPDATE SKIP LOCKED`.
    - On success it deletes that user's outbox rows with `seq <=` the claimed `seq`.
    - On failure it increments `attempts` and backs off, up to 60 seconds between tries. It never gives up.
    - It alerts when the oldest outbox row is older than 5 minutes.
  - **State:** none yet.
  - **Done when:** the rollout is complete and every process exports `app_flag_value`.
  - **If it fails:** roll the deploy back. With all flags off, behaviour is identical to today.

### Phase B: Dual writes (MySQL is SoT)

- [ ] **3. Turn on dual write.**
  - **Starts:** flag change `users.dual_write=true`.
  - **Changes:**
    - Each write takes a shared lock on the MySQL fence and requires `open`.
    - Each write inserts an outbox row in the same MySQL transaction.
    - After commit, the request makes one best-effort copy to Postgres. It re-reads the row from the MySQL primary and uses a 100 ms timeout. A circuit breaker opens after 5 consecutive failures and stays open for 10 seconds, during which copies are skipped. Any error is swallowed and counted, and the request still succeeds.
    - If the copy works, the request deletes the outbox rows it covered. Otherwise the drainer repairs the row within seconds.
  - **State:** the MySQL outbox, which is durable and committed atomically with the write.
  - **If it fails:**
    - Postgres down: the outbox grows and drains on recovery. Users see nothing.
    - MySQL down: the write fails, exactly as today.
    - Any other bad behaviour: set the flag to false. Rows already in the outbox still drain.

- [ ] **4. Confirm every instance is dual-writing.**
  - **Starts:** the number of `app_flag_value{flag="users.dual_write"}` series showing `true` equals the running process count (web and workers). Then wait a further 2 minutes, so that stale replica reads cannot miss a delete made by the last instance to switch.
  - **Changes:** nothing.
  - **State:** none.
  - **If it fails:** wait, or investigate the missing process. The backfill must not start until this holds.

- [ ] **5. Backfill.**
  - **Starts:** step 4 is satisfied, then `users.backfill_enabled=true`.
  - **Changes:** a single backfill runner takes a lease row in `backfill_state` (so two runners cannot run at once) and loops:
    1. **Pause check, before every batch:** if `mysql_replica_lag_seconds` is above 5 or missing, sleep 10 seconds and recheck. A missing metric counts as "too laggy", so the check fails closed.
    2. **Read** at most 1,000 rows (under the 2,000 cap) with `id > last_id ORDER BY id` from `mysql.replica`.
    3. **Write**, in one Postgres transaction: upsert the batch with the version rule and tombstone guard, and run `UPDATE backfill_state SET last_id = <max id read> WHERE last_id < <that id>`.
    4. **Stop** when a read returns no rows.
  - **State:** `backfill_state.last_id` in Postgres. It commits atomically with each batch, so after a crash the runner resumes after the last completed batch.
  - **If it fails:**
    - Crash: restart and resume from `last_id`.
    - Email unique violation on a row: retry the batch row by row, then insert an outbox row for the offending id so the drainer retries it with backoff.
    - Stale or replayed rows: the version rule and tombstones make them harmless.
    - Rows written after the cursor has passed, or while the replica lags: covered by dual write.
    - To pause: set the flag to false.

- [ ] **6. Full comparison.**
  - **Starts:** the backfill has finished and the oldest outbox row is under 5 seconds old. A job then walks both tables in id order, merged.
  - **Changes:**
    - It classifies every id as missing in Postgres, extra in Postgres, or different in version or fields.
    - It rechecks each difference against the MySQL primary and the outbox. A difference counts as a mismatch only if it persists and no outbox row is pending for that id.
    - It heals each mismatch by inserting an outbox row. For an "extra in Postgres" id, the drainer writes the tombstone and deletes the row.
  - **State:** a result row (counts, started, ended) in Postgres.
  - **If it fails:** a pass with any mismatch is not a pass. Repair, then rerun until one full pass reports 0. Equal version with different content should be impossible, so it pages a human.
  - **Gate:** one full pass reporting 0 mismatches is the only condition for step 7.

### Phase C: Move reads

- [ ] **7. Ramp reads.**
  - **Starts:** step 6 reports 0 mismatches. Raise `users.read_pg_pct` through 1, 10, 50 and 100, holding each level until p99 latency and error rates are healthy.
  - **Changes:**
    - `get` reads Postgres when `flags.enabled_for("users.read_pg_pct", user_id)` is true.
    - A Postgres error or timeout falls back to the MySQL replica within the same call, so reads never fail.
    - A Postgres read may trail a write by the drain lag, similar to today's replica lag. A stale read followed by `update` raises `StaleWrite`, which callers already handle.
  - **State:** the flag.
  - **If it fails:** lower the percentage. No data is touched.

- [ ] **8. Soak at 100% reads for at least 3 days.**
  - **Starts:** every instance exports `read_pg_pct=100`. That moment starts the 3-day clock.
  - **Changes:** nothing. The full comparison reruns daily.
  - **State:** the clock start time, recorded in the migration log.
  - **If it fails:** any drop below 100%, or a nonzero comparison, resets the clock.

### Phase D: Switch the source of truth

- [ ] **9. Run the switch.** This is the only planned write pause. It is a scripted, resumable state machine whose progress is stored in the Postgres `switch_state` row.
  - **Starts:** a manual script launch, once all of these hold:
    - at least 3 days at 100% reads
    - the latest comparison reports 0 mismatches
    - the outbox is idle
    - the reverse-direction code paths (Postgres outbox, MySQL tombstones, fences), deployed in step 2, have been tested
  - **Changes**, in order:
    1. **Close the MySQL fence.** The update waits for in-flight writes. From then on every SoT write (create, update, delete, including the erasure job) gets a retryable 503. This starts the write pause and a 45-second deadline for sub-steps 2 to 4.
    2. **Drain** the MySQL outbox to zero, and verify with a comparison of the rows touched since the last full pass.
    3. **Set the Postgres sequence** to `greatest(MySQL max(id) read from the primary, Postgres max(id)) + 1000`.
    4. **Open the Postgres fence.**
    5. **Set the flags** `users.sot=pg` and `users.mirror=both`.
  - **Effects after the flags change:**
    - A write commits to Postgres first, with an outbox row in the same transaction, then makes a best-effort copy to MySQL. The drainer reads the Postgres primary and writes to MySQL with the version rule and tombstones.
    - Instances still holding the old flag hit the closed MySQL fence and return 503. They pick up the new flag within 30 seconds.
    - Creates use the Postgres identity sequence.
  - **Pause length:** normally the drain (about 10 seconds) plus up to 30 seconds of flag refresh. The worst case is the 45-second deadline plus 30 seconds of refresh, which is 75 seconds, under the 90-second limit. Reads are unaffected.
  - **State:** the fence rows, the flags and `switch_state`.
  - **If it fails:**
    - Drain or verification not finished by the 45-second deadline: reopen the MySQL fence. Nothing has been written to Postgres as SoT, so this is a clean abort.
    - Script crash before the Postgres fence opens: a watchdog reopens the MySQL fence after 60 seconds.
    - Crash after that point: resume forward from `switch_state`. A resumed switch ends with the Postgres fence open.

### Phase E: Soak with rollback available

- [ ] **10. Soak for at least 14 days.**
  - **Starts:** step 9 completes. The 14-day clock starts there.
  - **Changes:** nothing. The reverse mirror keeps MySQL current. The comparison reruns daily in both directions. "MySQL behind" is tolerated only while the Postgres outbox has pending rows.
  - **State:** the Postgres outbox, plus tombstones on both sides.
  - **If it fails:** a MySQL outage only grows the Postgres outbox. Postgres writes continue and nothing is lost.

- [ ] **10R. Rollback (any time before step 11).**
  - **Starts:** a manual script launch. It is the switch run in the opposite direction, and a second write pause, with the same 45-second deadline and 75-second worst case.
  - **Changes**, in order:
    1. Close the Postgres fence (writes get 503).
    2. Drain the Postgres outbox to zero.
    3. Run `ALTER TABLE users AUTO_INCREMENT = max(id) + 1000`.
    4. Open the MySQL fence.
    5. Set `users.sot=mysql` and `users.mirror=both`, so Postgres is the follower again.
  - **Why no write is lost:** every write already reached MySQL through the reverse mirror, and the drain in sub-step 2 finishes whatever was pending. Deletes use tombstones, so erased users stay erased.
  - **State:** the fence rows, the flags and `switch_state`.
  - **If it fails:**
    - MySQL unreachable, so the drain cannot finish: abort and reopen the Postgres fence. Writes continue on Postgres.
    - Deadline passed: abort the same way.

### Phase F: Retire MySQL

- [ ] **11. Stop mirroring writes.**
  - **Starts:** all of these hold:
    - at least 14 days since step 9
    - no rollback is wanted
    - the Postgres outbox is empty
    - the final comparison reports 0
  - **Changes:** set `users.mirror=deletes_only`. Creates and updates go to Postgres only. Deletes are still copied to MySQL so erased users do not linger in the stale table. This is the point of no return for rollback.
  - **State:** the flag.
  - **If it fails:** set `mirror=both` right away. MySQL misses any create or update made while the flag was `deletes_only`, so first check that the outbox is empty. If unmirrored writes already happened, MySQL is stale and rollback is no longer safe.

- [ ] **12. Archive MySQL, remove the code, then drop the table.**
  - **Starts:** step 11 has run, then a deploy follows.
  - **Changes**, in order:
    1. Take a final dump of MySQL `users`. Give it a short retention, because it holds data that the erasure job no longer purges.
    2. Deploy code with the MySQL paths, outbox and fences removed.
    3. After 7 days with no connections to the table, drop MySQL `users` and its outbox, tombstone and fence tables.
  - **State:** the dump.
  - **If it fails:** roll back the deploy. The MySQL table is untouched until sub-step 3, which is the only irreversible action.
