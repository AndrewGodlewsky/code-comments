# Migrate `users` from MySQL 8 to Postgres 16

## What this is

Today every read and write of `users` goes through `UserRepository`, which writes only to MySQL. This plan moves the table to Postgres 16 without downtime. MySQL stays the source of truth while every write is also copied to Postgres. A backfill copies the existing rows. A full comparison must find zero mismatches before reads move to Postgres. Then Postgres becomes the source of truth in one planned switch. MySQL keeps receiving copies for 14 days, so we can roll back. Only after that is MySQL `users` dropped.

## Terms

- **Source**: the store that decides truth for reads and writes.
- **Shadow**: the other store. It is kept in sync by copying.
- **Version**: the `version` column. It starts at 1 and goes up by 1 on every update.
- **Outbox**: a table in the source store. It has one row per user, written in the same transaction as each user write. Its `seq` goes up on every write. A row is removed only after the shadow has the same `seq`.
- **Tombstone**: a record that a user was erased. It holds no personal data. It stops an erased user from being copied back.
- **Copy rule**: the only way a row is written into the shadow. See "How copying works".
- **Pause**: writes get a retryable 503. Reads continue.

## How copying works

The copy rule is used by dual writes, the repair sweeper, the backfill and the comparison repair.

Copy rule, in one transaction on the shadow:

1. Take `pg_advisory_xact_lock(id)` on the user id.
2. If a tombstone exists for the id, do nothing.
3. Otherwise run `INSERT ... ON CONFLICT (id) DO UPDATE ... WHERE users.version < EXCLUDED.version`.

The conflict target is `id` only. A unique-email clash raises an error, which is retried. It is never dropped.

Repair sweeper: runs on every worker, every few seconds. It takes up to 500 outbox rows with `FOR UPDATE SKIP LOCKED`. For each row, it reads the current row and `seq` from the source primary, or treats the user as erased if the row is gone. It applies the copy rule to the shadow. It deletes the outbox row only if `seq` still matches. It drains the outbox of whichever store is the source at the time. Retry backoff is capped at 5 minutes. Rows are never dropped. The outbox holds one row per user, so its size is bounded by the number of users.

Erasure: the erasure job records each request in the MySQL table `erasure_requests` and works through it until done. It does not use `jobs:dead`. Each erasure deletes the user row and writes an outbox row of kind `erase`. An erasure is complete only when the shadow has a tombstone and no user row. An audit checks this.

Ids: before the switch, MySQL assigns ids. After step 7, Postgres assigns ids from its identity sequence. Ids are never reused, including tombstoned ids. MySQL receives the same ids explicitly in step 8.

## Rollout steps

Do the steps in order. Each step says what starts it, what it changes, where its state lives, and what happens if it fails.

- [ ] **0. Deploy the migration layer with every switch off**
  - Starts: a normal deploy.
  - Changes: no user-visible change. `UserRepository` sends every create, update and delete through the migration layer.
    - MySQL, new tables: `users_sync_outbox` (`user_id` primary key, `seq`, `kind` upsert or erase, `attempts`, `enqueued_at`, `last_error`), `user_tombstones` (`id`, `erased_at`), `user_sync_locks` (one row per id, for locking), and `erasure_requests`.
    - Postgres `pg-core`, new tables: `users` (`id` BIGINT `GENERATED BY DEFAULT AS IDENTITY`, `email` UNIQUE, `name`, `plan`, `version` INT, `updated_at` TIMESTAMP(3)), `user_tombstones`, `users_sync_outbox`, and `migration_state` (`name` primary key, `last_id`, `updated_at`, plus checkpoints and the switch timestamp).
    - Flags, all off by default: `users_write_state` = `mysql`, `users_shadow_writes` = false, `users_read_pg_pct` = 0, `users_backfill` = false.
    - The repair sweeper starts on every worker. It does nothing while the outbox is empty.
    - Lint: `no-raw-users-sql` allows SQL on `users` only inside the migration module.
    - Check before step 1: confirm that `app_flag_value` exports the value of the string flag `users_write_state`.
  - State: the new schemas and the flag store. No existing `users` data changes.
  - If it fails: roll back the deploy. The new tables are additive and unused.

- [ ] **1. Turn on dual writes and the repair sweeper**
  - Starts: flag `users_shadow_writes` = true, set once step 0 is live on every instance.
  - Changes, for each create, update or delete:
    1. Check the flag just before the transaction opens.
    2. In one MySQL transaction, with a 3 s hard timeout, do the write, upsert the user's outbox row with `seq` + 1, and read that outbox row back.
    3. Commit.
    4. Copy the row to Postgres with the copy rule, with a 300 ms timeout. Catch all exceptions.
    5. If the copy succeeds, delete the outbox row only if its `seq` still matches.
    6. The request succeeds once MySQL has committed.
  - State: MySQL outbox and tombstones; Postgres rows.
  - Alerts: outbox depth, and age of the oldest row.
  - If Postgres fails: the request still succeeds. The outbox keeps the user, and the sweeper retries until Postgres recovers.
  - If MySQL fails: a normal write failure, because MySQL is the source.
  - If the flag is turned off: writes stop shadowing. The sweeper still drains what is pending.

- [ ] **2. Confirm every instance is dual-writing**
  - Starts: step 1's flag change.
  - Check: `app_flag_value{flag="users_shadow_writes"}` is true on every instance, so the count matches the instance count. Every instance runs the step 0 build. Hold for one full 30 s refresh plus one scrape interval.
  - Changes: none.
  - State: none.
  - If it fails: after 5 minutes, investigate the lagging instances. Do not start the backfill.

- [ ] **3. Run the backfill**
  - Starts: step 2 holds, and `users_backfill` = true. It runs as a long-lived worker loop, not as a Redis job, so the 5-retry cap does not apply.
  - Changes, on each loop:
    1. Read the cursor `migration_state.backfill.last_id` (default 0) from Postgres.
    2. Check replica lag with a direct query, the same source that feeds `mysql_replica_lag_seconds`. If lag is above 5 s or unknown, sleep 1 s and check again. Do not read a batch.
    3. Read up to 2,000 rows from the replica with `WHERE id > cursor ORDER BY id LIMIT 2000`.
    4. In one Postgres transaction, apply the copy rule to each row in id order, which avoids deadlocks. Set `backfill.last_id` to the last id read. Commit.
  - Completion: when the replica returns no rows after the cursor, set `backfill.complete_at`. The loop stops when the flag is off or `users_write_state` is no longer `mysql`.
  - State: `migration_state` in Postgres.
  - If the loop crashes: an uncommitted batch rolls back, and the loop resumes from the committed cursor. Rows and cursor commit together, so no batch is skipped or half-applied.
  - Stale replica reads are safe. The version rule stops old data from overwriting new data. Rows changed after step 2 reach Postgres through dual writes.
  - If Postgres fails: back off and retry. Requests are not affected. The migration connection pool is capped (for example, 5 connections) so it cannot starve request traffic.

- [ ] **4. Compare until zero mismatches**
  - Starts: `backfill.complete_at` is set, and the outbox is nearly empty.
  - Changes: no data changes, except repair rows added to the outbox.
    1. Split the id space into ranges of 10,000.
    2. For each range, compare fingerprints from the replica and from Postgres: `(id, version, hash of all columns)`. Also compare the tombstone id sets and the row counts.
    3. A mismatch counts only if rechecking that id on both primaries still differs and the id has no outbox row. Repair each real mismatch with an outbox upsert.
  - Done when: one full pass, started after the last repair, finds zero mismatches across rows and tombstones.
  - State: range checkpoints in `migration_state`. The pass can resume.
  - If a non-zero result appears: it is repaired and the pass repeats. If the same kind of mismatch keeps recurring, investigate it as a bug before continuing.
  - If the compare crashes: resume from its checkpoint.

- [ ] **5. Move reads to Postgres in steps**
  - Starts: step 4 passes with zero mismatches. Ramp `users_read_pg_pct` through 1, 10, 50 and 100. Hold each step for at least 1 hour. Check the error rate, the fallback count, p99 latency and the sampled comparison. The bucket is keyed by user id, so each user always gets the same answer.
  - Changes: reads only.
    - While MySQL is the source, read Postgres for bucketed users. On a Postgres error or a miss, read the MySQL replica as today and count the fallback.
    - After the source switch in step 7, reads follow the source. A Postgres miss is a miss, with no MySQL fallback. This stops a pending MySQL-side erasure from returning an erased user.
    - Ongoing: a sampled comparison of 0.1% of ranges per hour.
  - State: none new.
  - If it fails: set the percentage back. The change reaches every instance within 30 s. No data changes.

- [ ] **6. Hold reads at 100% on Postgres for 3 days**
  - Starts: `users_read_pg_pct` = 100, confirmed by metric on every instance.
  - Clock: starts when the last instance reports 100. Any drop below 100, any fallback, or any mismatch in the sampled comparison resets the clock.
  - Done when: 72 hours pass with clean metrics.
  - State: the clock start in `migration_state`.
  - If it fails: the clock resets. A mismatch also sends you back to step 4.

- [ ] **7. Planned switch: Postgres becomes the source of truth**
  - Starts: step 6 is done, the latest step 4 pass is clean, the outbox is empty, Postgres is healthy, and an operator is on call. Every instance must be pausable during the window.
  - Changes, in order:
    - a. Set `users_write_state` = `paused`. Within 30 s, every instance returns a retryable 503 for writes. Reads continue. Erasure work waits.
    - b. Wait 35 s. Check the metric: every instance reports `paused`. If one does not, set `mysql`, abort, and remove that instance from rotation.
    - c. Barrier, at most 15 s: wait until the MySQL outbox is empty, so every write committed before the pause has reached Postgres. If it is not empty within 15 s, set `mysql` and abort.
    - d. Under the pause, set the Postgres identity sequence to `max(MySQL max id, Postgres max id) + 1`. Postgres identity does not advance on explicit-id inserts, so this step is required.
    - e. Set `users_write_state` = `postgres`. Each instance opens writes when it sees the new value, within 30 s.
  - Pause per instance: at most 35 + 15 + 30 = 80 s, under the 90 s limit. A write that began before the pause can commit at most 3 s after an instance sees the pause, which the 35 s wait covers.
  - State: a dated `switch_pg_source_at` in `migration_state`. It starts the 14-day clock.
  - If it fails before e: MySQL is still the source. Only the pause and the outbox drain changed.
  - If it fails after e: do not roll back automatically. Use step 9.

- [ ] **8. Shadow to MySQL, and hold for 14 days**
  - Starts: step 7e.
  - Changes:
    - Writes commit to Postgres, with the Postgres outbox in the same transaction. The sweeper then copies them to the MySQL shadow with the copy rule. The MySQL side locks with `SELECT ... FOR SHARE` on `user_tombstones` and `SELECT ... FOR UPDATE` on the user row. Do not use `ON DUPLICATE KEY UPDATE`, because it would also match a unique-email clash.
    - Erasure writes a Postgres tombstone and deletes the row. The MySQL shadow is erased through the outbox.
    - Run the step 4 comparison in reverse, regularly.
  - Clock: 14 days from `switch_pg_source_at`. Any re-switch restarts it.
  - State: Postgres outbox; MySQL shadow.
  - If MySQL is unreachable: writes still succeed on Postgres, and the outbox grows. A rollback is blocked until the outbox drains.
  - If Postgres is unreachable: writes fail, because Postgres is the source. Treat this as an incident, and consider step 9.

- [ ] **9. Roll back to MySQL as the source (possible until step 10)**
  - Starts: an incident decision, or a failed Postgres source. A rollback is possible only while the outbox can drain.
  - Changes: the same as step 7, with `mysql` as the target.
    - a. Set `paused`. Wait 35 s. Confirm by metric.
    - b. Barrier: drain the Postgres outbox into MySQL.
    - c. Check that the MySQL AUTO_INCREMENT is greater than the max id in Postgres. InnoDB advances the counter on explicit inserts, but verify it anyway.
    - d. Set `users_write_state` = `mysql`.
  - Keep `users_shadow_writes` = true, so MySQL-to-Postgres dual writes continue.
  - Pause per instance: at most 80 s.
  - State: as in step 8.
  - If the barrier times out because MySQL is unreachable: do not roll back. Stay on Postgres as the source. No write is lost, because every write is in Postgres.
  - Re-switch requires step 4 (a zero-mismatch pass), then step 6 (the 3-day hold), then step 7 again.

- [ ] **10. Postgres-only writes (point of no return)**
  - Starts: 14 days after `switch_pg_source_at`, and all of these hold: the latest reverse comparison is clean, the MySQL outbox is empty, a snapshot of the MySQL `users` table is exported and kept, and a go decision is recorded.
  - Changes: `users_shadow_writes` = false. MySQL is no longer written. The rollback procedure is removed from the runbook. No pause is needed, because the source does not change.
  - State: none new.
  - If it fails: if the flag applies only partly, instances that still shadow-write to MySQL do so harmlessly. Set the flag again. No data is lost.

- [ ] **11. Retire MySQL `users`**
  - Starts: step 10, and an inventory of every other reader of `users`. Reporting jobs share the replica and may query it directly. Repoint them to Postgres first.
  - Changes: after the snapshot retention period, drop MySQL `users`, `users_sync_outbox` and `user_tombstones`. Remove the migration layer, the flags, the lint exception and every MySQL read of `users`.
  - Ordering: drop only after the readers are repointed and the retention period has passed.
  - State: the snapshot, which is the only way back.
  - If it fails: a reader that still queries MySQL fails visibly. The only way back is the snapshot, so do not drop anything until the inventory is verified.

## Open questions

- Does `app_flag_value` export string flags? If it does not, replace `users_write_state` with two booleans and keep the ordering rules in step 7 (see step 0).
- How long is the MySQL snapshot kept before step 11? The plan does not set this period.
