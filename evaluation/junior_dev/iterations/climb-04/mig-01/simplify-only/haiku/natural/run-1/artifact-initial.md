# Migrate `users` from MySQL 8 to Postgres 16

Terms: the **source** is the store that decides truth for reads and writes. The **shadow** is the other store. The **outbox** is a table in the source store, written in the same transaction as each user write. It holds one row per user with a `seq` that increments on every write. A row is removed only after the shadow has the matching `seq`.

- [ ] **0. Deploy the migration layer with every switch off**
  - Starts: a normal deploy of the release that contains the migration layer.
  - Changes: no user-visible change. `UserRepository` routes every create, update and delete through the migration layer. Schema additions:
    - MySQL: `users_sync_outbox` (`user_id` PK, `seq`, `kind` upsert|erase, `attempts`, `enqueued_at`, `last_error`), `user_tombstones` (`id` PK, `erased_at`, no personal data), and `user_sync_locks` (one row per id, used for locking).
    - Postgres `pg-core`: `users` (`id` BIGINT `GENERATED BY DEFAULT AS IDENTITY`, `email` UNIQUE, `name`, `plan`, `version` INT, `updated_at` TIMESTAMP(3)), `user_tombstones`, `users_sync_outbox`, and `migration_state` (`name` PK, `last_id`, `updated_at`, plus checkpoints and the switch timestamp).
  - Flags, all default off: `users_write_state` = `mysql`, `users_shadow_writes` = false, `users_read_pg_pct` = 0, `users_backfill` = false.
  - Start the repair sweeper (see step 1) on every worker. It does nothing while the outbox is empty.
  - Lint: `no-raw-users-sql` allows SQL on `users` only inside the migration module.
  - Check before step 1: confirm that `app_flag_value` exports the value of the string flag. If it cannot, replace `users_write_state` with two booleans and keep the same ordering rules in step 7.
  - State: the two schemas and the flag store. Nothing in the existing `users` data changes.
  - If it fails: roll back the deploy. The new tables are additive and unused.

- [ ] **1. Turn on dual writes and the repair sweeper**
  - Starts: flag `users_shadow_writes` = true, set after step 0 is live on every instance.
  - Changes, per write (create, update or delete):
    - One MySQL transaction does the write, upserts the user's outbox row with `seq` + 1, and reads the row back inside the same transaction. The transaction has a 3 s hard timeout, and the flag is checked just before it opens.
    - After commit, the request copies that row to Postgres with a 300 ms timeout. All exceptions are caught.
    - If the copy succeeds, the outbox row is deleted only if its `seq` still matches.
    - The request succeeds once MySQL has committed.
  - Copy rule (used by every copy: dual write, sweeper, backfill, compare repair). One Postgres transaction:
    - Take `pg_advisory_xact_lock(id)`.
    - If a tombstone exists for the id, do nothing.
    - Otherwise `INSERT ... ON CONFLICT (id) DO UPDATE ... WHERE users.version < EXCLUDED.version`.
    - The conflict target is `id` only. A unique-email clash raises an error that is retried, not dropped.
  - Erasure: the erasure job records each request in a MySQL table, `erasure_requests`, and works through it until done. It does not depend on `jobs:dead`. Each erasure does a MySQL delete with an outbox row of kind `erase`. The erasure is complete only when Postgres has a tombstone and no user row, which an audit checks.
  - Repair sweeper: on every worker, every few seconds, take up to 500 outbox rows with `FOR UPDATE SKIP LOCKED`. For each, read the current row and `seq` from the MySQL primary (or treat it as erased), apply the copy rule to Postgres, and delete the outbox row if `seq` matches. Retry backoff is capped at 5 minutes. Rows are never dropped. The outbox is keyed by user, so its size is bounded by the number of distinct users.
  - State: MySQL outbox and tombstones; Postgres rows.
  - Alerts: outbox depth, and age of the oldest row.
  - If Postgres fails: the request still succeeds, the outbox keeps the user, and the sweeper retries until Postgres recovers.
  - If MySQL fails: a normal write failure, since MySQL is the source.
  - If the flag is turned off: writes stop shadowing, and the sweeper still drains what is pending.

- [ ] **2. Confirm every instance is dual-writing**
  - Starts: step 1's flag change.
  - Check: `app_flag_value{flag="users_shadow_writes"}` is true on every instance (the count matches the instance count), and every instance runs the step 0 build. Hold for one full 30 s refresh plus a scrape interval.
  - Changes: nothing.
  - If it fails: after 5 minutes, investigate the lagging instances. Do not start backfill.

- [ ] **3. Run the backfill**
  - Starts: step 2 holds, and `users_backfill` = true. It runs as a long-lived worker loop, not as a Redis job, so the 5-retry cap does not apply.
  - Each loop:
    - Read the cursor `migration_state.backfill.last_id` (default 0) from Postgres.
    - Check replica lag with a direct query, the same source that feeds `mysql_replica_lag_seconds`. If lag is above 5 s, or unknown, sleep 1 s and check again. Do not read a batch.
    - Read up to 2,000 rows from the replica with `WHERE id > cursor ORDER BY id LIMIT 2000`.
    - In one Postgres transaction, apply the copy rule to each row in id order (this avoids deadlocks) and set `backfill.last_id` to the last id read. Then commit.
  - Crash recovery: an uncommitted batch rolls back, and the loop restarts from the committed cursor. Rows and cursor commit together, so no batch is skipped or half-applied.
  - Completion: when the replica returns no rows after the cursor, set `backfill.complete_at`. The loop stops when the flag is off or `users_write_state` is no longer `mysql`.
  - Stale replica reads are safe. The version rule stops old data from overwriting new data. Rows changed after step 2 reach Postgres through dual writes.
  - State: `migration_state` in Postgres.
  - If Postgres fails: back off and retry. Requests are not affected. The migration connection pool is capped (for example, 5 connections) so it cannot starve request traffic.

- [ ] **4. Full comparison until zero mismatches**
  - Starts: `backfill.complete_at` is set, and the outbox is nearly empty.
  - Changes: no data changes except repair rows added to the outbox.
    - Split the id space into ranges of 10,000.
    - For each range, compare fingerprints from the replica and from Postgres: `(id, version, hash of all columns)`. Also compare the tombstone id sets, and the count of Postgres rows against MySQL rows.
    - A mismatch counts only if rechecking that id on both primaries still differs, and the id has no outbox row. Real mismatches are repaired by an outbox upsert, and the pass repeats.
  - Done when: one full pass, started after the last repair, finds zero mismatches across rows and tombstones.
  - State: range checkpoints in `migration_state`. The pass can resume.
  - If it fails: a non-zero result is repaired and the pass repeats. Investigate a pattern that keeps recurring as a bug before continuing. If the compare crashes, resume from its checkpoint.

- [ ] **5. Move reads to Postgres in steps**
  - Starts: step 4 passes with zero mismatches. Ramp `users_read_pg_pct` through 1, 10, 50 and 100. Hold each step at least one hour and check error rate, fallback count, p99 latency and the sampled comparison. The percentage bucket is keyed by user id, so each user always gets the same answer.
  - Read rule while MySQL is the source:
    - Read Postgres for bucketed users.
    - On a Postgres error or a miss, read the MySQL replica as today, and count the fallback.
  - Read rule after the source switch: reads follow the source. A Postgres miss is a miss, with no MySQL fallback. This keeps a pending MySQL-side erasure from returning an erased user.
  - Ongoing: a sampled comparison of 0.1% of ranges per hour.
  - Changes: reads only.
  - If it fails: set the percentage back. The change reaches every instance within 30 s. No data changes.

- [ ] **6. Hold reads at 100% on Postgres for at least 3 days**
  - Starts: `users_read_pg_pct` = 100, confirmed by metric on every instance.
  - Clock: starts when the last instance reports 100. Any drop below 100, any fallback, or any mismatch in the sampled comparison resets the clock. A mismatch also sends you back to step 4.
  - Done when: 72 hours pass with clean metrics.
  - State: the clock start in `migration_state`.

- [ ] **7. Planned switch: Postgres becomes the source of truth**
  - Starts: step 6 is done, the latest step 4 pass is clean, the outbox is empty, Postgres is healthy, and an operator is on call. The window is the one in which every instance can be paused.
  - Procedure:
    - a. Set `users_write_state` = `paused`. Within 30 s, every instance returns a retryable 503 for writes. Reads continue. Erasure work waits.
    - b. Wait 35 s. Check the metric: every instance reports `paused`. If any instance does not, set `mysql`, abort, and remove the stale instance from rotation.
    - c. Barrier, at most 15 s: wait until the MySQL outbox is empty, so every write committed before the pause has reached Postgres. If it is not empty within 15 s, set `mysql`, abort.
    - d. Under the pause, set the Postgres identity sequence to `max(MySQL max id, Postgres max id) + 1`. Postgres identity does not advance on explicit-id inserts, so this step is required.
    - e. Set `users_write_state` = `postgres`. Each instance opens writes when it sees the new value, within 30 s.
  - Per-instance pause: at most 35 + 15 + 30 = 80 s, under the 90 s limit. A write that began before the pause can commit at most 3 s after an instance sees the pause, which the 35 s wait covers.
  - Id assignment after step e: creates use the Postgres identity. Ids are never reused, including tombstoned ids. MySQL receives the same ids explicitly in step 8.
  - State: a dated `switch_pg_source_at` in `migration_state`, which starts the 14-day clock.
  - If it fails before step e: MySQL is still the source. The only changes are the pause and the outbox drain. If it fails after step e, do not roll back automatically. Use step 9.

- [ ] **8. Shadow to MySQL, and hold for 14 days**
  - Starts: step 7e.
  - Changes:
    - Writes commit to Postgres, with the Postgres outbox in the same transaction. They are then copied to the MySQL shadow with the same copy rule. The MySQL side locks with `SELECT ... FOR SHARE` on `user_tombstones` plus `SELECT ... FOR UPDATE` on the user row. Do not use `ON DUPLICATE KEY UPDATE`, because it would also match a unique-email clash.
    - Erasure writes a Postgres tombstone and deletes the row. The MySQL shadow is erased through the outbox.
    - Run the same comparison as step 4 in reverse, regularly.
  - Clock: 14 days from `switch_pg_source_at`. Any re-switch restarts it.
  - State: Postgres outbox; MySQL shadow.
  - If MySQL is unreachable: writes still succeed on Postgres, and the outbox grows. A rollback is blocked until the outbox drains.
  - If Postgres is unreachable: writes fail, because Postgres is the source. Treat this as an incident and consider step 9.

- [ ] **9. Roll back to MySQL as the source (available until step 10)**
  - Starts: an incident decision, or a failed Postgres source. Only possible when the outbox can drain.
  - Procedure: the same as step 7, with `mysql` as the target.
    - Set `paused`. Wait 35 s. Confirm by metric.
    - Barrier: drain the Postgres outbox into MySQL.
    - Check that the MySQL AUTO_INCREMENT is greater than the max id in Postgres. InnoDB advances the counter on explicit inserts, but verify it.
    - Set `users_write_state` = `mysql`.
  - Keep `users_shadow_writes` = true, so MySQL-to-Postgres dual writes continue.
  - Per-instance pause: at most 80 s.
  - If the barrier times out (MySQL is unreachable): do not roll back. Stay on Postgres as the source. No write is lost, because every write is in Postgres.
  - Re-switch requires step 4 (a zero-mismatch pass), then step 6 (the 3-day hold), then step 7 again.

- [ ] **10. Postgres-only writes (point of no return)**
  - Starts: 14 days after `switch_pg_source_at`, the latest reverse comparison is clean, the MySQL outbox is empty, a snapshot of the MySQL `users` table is exported and kept, and a go decision is recorded.
  - Changes: `users_shadow_writes` = false. MySQL is no longer written. The rollback procedure is removed from the runbook. No pause is needed, because the source does not change.
  - If it fails: if the flag applies only partly, instances that still shadow write to MySQL harmlessly. Set the flag again. No data is lost.

- [ ] **11. Retire MySQL `users`**
  - Starts: step 10, plus an inventory of every other reader of `users`. Reporting jobs share the replica and may query it directly. Repoint them to Postgres first.
  - Changes: drop MySQL `users`, `users_sync_outbox` and `user_tombstones`. Remove the migration layer, the flags, the lint exception and every MySQL read of `users`.
  - Ordering: drop only after the readers are repointed and the snapshot retention period has passed.
  - If it fails: a reader that still queries MySQL fails visibly. The only way back is the snapshot, so do not drop until the inventory is verified.
