# Plan: move `users` from MySQL 8 to Postgres 16 with no downtime

All of the logic lives in `UserRepository`. Instances are coordinated by the existing flags, with a database-level fence for the source-of-truth switch.

## Design decisions

**Flags**
- `users.write_mode` is a string flag with four values:
  - `mysql`: writes go to MySQL only.
  - `dual`: MySQL is the source of truth and Postgres is the mirror.
  - `dual_pg`: Postgres is the source of truth and MySQL is the mirror.
  - `pg`: writes go to Postgres only.
- `users.read_pg_pct` is a percentage flag. It buckets reads by user id with `flags.enabled_for`.

**Repair is a durable outbox, not the job queue.**
- `jobs` needs Redis, `enqueue` can raise, and dead-lettered jobs are never processed. It cannot meet "fixed automatically".
- Every write inserts a row into `users_sync_outbox(seq, user_id, enqueued_at)` in the same transaction as the write.
- After commit, the request makes one inline attempt at the mirror, with a 300 ms timeout.
  - On success it deletes its outbox row.
  - On failure it ignores the error, and the outbox row stays.
- A separate `sync-drainer` process polls the outbox with `FOR UPDATE SKIP LOCKED`, so many drainers can run.
  - For each `user_id` it reads the current row from the source-of-truth primary (never a replica) and applies it to the mirror.
  - If the row is gone from the source, it applies a delete.
  - It retries forever with backoff and deletes the outbox row only on success.
  - Applies are idempotent.
- A circuit breaker skips inline attempts for 10 s after a mirror failure, so a Postgres outage does not add latency to requests.
- Alerts:
  - Page if the oldest outbox row is older than 60 s.
  - Page if the outbox depth keeps growing.

**One apply rule for every copy.** It covers dual write, backfill, repair and reverse sync.
- One statement or transaction inserts the full row.
- It is skipped if the id is in `users_erased` (the tombstone table).
- `ON CONFLICT (id) DO UPDATE ... WHERE users.version < EXCLUDED.version` makes it insert-if-missing or replace-if-lower. Equal versions are never replaced.
- Create and update `SELECT` the committed row inside the transaction. The mirror therefore gets an upsert of the full row, not a bare `UPDATE`.

**Deletes**
- A delete does three things, in this order:
  1. Best effort, it writes the tombstone `users_erased(id)` to the mirror first. A failure here is ignored.
  2. In one source transaction it deletes the row and inserts an outbox row.
  3. It then deletes the row in the mirror inside the same transaction that writes the tombstone, so inline apply and repair always do both.
- Tombstones are never removed. Ids are never reused.
- Backfill re-reads each batch's rows from the primary and skips ids that are missing there or have a pending outbox row.
- The only window in which an erased row could be re-inserted is when Postgres failed twice (the tombstone write and the inline delete) and a backfill batch lands in between. The drainer closes that window within seconds, and the alert above covers it.

**Switch coordination uses a database fence, not only flags.** Flags are cached for up to 30 s, so instances can disagree.
- Each database has a one-row table `users_authority(holder)`.
- Every write transaction starts with `SELECT holder ... FOR SHARE`. If `holder` is not the database that instance's mode expects to write first, the transaction aborts and the caller gets a retryable 503 with `Retry-After`.
- The switch does `UPDATE users_authority SET holder = ...`. That takes an exclusive lock, which waits for in-flight writes and blocks new ones.
- Once the UPDATE commits, no instance can write the old source of truth, whatever its cached flag says.
- Reads are never fenced.

**Where state lives**
- Backfill cursor, comparison results and switch timestamps live in a Postgres table `migration_state`.
- The cursor is updated in the same Postgres transaction as the batch it covers. A batch is either fully applied with the cursor moved, or neither.

**New ids after the switch**
- Postgres `users.id` is `BIGINT GENERATED BY DEFAULT AS IDENTITY`. Copies carry explicit ids.
- During the switch pause, with writes fenced and the outbox drained, set the sequence with `setval(seq, GREATEST(MySQL AUTO_INCREMENT, max(pg id)) + 1000)`.
- On rollback, MySQL accepts explicit ids from reverse sync, and InnoDB moves its AUTO_INCREMENT past them. Every switch to Postgres repeats the `setval`.

## Checklist

- [ ] **0. Rehearse and set limits (staging)**
  - **Starts when:** before any production change.
  - **What it does:**
    - Run the full plan against a staging copy.
    - Measure the switch pause and the rollback pause. Both must come in well under 90 s.
    - Run a reverse-sync (rollback) rehearsal.
  - **State:** none.
  - **If it fails:** fix the plan or code, and do not proceed.

- [ ] **1. Create the schema (additive only)**
  - **Starts when:** a reviewed migration is run by hand.
  - **What it changes:**
    - Postgres: `users` with the same columns, unique `email`, and the identity id; `users_erased`; `users_sync_outbox`; `users_authority` with `holder='mysql'`; `migration_state`.
    - MySQL: `users_sync_outbox`, `users_authority` with `holder='mysql'`, and `users_erased`.
    - The MySQL `users` table is not touched.
  - **State:** the new tables.
  - **If it fails:** every DDL statement is idempotent (`IF NOT EXISTS`), so fix it and re-run. Nothing reads these tables yet.

- [ ] **2. Deploy the new repository and the `sync-drainer`, with `users.write_mode=mysql`**
  - **Starts when:** a normal rolling deploy.
  - **What it changes:**
    - The repository now has the authority check and all four modes.
    - In `mysql` mode, behaviour is the same as today plus the `FOR SHARE` read of the authority row.
    - The `sync-drainer` runs but is idle.
  - **Done when:** the rollout is finished, no old-build instance is running, and every instance exports `app_flag_value{flag="users.write_mode"}`.
  - **State:** none new.
  - **If it fails:** roll back the deploy. Behaviour is unchanged, so this is safe.

- [ ] **3. Turn on dual writes: set `users.write_mode=dual`**
  - **Starts when:** step 2 is done and the Postgres inline success rate is proven in staging.
  - **What it changes:** from now on every write follows the dual-write and outbox design above.
  - **State:** the MySQL outbox is the repair state.
  - **If it fails:**
    - A Postgres failure never fails a request. It only grows the outbox.
    - Before the backfill starts, reverting the flag to `mysql` is safe: the backfill will cover everything.
    - After the backfill starts, never revert to `mysql`. Writes would stop being tracked and Postgres would drift. Fix forward instead.

- [ ] **4. Confirm every instance is dual-writing, and record the baseline**
  - **Starts when:** at least 60 s after the step 3 flag change, plus 2 minutes for requests that were already in flight.
  - **What it checks:**
    - The number of instances reporting `users.write_mode=dual` equals the number of running instances.
    - The dual-write success rate is at least 99%.
    - The oldest outbox row is under 60 s old.
  - **What it changes:** it records the primary's current `gtid_executed` (or binlog file and position if GTIDs are off) into `migration_state.backfill_baseline`.
  - **State:** `migration_state`.
  - **If it fails:** wait and re-check. If an instance is stuck on the old value, restart or remove it. Do not start the backfill until every instance is confirmed.

- [ ] **5. Backfill**
  - **Starts when:**
    - Step 4 is done.
    - The replica has applied the baseline (`WAIT_FOR_EXECUTED_GTID_SET`). Without that, the backfill could read a row version older than one written before dual writes began.
    - `mysql_replica_lag_seconds` is at most 5.
  - **What it does:**
    - One backfill process runs at a time, guarded by a Postgres advisory lock.
    - Per batch it reads at most 2,000 rows from the replica with `id > cursor ORDER BY id`.
    - It re-checks those rows on the primary and skips ids that are missing or have pending outbox rows.
    - It applies them in one Postgres transaction and sets `migration_state.backfill_cursor` to the batch's last id in that same transaction.
    - Before every batch it pauses while `mysql_replica_lag_seconds > 5`. If the metric is missing, it also pauses.
    - If a batch hits an email-uniqueness conflict (a stale holder of a recycled email), it applies the batch row by row. It sends conflicting ids to the outbox for the drainer, and the cursor still advances.
  - **State:** the cursor in Postgres.
  - **If it fails:**
    - After a crash or a Postgres error, restart. It resumes from the stored cursor, and a half-done batch is simply redone.
    - It is idempotent, so a repeated batch is harmless.
    - It is finished when a batch comes back empty. That is roughly 19,000 batches.

- [ ] **6. Full comparison pass**
  - **Starts when:** the backfill is finished and the outbox is empty.
  - **What it does:**
    - It compares by id range, using per-chunk checksums over `(id, email, name, plan, version, updated_at)` from the replica (same lag rule) and from Postgres. It then does a row-level diff of any chunk that differs.
    - It re-checks each differing row against the primary after the outbox has drained. Only a persistent difference counts as a mismatch.
    - Missing, extra, and differing rows all count. A row in Postgres but not in MySQL counts, as does an id in `users_erased` that exists in MySQL.
    - It sends each mismatched id to the outbox, which repairs it.
    - A Postgres row with a higher version than MySQL is a bug. It alerts and does not auto-fix.
  - **Done when:** a whole pass finishes with zero persistent mismatches. The result is written to `migration_state` with start and end times.
  - **State:** `migration_state`.
  - **If it fails:** repair, then run the whole pass again. Passes with mismatches do not count.

- [ ] **7. Ramp reads to Postgres**
  - **Starts when:** a zero-mismatch pass from step 6 finished within the last 24 h.
  - **What it changes:**
    - Set `users.read_pg_pct` to 1, then 10, 50 and 100, holding each level for at least an hour.
    - A Postgres read has a 200 ms timeout. On an error or a miss it falls back to the MySQL replica, so reads never fail.
  - **Advance only if:**
    - The fallback rate is under 0.1% and latency is acceptable.
    - The oldest outbox row is under 30 s old.
    - A nightly comparison pass shows no new mismatches.
  - **State:** the flag.
  - **If it fails:** lower the percentage. This is instant, within the 30 s flag refresh. Pause the ramp on any mismatch.

- [ ] **8. Soak at 100% reads for at least 3 days**
  - **Starts when:** every instance reports `users.read_pg_pct=100`. The time is stored in `migration_state`.
  - **What it checks:** nightly comparison passes stay clean, and fallbacks, outbox age and replica load stay healthy.
  - **State:** `migration_state`.
  - **If it fails:** if the percentage drops below 100, the clock resets. Fix the cause and restart the 3 days.

- [ ] **9. Pre-switch checklist**
  - **Starts when:** at least 3 days of step 8 have passed.
  - **What it checks:**
    - A new full comparison pass shows zero mismatches.
    - The outbox is empty.
    - The reverse drainer (Postgres to MySQL) is deployed and idle.
    - The rehearsed rollback works.
    - The switch is scheduled in a low-traffic window.
  - **State:** none.
  - **If it fails:** fix and repeat. Do not switch.

- [ ] **10. Switch the source of truth to Postgres (writes pause for at most 90 s)**
  - **Starts when:** an operator runs the scripted switch after step 9.
  - **Steps and time limits, measured from T0:**
    1. **T0, fence MySQL.** `UPDATE users_authority SET holder='switching'` on MySQL, with a 5 s lock timeout. When it commits, no more MySQL writes are possible and writers get 503. If it times out, nothing has changed. Retry later.
    2. **Drain.** Run the drainers hard until the MySQL outbox is empty (cap 20 s). Because writes are blocked, this ends. If the cap is exceeded, set the holder back to `mysql`, which ends the pause. Investigate and try again.
    3. **Prepare Postgres.** `setval` the identity sequence as described above. Set the Postgres `holder='pg'`. Set the MySQL `holder='pg'`.
    4. **Flip the flag** to `users.write_mode=dual_pg`.
    5. **Wait for instances.** Each instance resumes writes the moment it refreshes the flag, within 30 s. Until then it gets the 503 from the fence. Confirm via `app_flag_value`.
    6. **Remove stragglers.** At T0+60 s, take any instance that has not reported `dual_pg` out of the load balancer.
  - **Expected pause:** about 40 to 55 s, with a hard bound under 90 s.
  - **What changes afterwards:**
    - Writes commit to Postgres first. Each write inserts a Postgres outbox row, and the MySQL mirror is applied inline and then by the reverse drainer.
    - Reads stay on Postgres.
    - Erasures delete in Postgres and write a tombstone there. The reverse drainer deletes in MySQL and also writes a tombstone to MySQL `users_erased`.
  - **State:** `migration_state.switched_at` (the 14-day clock), the authority rows, and the Postgres outbox.
  - **If it fails:**
    - Before step 4, abort by setting the MySQL holder back to `mysql`.
    - After step 4, use the rollback in step 11.

- [ ] **11. Soak for at least 14 days with MySQL kept as a mirror (rollback stays available)**
  - **Starts when:** step 10 is complete.
  - **What it does:**
    - The reverse drainer keeps MySQL current from the Postgres outbox, with the same apply rule.
    - Nightly comparison passes run, and the same alerts apply.
  - **Rollback (also at most a 90 s write pause):**
    1. Fence Postgres: `UPDATE users_authority SET holder='switching'` on Postgres.
    2. Drain the Postgres outbox into MySQL until it is empty.
    3. Set the MySQL `holder='mysql'`.
    4. Flip the flag to `dual`.
    5. Wait until every instance reports `dual`.
  - **Why no write is lost:** every Postgres write has a durable outbox row, and the fence waits until the outbox is empty before MySQL takes over.
  - **State:** the Postgres outbox, the authority rows, and `migration_state`.
  - **If it fails:**
    - If MySQL is unreachable at rollback time, set the Postgres holder back to `pg` and continue on Postgres.
    - After a rollback, Postgres keeps being mirrored through the usual `dual` path. A later second switch repeats steps 9 and 10, including the `setval`.

- [ ] **12. Switch to Postgres-only writes**
  - **Starts when:** at least 14 days after `switched_at`, and the last comparison pass is clean.
  - **What it changes:**
    - The command refuses to run earlier than `switched_at` plus 14 days.
    - Check that the Postgres outbox is empty.
    - Set `users.write_mode=pg`, which stops mirroring to MySQL. No write pause is needed.
    - When every instance reports `pg`, stop the reverse drainer.
    - Revoke the app user's write grants on MySQL `users`, so any straggler fails loudly instead of silently writing.
    - Take a final MySQL dump and store it under the erasure retention rules.
  - **State:** the flag, `migration_state`, and the dump.
  - **If it fails:**
    - Flipping the flag back to `dual_pg` before the grants are revoked is still safe.
    - After that, rollback without loss is gone by design.

- [ ] **13. Retire MySQL `users`**
  - **Starts when:** after step 12, plus a quiet period (suggested 7 days).
  - **What it changes:**
    - First rename the table to `users_retired`, so that an unexpected reader fails and the change can be undone. Later `DROP` it.
    - Remove the MySQL replica reads, the MySQL code paths, the `dual`, `dual_pg` and `mysql` modes, and the authority, outbox and `users_erased` tables in MySQL. Keep `no-raw-users-sql` pointed at Postgres.
    - Remove the flags `users.write_mode` and `users.read_pg_pct`.
    - Keep the Postgres tombstones, since they stay permanently. Drop the Postgres outbox and authority tables.
  - **State:** none.
  - **If it fails:** until the `DROP`, rename `users_retired` back. After the `DROP`, restore from the step 12 dump.
