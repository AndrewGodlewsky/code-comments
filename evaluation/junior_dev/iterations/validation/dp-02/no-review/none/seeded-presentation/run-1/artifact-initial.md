# Clickstream plan

1. Replay and the swap. When someone needs to redo a day (D), usually after an enrichment fix has gone out, there's a `replay --day D` command, and the thing to know is that the prod partition only changes at the very end when the staging table `events_clean_staging_D` gets swapped in atomically (the warehouse supports single-partition replace) after a row-count check (within 1% of what's there now, otherwise it stops and a human looks), so dashboards keep reading the old day the whole time and then the new one, never a mix, and if the swap itself fails the old partition just stays and you retry the swap, and afterwards staging is dropped and the `replay:D` lock released.

2. Events/IDs: event_id (UUID from client), device_id, client ts, plus received_at which the edge endpoint stamps; day = UTC date of received_at, NOT the client ts, everywhere (partitions, archive folders, replay).

3. The dedup worker runs every minute off the topic with its own consumer group and does a set-if-absent per event in the KV store's `dedup` namespace (first one in wins) — key is event_id and value is partition+offset of that copy in the log, 8 day TTL because retries can come 7 days late plus a day of margin, and the TTL is the only thing that clears entries — if the key isn't there it's a first copy and kept, if it's there with a different offset the event's a dup and dropped, and if it's there with the exact same offset that means we're re-reading after a crash so keep it. If the seen-IDs cache is down the streaming job backs off and retries that micro-batch and does NOT let anything through unchecked, events just pile up in the log meanwhile (14 days of retention) and the ingest API keeps accepting/acking, page someone at 5 min lag.

4. Bots: open, Product hasn't decided drop vs keep with a flag; it would live in enrichment (which replay reuses); archived copies remain either way.

5. Mobile/web SDKs: batches up to 100; they hold events until a 202 (mobile has the on-device buffer, 7 days max, then discarded); timeout/429/5xx means send the same batch again, same event_ids, backoff 1s→2s→4s… capped at 5 min; anything listed as rejected in the response gets discarded and is not resent.

6. Cold copy writer (bucket sink): separate consumer group on the log, writes every accepted event including dups, untouched (with its log partition/offset), to hourly files `archive/date=<day>/hour=<HH>/`, lifecycle 90 days; commits its offset only once a file is completely written and names files by partition+offset range so a rewrite after a crash replaces rather than duplicates; if object storage is down it stops/retries while the log holds up to 14 days, alert at 15 min lag, live side unaffected (but the day marker and therefore replay of that day wait); at 02:00 UTC once it's past the previous day's last event it drops `archive/date=<day>/_COMPLETE`.

7. Ingest API: POST, valid events get received_at and get appended to the Kafka-style log keyed by device_id; 202 only after the replicated append is confirmed, response body lists rejected event_ids; malformed = missing event_id or device_id or > 32 KB, those go with a reason to the reject bucket (14 days); no state of its own; append fails/times out → 503 → whole batch retried by the client, and if the append had actually landed but the ack got lost you get dups in the log, which the dedup worker deals with.

8. Replay preconditions + job: D must be closed (≥ 02:00 UTC on D+1), `_COMPLETE` present, streaming job committed past D's last event, within the 90 days, and nobody else holding `replay:D` (set-if-absent in the KV store, but in its own `replay-locks` namespace, not the dedup one). The replay batch job takes its events only from the archive bucket for date=D — never the topic — and never reads or writes the TTL store; the only other thing it reads is read-only event_id lookups in the clean table for D-7..D-1; it runs on separate compute, so live isn't slowed and live dedup state is left alone. Dedup in replay: per event_id within D keep the earliest received_at (tie → lowest log offset), and drop any event_id that's already in the clean table for D-7..D-1 because then the first copy was on an earlier day. Enrich with the current code and write to staging. If the batch job dies, drop staging, release the lock and rerun from scratch; the warehouse events table hasn't been touched and still serves the old D.

9. Load: the consumer merges each micro-batch into events_clean on event_id (insert if new, overwrite if present), partitioned by day, THEN commits its offset; ~1–2 min latency vs the 5 min target. Load failure → no commit → retry. Crash between load and commit → re-read → same offsets in the seen-IDs cache so kept → merge overwrites, so no loss and no doubles.

10. Enrichment: geo-IP + UA parsing + enrichment_version; events that fail enrichment are loaded with empty fields + enrichment_error, not dropped.

State is in: the client buffer, the log, the archive, the reject bucket, the dedup KV namespace, the clean table, and staging + the lock (separate KV namespace) during a replay.
