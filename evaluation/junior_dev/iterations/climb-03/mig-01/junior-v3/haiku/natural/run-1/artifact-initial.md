# Move `users` from MySQL 8 to Postgres 16 without downtime

## Mechanisms

1. **Outbox in MySQL.** Every write (create, update, erase) upserts `user_sync_outbox(user_id PK, version, op)` in the same MySQL transaction as the change. The outbox is durable and commits atomically with the source of truth. `app.jobs` is not the durability layer: `enqueue` raises when Redis is down, and `jobs:dead` has no consumer. Jobs may serve only as a wake-up hint.
2. **Inline apply.** After the MySQL commit, the request tries to apply its row to Postgres with a short timeout (for example 200 ms). On success it runs a compare-and-delete on the outbox (`DELETE ... WHERE user_id = ? AND version <= applied_version`), so a newer pending write is never removed. On failure the outbox row stays, and the request still succeeds.
3. **Sweeper.** One active worker (lease in MySQL) drains the outbox. For each entry it reads the current row from the MySQL primary, copies it to Postgres under the version rule, and then compare-and-deletes the entry. Outbox depth and oldest-entry age are alerted.
4. **Version rule in SQL.** Every copy into Postgres is `INSERT ... ON CONFLICT (id) DO UPDATE ... WHERE users.version < EXCLUDED.version`. It runs only after taking the per-id advisory lock `pg_advisory_xact_lock(<namespace>, id)` and checking that no tombstone exists for the id.
5. **Tombstones and erasure.** The erasure job uses this order: (a) write the tombstone in the target store and delete any copy there, (b) delete the row in the source store, (c) record the erasure in the source's `user_erasures` table. Every copy takes the same per-id lock and checks for a tombstone, so an erased id cannot reappear once its tombstone commits. The job is idempotent and retried until all three steps succeed. Ids are never reused: InnoDB's AUTO_INCREMENT counter is persistent, and the Postgres sequence only moves forward.
6. **Fences, not flags.** Each database has a `users_control` row (`owner` in {`mysql`, `paused`, `pg`}, plus `epoch`). Every write holds `FOR SHARE` on its own database's control row for the whole transaction and fails with a retryable 503 unless that database owns writes. A switch takes an exclusive lock on the row, so it waits for in-flight writes and blocks new ones. Feature flags can be up to 30 s stale, so they never decide correctness.
7. **Routing.** Each write reads the MySQL `users_control.owner` row (a primary-key read) to choose the MySQL path (phase A) or the Postgres path (phase B). If MySQL is unreachable, the write uses the cached flag `users.write_owner`. A wrong route is rejected by the fence and retried by the client.
8. **Ids.** In phase A, ids come from MySQL AUTO_INCREMENT and are copied explicitly. The Postgres identity column is `GENERATED BY DEFAULT`. At the switch, while writes are paused, the Postgres sequence is set to `MAX(id)` from MySQL plus a margin of 10,000,000. The MySQL counter is frozen in phase B. During rollback, the MySQL AUTO_INCREMENT counter must be verified to be above the maximum id before writes reopen.
9. **Backfill progress** is a checkpoint row in MySQL (`migration_state`), not in Postgres, because the MySQL primary is the surviving source during the copy.

## State inventory

| State | Where | Purpose |
|---|---|---|
| `users_control` (owner, epoch, owner_since, mode) | MySQL and Postgres | Write fence and ownership; the one authority for correctness |
| `user_sync_outbox` (forward) | MySQL | Durable pending copies MySQL to Postgres |
| `user_sync_outbox` (reverse) | Postgres | Durable pending copies Postgres to MySQL (phase B) |
| `user_erasures` / `user_tombstones` | Each database | Erased ids; blocks copies |
| `migration_state` (backfill checkpoint, lease, read-phase timestamps, compare runs) | MySQL primary | Survives crashes; controls gates |
| Flag `users.dual_write` | Flag service | Turns inline apply on or off; the outbox is written regardless |
| Flag `users.read_source` (percent, keyed by user id) | Flag service | Read routing ramp |
| Flag `users.write_owner` | Flag service | Fallback route only |
| `app_flag_value{flag=...}` per instance | Metrics | Proves every instance has a change |
| `mysql_replica_lag_seconds`, outbox depth and age, compare mismatches | Metrics | Gates and alerts |

## Standing rules

- From Phase 0 onward, every build that writes `users` must include the outbox and the fence. Never roll back below the Phase 0 build once the backfill has started.
- Repair and comparison re-check every suspected mismatch against the MySQL primary. The replica is never the authority for a repair.
- Email matching follows MySQL's case-insensitive unique collation. Decide before backfill whether Postgres uses a unique index on `lower(email)` or `citext`, and make the comparison use the same rule.
- Store all timestamps as UTC. Map `DATETIME(3)` to `timestamp(3) without time zone` and normalise to UTC milliseconds in comparisons.
- Extend the `no-raw-users-sql` lint rule to cover `user_*` tables and the control tables.

## Steps

- [ ] **0. Create schemas and control rows.**
  - Starts: approval of this plan.
  - Changes: Postgres gets `users` (identity `GENERATED BY DEFAULT`, UTC timestamps, the email rule above), `user_tombstones`, the reverse outbox, and `users_control` (`owner=mysql`, epoch 1). MySQL gets `users_control` (`owner=mysql`, epoch 1), `user_sync_outbox`, `user_erasures`, and `migration_state`.
  - State: the DDL and the control rows.
  - If it fails: drop the new objects. No service behaviour has changed.

- [ ] **1. Deploy the full Phase 0 build to every instance.**
  - Starts: the deploy pipeline, once step 0 is done.
  - Changes: writes add the fence check, the outbox upsert (always on), and the inline apply, which stays dormant while `users.dual_write` is 0. Reads stay on MySQL. The phase B routing and reverse sweeper are shipped but dormant, because `owner=mysql`.
  - State: control rows and the flag.
  - If it fails: roll back to the previous build. This is safe only if no instance has written `users` with the new build, because the outbox would then miss those writes. Otherwise, roll forward.

- [ ] **2. Start the sweepers and verify them with dual write still off.**
  - Starts: step 1 completes on every instance.
  - Changes: the forward sweeper runs. The outbox should drain to near zero, since no inline apply runs yet.
  - State: the lease in `migration_state`, and outbox depth and age.
  - If it fails: the outbox grows. No user impact. Fix the sweeper before continuing.

- [ ] **3. Turn on dual write.**
  - Starts: step 2 is healthy, with the outbox near zero and the sweeper running.
  - Changes: flag `users.dual_write` goes from 0 to 100 in one step. Writes are now applied inline to Postgres after the MySQL commit.
  - State: the flag.
  - If it fails: set the flag back to 0. Writes keep landing in the outbox, so nothing is lost.

- [ ] **4. Gate for the backfill.**
  - Starts: this gate is checked automatically by the backfill job, and a person confirms it.
  - Conditions, all required: every instance reports Phase 0 build and `app_flag_value{flag="users.dual_write"}` = 100 for at least two minutes (two refresh cycles); no instance on an older build exists; outbox depth is below 1,000 and the oldest entry is under 60 s old; Postgres is healthy.
  - State: `migration_state.backfill_gate_at`.
  - If it fails: the gate stays closed and an alert fires. Nothing else changes.

- [ ] **5. Backfill.**
  - Starts: the gate in step 4 opens. Only one worker runs at a time, holding a lease in `migration_state` that is renewed on each batch.
  - Changes, per batch: check replica lag (`SHOW REPLICA STATUS` on the replica), and if it is above 5 s, sleep 5 s and check again. Read up to 2,000 rows from the replica with `WHERE id > last ORDER BY id LIMIT 2000`. Apply the batch in one Postgres transaction using the locks, tombstone checks, and version rule above. Commit to Postgres, then set `migration_state.last_completed_id` to the batch's maximum id in MySQL. An empty batch means the backfill is done.
  - State: `migration_state` (checkpoint, lease, counters).
  - If it fails: after a crash, the lease expires and a new worker resumes after `last_completed_id`. The batch is repeated safely because copies are idempotent. If Postgres is down, the batch retries with backoff. Users are unaffected.

- [ ] **6. Full comparison, repeated until clean.**
  - Starts: the backfill reports done.
  - Changes: compare both tables in id-range chunks of 2,000 ids, reading the replica and Postgres and pausing on replica lag the same way as the backfill. Classify differences as missing in Postgres, lower version in Postgres, higher version in Postgres (should never happen, so it alerts), field difference, or extra in Postgres. Re-check every candidate against the MySQL primary and the outbox. A run is clean when it has zero confirmed mismatches. Missing and extra rows explained by a tombstone do not count.
  - State: `migration_state` compare-run records, with start time and mismatch counts.
  - If it fails: missing and lower-version rows are repaired by the sweeper. Other classes are investigated before the run is repeated. Users are unaffected.

- [ ] **7. Move reads to Postgres in steps.**
  - Starts: a clean compare run from step 6.
  - Changes: flag `users.read_source` goes 1, 10, 50, 100 percent. The key is the user id, so each user gets a stable answer. Each step waits until every instance reports the value and 30 minutes pass with no Postgres read errors or mismatch spike. A read tries Postgres first; if Postgres errors or the row is missing, it falls back to the MySQL replica, so reads never fail.
  - State: the flag, plus `migration_state.reads_pg_since` once all instances report 100.
  - If it fails: set the flag back to 0. Writes are unaffected, and the clock resets.

- [ ] **8. Soak reads at 100% on Postgres for at least 3 days.**
  - Starts: `reads_pg_since` is recorded.
  - Changes: none. Comparison keeps running daily as a guard.
  - State: `migration_state.reads_pg_since`.
  - If it fails: any read rollback resets `reads_pg_since`, and the 3-day soak starts again.
  - Known trade-off: a Postgres read can return an older row while that user's repair is still in the outbox. The window is bounded by the outbox-age alert, which should be set to a few seconds.

- [ ] **9. Switch the source of truth to Postgres (phase B), within a 90 s write pause.**
  - Starts: all of these must hold, and the job refuses to run otherwise. `reads_pg_since` is at least 3 days ago. A clean compare run finished within the last 24 hours. Outbox depth is below 100. Postgres is healthy.
  - Changes, in order:
    1. Pre-drain: the sweeper drains the outbox until it is near zero, before any pause.
    2. Pause: in MySQL, `UPDATE users_control SET owner='paused', epoch=epoch+1 WHERE owner='mysql'`, with `lock_wait_timeout` of 5 s. In-flight writes finish first because they hold `FOR SHARE`. New writes receive 503.
    3. Drain: with writes fenced, the sweeper empties the outbox. Then run a delta check of rows with `updated_at` at or after the last clean run's start, and require zero mismatches.
    4. Commit point: set the Postgres sequence to MySQL `MAX(id)` plus 10,000,000, then set Postgres `users_control` to `owner='pg'`, with a new epoch. Before this point, abort by restoring MySQL to `owner='mysql'`. After it, always finish step 5.
    5. Set MySQL `users_control` to `owner='pg'`. Routing moves to phase B, writes resume, and the reverse sweeper starts.
  - Budget: abort at 80 s if steps 2 to 4 have not finished. Pre-drain and the lock timeout keep the in-fence work short.
  - State: both control rows, and `migration_state.pg_owner_since`.
  - If it fails: if the abort happens before the commit point, MySQL is restored and nothing changes. If MySQL is unreachable after the commit point, Postgres still accepts writes through the phase B path, and the MySQL routing row is finished later. Writes never run on both paths at once, because each path's own fence rejects it.

- [ ] **10. Phase B soak, at least 14 days.**
  - Starts: step 9 is committed.
  - Changes: a write runs its phase B path, which takes the Postgres fence lock, writes Postgres, and upserts the reverse outbox in the same Postgres transaction. The reverse sweeper applies those rows to MySQL with the version rule and tombstone checks. Reads stay on Postgres. Erasure runs in reverse order: the MySQL tombstone first, then the Postgres delete, then the MySQL delete.
  - State: the reverse outbox in Postgres, and the MySQL copy.
  - If it fails: if MySQL is down, the reverse outbox grows in Postgres and writes continue. A rollback then waits until the outbox is drained.

- [ ] **10R. Rollback (available any time before step 11).**
  - Starts: a decision to roll back.
  - Changes, in order:
    1. Move reads to MySQL with `users.read_source` = 0.
    2. Pre-drain the reverse outbox into MySQL.
    3. Pause: in Postgres, set `users_control` to `owner='paused'` under an exclusive lock, which waits for in-flight Postgres writes. Writes receive 503.
    4. Drain the reverse outbox. Run the delta check against MySQL.
    5. Verify that the MySQL AUTO_INCREMENT counter is above `MAX(id)`. If it is not, set it. This is a metadata-only change in MySQL 8.
    6. Commit point: set MySQL `users_control` to `owner='mysql'`, with a new epoch. Writes resume on the phase A path.
    7. Stop the reverse sweeper and start the forward sweeper.
  - Budget: 90 s, with the same abort rule as step 9 before the commit point.
  - State: both control rows.
  - If it fails: before the commit point, restore Postgres to `owner='pg'`. Nothing is lost, because the reverse outbox is durable.

- [ ] **11. Switch to Postgres-only writes (phase C).**
  - Starts: at least 14 days after `pg_owner_since`, no rollback planned, and the reverse outbox is empty.
  - Changes: set the Postgres `users_control.mode` from `pg_reverse` to `pg_only`, under an exclusive lock that waits for writers. Writers stop upserting the reverse outbox. Stop the reverse sweeper. No pause is needed, because the source of truth does not change. MySQL is frozen, and rollback is no longer possible.
  - State: `users_control.mode`.
  - If it fails: the system stays in phase B, and nothing else changes.

- [ ] **12. Retire the MySQL table.**
  - Starts: phase C is stable.
  - Changes: take a final MySQL snapshot and verify it. Revoke the application's MySQL access to `users`. Drop the table only after the backup is verified. The team owns the choice of how long to keep the backup.
  - State: the snapshot and its verification record.
  - If it fails: keep the table. Dropping is gated on the verified backup.

## Open decisions

- The 90 s budget is split into a 5 s fence lock timeout, an 80 s abort point, and a pre-drain that keeps the in-fence drain short. Measure the real drain time in staging before step 9.
- The sequence margin of 10,000,000 is a choice; any value above the frozen MySQL maximum works.
- Tombstones in Postgres are kept indefinitely, since they are small.
- The email collation rule in Postgres must be decided before step 0.
- Read-after-write staleness during repair is bounded by the outbox-age alert. Confirm the alert threshold.
- The backup retention period before the MySQL table is dropped.
