# Per-customer rate limiting on the public API\n\n## What this is\n\nThe API Gateway allows each customer 100 requests per minute on the Standard plan. After it resolves the API key, it adds one to the customer's counter in Redis and forwards the request only if the customer is still under the limit. Otherwise it returns 429. All of a customer's keys share one counter. If Redis errors or is slow, the gateway forwards the request anyway (fail open).\n\n## Terms\n\n- **Customer**: the owner of one or more API keys. The budget belongs to the customer.\n- **Plan**: Standard or Enterprise. The Key Service returns it with the customer ID.\n- **Window**: one clock minute, such as 12:00:00 to 12:00:59. Each window has its own counter.\n- **Counter**: the Redis key `rl:{customerId}:{windowStart}`. It holds the number of counted requests in one window. `windowStart` is the epoch second at the start of the current minute.\n- **Counted request**: a request that passed the limit check. It uses budget even if the backend then fails.\n- **Fail open**: when the counter store errors or is slow, forward the request without the limit check.\n- **OPEN**: a decision product has not made yet. Nothing ships for it until it is decided.\n\n## Sequence\n\n```mermaid\nsequenceDiagram\n    participant C as Client\n    participant G as API Gateway\n    participant K as Key Service\n    participant R as Redis counters\n    participant B as Backend service\n\n    C->>G: Request with X-Api-Key\n    alt Key not in gateway cache (5 min TTL)\n        G->>K: Resolve key\n        K-->>G: customerId and plan, or unknown\n    end\n    alt Key missing or unknown\n        G-->>C: 401 Unauthorized\n        Note over G,R: Counter store is not touched\n    else Key valid\n        alt Plan has no limit set (Enterprise, OPEN)\n            G->>B: Forward request\n            B-->>G: Response\n            G-->>C: Response, no rate-limit headers\n        else Plan limit (Standard = 100)\n            G->>R: Run check script on rl:customerId:windowStart\n            alt Error or no reply within 50 ms\n                Note over G: Fail open\n                G->>G: Emit ratelimit_store_unavailable\n                G->>B: Forward request\n                B-->>G: Response\n                G-->>C: Response, no rate-limit headers\n            else Store replied\n                R-->>G: Allowed with count, or denied with count\n                alt Denied (count already at limit)\n                    G-->>C: 429 with Retry-After in seconds\n                    Note over G,B: Not forwarded, counter unchanged\n                else Allowed (count incremented)\n                    G->>B: Forward request\n                    B-->>G: Response, any status including 500\n                    G-->>C: Response with X-RateLimit-Limit and X-RateLimit-Remaining\n                end\n            end\n        end\n    end\n```\n\n## Steps\n\n1. **Authenticate.** Read the `X-Api-Key` header and resolve it to a customer ID and plan. Use the gateway's in-memory cache (5 minutes). On a cache miss, ask the Key Service. If the key is missing or unknown, return 401 and stop. Do not read or change any counter.\n2. **Pick the limit.** Standard: 100 requests per minute. Enterprise: OPEN. Until product sets a limit, skip the check and forward the request with no rate-limit headers. Any other plan value counts as Standard, so an unknown plan is never unlimited.\n3. **Run the check script** on the counter for the current window (see below). It counts the request only if the count is under the limit. It does both in one atomic step, so two gateway instances cannot both take the last slot.\n4. **If Redis errors or does not reply within 50 ms**, fail open. Emit `ratelimit_store_unavailable` and forward the request with no `X-RateLimit-*` headers.\n5. **If the script denies the request** (the count is already at the limit), return 429 with `Retry-After`. Do not forward the request. The counter does not change. `Retry-After` = max(1, ceil(windowEnd - now)) seconds, where windowEnd = (floor(now / 60) + 1) * 60. Both values come from the gateway clock.\n6. **Otherwise forward the request** and return the backend's response, whatever its status. Add `X-RateLimit-Limit` (the plan limit) and `X-RateLimit-Remaining` (the limit minus the count after this request) only when the check ran and allowed the request.\n\n### The check script\n\n```lua\n-- KEYS[1] = counter key, ARGV[1] = limit, ARGV[2] = expiry in seconds (120)\nlocal n = tonumber(redis.call('GET', KEYS[1]) or '0')\nif n >= tonumber(ARGV[1]) then return {0, n} end   -- denied, nothing changed\nn = redis.call('INCR', KEYS[1])\nif n == 1 then redis.call('EXPIRE', KEYS[1], ARGV[2]) end  -- first request in the window sets the expiry\nreturn {1, n}                                         -- allowed, n includes this request\n```\n\nA missing key reads as 0, and the first `INCR` creates it with the value 1. Redis deletes the key 120 s after that. The 120 s is longer than the 60 s window only to cover clock skew. It does not change any count, because each request uses only the counter for its own window.\n\nInstance clocks must be kept in sync with NTP. If two instances disagree about the minute, they may use adjacent counters for a few seconds around the boundary. The error is about the size of the clock skew.\n\n## What happens when things fail\n\n| Situation | What the client gets | Budget used? |\n|---|---|---|\n| Key missing or unknown | 401 | No. No counter is touched. |\n| Key Service errors or is slow | Not defined (see Open questions) | Not defined |\n| Plan has no limit (Enterprise, OPEN) | Forwarded response, no rate-limit headers | No |\n| Redis error or no reply in 50 ms | Forwarded response, no rate-limit headers, metric emitted | Maybe. If Redis ran the script before the timeout, the request was counted, and the gateway does not know it. |\n| Over the limit | 429 with `Retry-After`, not forwarded | No |\n| Backend fails after the check (for example 500) | The backend's response, with rate-limit headers | Yes. No refund. |\n\nA retry after a 429 or a timeout is counted again only if it is allowed through. A retry after a backend timeout is a new counted request.\n\nAccepted trade-offs for v1:\n\n- **Fixed window**: a customer can send up to about 200 requests across a minute boundary (100 at the end of one window, 100 at the start of the next). A sliding window or token bucket would smooth this, but would be more complex.\n- **Redis failover** can lose the latest increments, which allows a few extra requests in that window.\n- **Plan cache**: the gateway caches plans for 5 minutes, so a plan change takes up to 5 minutes to apply. This is existing behavior.\n\n## Open questions\n\n- **Enterprise limit**: product has not set it. Do not ship a number until product decides.\n- **Key Service failure**: what the gateway does when the Key Service errors or is slow is not defined here. This design does not change it, and it needs to be confirmed.\n- **Backend timeout**: no timeout for the forwarded call is defined. A slow backend can hold the request open.\n- **429 body**: the exact response body is not defined yet.\n- **Metric owner**: who owns `ratelimit_store_unavailable` and its alert threshold. Fail open hides store outages from clients.\n- **Redis topology**: single primary with replica, or managed Redis. Keys are per customer, so Redis Cluster would not split one customer's counter across shards.
