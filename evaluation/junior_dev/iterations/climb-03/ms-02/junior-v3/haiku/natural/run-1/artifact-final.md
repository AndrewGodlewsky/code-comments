# Plan: extract notifications into a Notification Service\n\nNotification sending moves from the monolith into a separate Notification Service, one notification type at a time. Business code still records each notification in the monolith's `notifications` table. A relay hands each pending row to the service over the broker, the service sends it through MailRelay, and it reports the result back. Steps 1 to 6 change nothing users can see. Steps 7, 8 and 9 move one type each. Step 10 removes the old sender.\n\n## Terms\n\n- **MailRelay**: the external email provider. Its `send()` takes an optional `idempotency_key`. If it already accepted a send with that key in the last 24 h, it drops the new send and still returns success.\n- **Idempotency key**: the notification's id, passed on every send from both the old worker and the service. MailRelay drops any repeat within 24 h.\n- **Owner**: `monolith` or `service`. Each row has one owner at a time, and only the owner sends it.\n- **Route flag**: `notifications.route.<type>`, set to `monolith` (the default) or `service`. Only the monolith reads it.\n- **Claim**: a lease a worker takes on a row before acting on it. The monolith stores it as `claim` (who holds it: `worker` or `relay`) and `claim_until` (when it expires). The service stores it as `lease_until`. Anyone may take an expired lease.\n- **Retry policy**, the same on both sides: at most 5 attempts in total, counted across both sides. Wait 1, 2, 4 and 8 minutes before attempts 2 to 5. After attempt 5 fails, mark the row `failed` and page on-call with `alerts.page_oncall`. The whole span is about 15 minutes, inside the 24 h key window.\n- **Broker**: at-least-once, and the only channel between the two systems. Two topics: `notifications.requested` (relay to service) and `notifications.results` (service to monolith). Messages are keyed by notification id.\n- **Inbox**: the service's table of received notifications, keyed by id. Kept at least 7 days.\n- **Results outbox**: the service's table of `sent` and `failed` results waiting to be published.\n\n## Steps\n\n### 1. Send the notification id as the idempotency key on the old worker\n\n- **Starts:** an ordinary deploy of `app/notifications.py` that adds `idempotency_key=row.id` to `mailrelay.send`.\n- **Data moves:** none.\n- **State:** the monolith `notifications` table, unchanged.\n- **If it fails:**\n  - The worker crashes after MailRelay accepts but before the batch commits. The rows stay `pending` and are sent again, and MailRelay drops the repeat. This should remove the roughly 30 duplicate emails a week.\n  - MailRelay is down or times out. The existing retry and backoff code applies unchanged.\n- **Known gap:** the worker still commits once per batch, so duplicates are covered within 24 h but not fixed. This is acceptable for this step.\n- **Gate to step 2:** one week of duplicate-email support tickets, compared with the baseline of about 30 a week.\n\n### 2. Add owner, claims and route flags with no behaviour change\n\n- **Starts:** an additive migration, then a deploy of the new worker.\n- **Data moves:** none.\n- **State:** on `notifications`, add `owner` (default `monolith`), `claim` and `claim_until`. They are nullable or defaulted, so the table is not rewritten. Add `notifications.route.<type>` for all three types, each set to `monolith`.\n- **Worker:** claims only rows where `owner = monolith`, `route = monolith`, `status = pending` and `next_attempt_at <= now()`, using `FOR UPDATE SKIP LOCKED` inside a transaction.\n- **If it fails:**\n  - A flag read errors. The worker sends nothing for that type in this loop and retries on the next loop. It never sends a service-owned row, because ownership is per row.\n  - The worker crashes during a claim. The lease expires and the row returns to the pool. Any repeat send carries the same key.\n\n### 3. Build the Notification Service with its own database, deployed with no traffic\n\n- **Starts:** the service is deployed to its own environment with its own database. No relay points at it yet.\n- **Data moves:** none yet.\n- **State:** the `inbox` and `results_outbox` tables, in the service's database only.\n- **Templates:** `templates.render` moves into the service. Both codebases use the same versioned template package until decommission. Golden-output tests check the service's output against the monolith's for all three types.\n- **Components:**\n  - **Consumer.** Validates the message and inserts it into `inbox` with `state = received` and `attempts = message.attempts`, using `ON CONFLICT DO NOTHING`. It commits, then acks. It sends nothing, so the 30 s ack timeout is safe.\n  - **Sender**, every 5 s (the current `POLL_SECONDS`). It takes rows with `state` `received` or `sending`, `next_attempt_at <= now()`, and a null or expired `lease_until`, using `SKIP LOCKED`. For each row:\n    1. **Claim**, in one transaction. If `attempts >= 5`, mark the row `failed`, write a `failed` result and page. Otherwise add 1 to `attempts`, set `state = sending`, set `lease_until = now() + 60 s`, and set `first_attempt_at = now()` if it is null.\n    2. **Age check.** If more than 12 h have passed since `first_attempt_at`, mark the row `failed`, write a `failed` result and page, without sending. This keeps every send inside the 24 h key window.\n    3. **Send** with `idempotency_key = id` and a 30 s timeout, so the send ends before its 60 s lease expires. On success, in one transaction, set `state = sent` and write a `sent` result.\n    4. **On `mailrelay.Error`** (including timeouts): if `attempts >= 5`, set `state = failed`, write a `failed` result and page. Otherwise set `state = received` and `next_attempt_at = now() + BACKOFF[attempts-1]` minutes. A row that arrives with `attempts = 2` is claimed as attempt 3 and waits 4 minutes after a failure.\n  - **Results publisher**, every 1 s. It publishes unpublished `results_outbox` rows to `notifications.results`, keyed by id, and marks a row published only after the broker confirms.\n- **If it fails:**\n  - The consumer crashes before the ack. The broker redelivers, the insert conflicts so nothing changes, and the message is acked.\n  - A duplicate message arrives after a terminal state. It is a no-op and is acked.\n  - A crash during a send. The lease expires and a retry goes out with the same key. If MailRelay had already accepted, the repeat is dropped and counts as success.\n  - A crash after MailRelay accepts but before `sent` is committed. Same path: the row ends `sent` with no second email.\n  - MailRelay is down. Backoff applies, then `failed` and a page after attempt 5.\n  - The broker is down. Nothing is consumed and nothing is sent. Messages wait in the broker (see Open questions: broker retention).\n  - The results publish fails. The row stays unpublished and is retried until the broker confirms.\n  - A message fails validation. If it has an `id`, insert the inbox row as `failed` with `last_error`, write a `failed` result and page. If it has no `id`, page on-call with the raw message and ack. The relay checks required fields before it publishes, so this happens only after a version mismatch.\n- **Deliberate change:** a crash uses up an attempt, because the claim adds 1 to `attempts`. This stops a poison message from looping forever. See Open questions: crash attempts.\n- **Gate to step 4:** golden-output parity for all three types, and passing fault tests with a fake MailRelay and a fake broker.\n\n### 4. Add the handoff relay and the broker topics to the monolith, with no type routed\n\n- **Starts:** deploy the relay thread, and create `notifications.requested` and `notifications.results`.\n- **Data moves:** none while every route is `monolith`.\n- **Relay loop**, about every 1 s:\n  1. **Claim** up to one batch of rows where `owner = monolith`, `status = pending`, `next_attempt_at <= now()`, `route = service`, and the claim is null or expired. The claim is `relay`, with a 2 min lease.\n  2. **Check and publish.** Check the required fields. A row that fails the check is marked `failed` and paged, as the old worker would do. Publish each other row as `{id, type, user_id, email, payload, created_at, attempts}`, where `attempts` is the number of sends the monolith has made.\n  3. **Wait** up to 30 s for the broker's confirmation.\n  4. **Set** `owner = service` and clear the claim.\n- `status` stays `pending` on the monolith until a result arrives (step 5). The monolith worker sends only rows whose route is `monolith`, so it skips these rows even in the short window while `owner` is still `monolith`.\n- **If it fails:**\n  - The relay crashes after publish but before the owner update. The claim expires after 2 min and the row is handed off again. The inbox dedupes by id. If the monolith later sends the row too (possible only after a rollback, while the owner is still `monolith`), MailRelay's key suppresses the repeat within 24 h.\n  - The broker is down, or confirmation times out. The row keeps `owner = monolith` and waits. It is delayed, not lost. A timeout is ambiguous, so the relay republishes and the inbox dedupes. If the outage passes the threshold in Open questions, roll the type's flag back.\n  - A flag read errors. The relay pauses for that loop.\n\n### 5. Consume results in the monolith so `notifications.status` tracks the service\n\n- **Starts:** deploy the consumer on `notifications.results`.\n- **Data moves:** a result `{id, outcome: sent | failed, attempts, at}` flows from the service to the monolith.\n- **Update:** `UPDATE notifications SET status = outcome, attempts = result.attempts WHERE id = $1 AND status = 'pending'`. The `at` time goes to service logs for latency measurement and is not stored in the monolith. Terminal states never change.\n- **If it fails:**\n  - Redelivery: the conditional update matches nothing, and the message is acked.\n  - An unknown id: the update matches nothing. The consumer logs it and acks. The relay sends only rows from this table, so this indicates a bug.\n  - A crash before the ack: redelivery, as above.\n  - The service is down: `status` lags. Delivery is not affected.\n- **Gate to step 6:** for a sample of test notifications, `status` matches what MailRelay accepted.\n\n### 6. Rehearse cutover and rollback in staging\n\n- **Starts:** a staging environment with the three types, MailRelay sandbox or test recipients, and a fake broker outage tool.\n- **Scenarios:**\n  - Flip a type to `service` while rows are pending, then flip it back.\n  - Kill the relay mid-batch.\n  - Kill the service mid-send.\n  - Take the broker down for 10 minutes.\n  - Make MailRelay return errors for a period.\n- **Check:** zero duplicate recipient deliveries, zero lost notifications, and each rollback takes effect within a minute.\n- **Gate to step 7:** every scenario passes, and the rollback procedure has been timed.\n\n### 7. Move `shipping_update` (day 0)\n\n- **Starts:** set `notifications.route.shipping_update = service`.\n- **Data moves:** the relay hands off the pending `shipping_update` backlog and all new rows of this type. The monolith worker stops claiming this type within 10 s. Claims in flight finish or expire. The claim rules prevent a double send.\n- **State:** `owner` and `status` on the monolith. `inbox` and `results_outbox` on the service.\n- **If it fails:** the cases in steps 3, 4 and 5 apply. For a broker or service problem, flip the flag back to `monolith`.\n- **Rollback:** flip back to `monolith`. The relay stops handing off rows within 10 s. The monolith worker resumes claiming the rows it still owns (`owner = monolith`) for this type. Rows already handed off (`owner = service`) finish on the service, which sends them whatever the flag says, so they are neither re-sent nor dropped. If one is stuck, the backlog alert fires and on-call checks the service and the broker. Do not reassign it to the monolith by hand.\n- **Gate to step 8:** at least 3 days on the service, with zero duplicates reported, a failed rate under the threshold, no `owner = service` row pending longer than the backlog threshold, and latency reviewed. Thresholds are in Open questions.\n\n### 8. Move `order_confirmed` (day 3 or later)\n\n- **Starts:** set `notifications.route.order_confirmed = service`.\n- **Data moves, state and failure handling:** as in step 7. The relay hands off the pending backlog and new rows, and the monolith worker stops claiming within 10 s. Rows already handed off finish on the service.\n- **Rollback:** flip back to `monolith`. Owned rows resume on the monolith. Handed-off rows finish on the service, with no re-send and no drop.\n- **Measurement:** enqueue-to-MailRelay latency is the service's `sent_at` minus the `created_at` that the monolith sets. It includes relay polling and broker transit. Check clock skew between the monolith database and the service.\n- **Gate to step 9:** at least 3 days on the service, the step 7 gate criteria, and p99 enqueue-to-MailRelay under 60 s on `order_confirmed`. Do not move `password_reset` before this p99 gate is met.\n\n### 9. Move `password_reset` (day 6 or later, after the p99 gate)\n\n- **Starts:** set `notifications.route.password_reset = service`.\n- **Data moves, state, failure handling and rollback:** as in step 7. The relay keeps polling at about 1 s so the latency budget holds. This type is time-sensitive, so watch it closely.\n- **Gate to step 10:** at least 7 days on the service, with the same criteria. The old worker stays deployable and remains the rollback path for this type throughout.\n\n### 10. Hold for 7 days, then decommission the old worker\n\n- **Starts:** `password_reset` has run on the service for 7 days (day 13 at the earliest).\n- **Precondition:** all three route flags are `service`, and there are zero `owner = monolith` rows with `status = pending` for 24 h. Run this query and confirm the result before removing anything.\n- **Change:** the relay stops checking the route flag and hands off every `owner = monolith` pending row. Nothing reads the flags after this.\n- **Remove:** `run_worker`, `_deliver`, the monolith's copy of the templates, and the monolith's send path. Keep `enqueue_notification`, the `notifications` table, the relay and the results consumer, because callers still record in the monolith. After this step there is no rollback to the monolith.\n- **If it fails:** a `monolith`-owned pending row found after removal is handed off by the relay like any other, so it is not lost. Investigate before reverting anything.\n\n## Timeline (earliest)\n\n| Day | Event |\n|---|---|\n| 0 | `shipping_update` moves |\n| 3 | `order_confirmed` moves, after the `shipping_update` gate |\n| 6 | `password_reset` moves, after the `order_confirmed` p99 gate |\n| 13 | Old worker removed, after 7 days on `password_reset` |\n\nSteps 1 to 6 come first. Each soak can run longer than its minimum.\n\n## Open questions\n\n- **Broker retention.** The plan assumes at least 7 days, so inbox dedupe covers redeliveries. If retention is shorter, keep the inbox longer, or treat redelivery beyond the window as failed and page.\n- **MailRelay key window.** Confirm whether the 24 h window is fixed from the first accepted send or sliding, and whether a key-dropped send can be told apart from a fresh send. The plan treats both as success, as the overview describes.\n- **Crash attempts.** Counting crashed attempts toward the 5 differs from today. Confirm this is acceptable, or count only completed attempts. Also, the 12 h age check starts at the service's first claim, not the monolith's first attempt, so a row retried on the monolith just before handoff has less margin. The 15-minute retry span limits this.\n- **Email addresses on the broker.** Confirm with security and data owners that the broker may carry email addresses and payloads.\n- **Thresholds and reviewers, to set before step 7.** The failed-rate threshold, the maximum backlog age for `owner = service` rows, the broker-outage duration that triggers rollback, and who reviews these during each soak.\n- **Template drift.** Decide whether the shared template package is versioned and pinned, or released in lockstep with both deployables.\n- **Clock skew.** Confirm that the database and service clocks are synchronised within a bound small enough for the p99 gate.\n- **Relay versus change-data capture.** The plan polls from the monolith. CDC would also work, but it adds infrastructure and is not needed to meet the latency gate.
