# Plan: Download CSV on the reports page

## Summary

The Download CSV button calls one new endpoint. The endpoint reads `reports.row_count` and picks one of two paths:

- **Small report (10,000 rows or fewer).** The response streams the CSV straight back. No job runs and nothing is stored.
- **Large report (more than 10,000 rows).** The endpoint records an export in a new `report_exports` table and enqueues a background job. The job streams rows from the read replica into the `exports` bucket using a multipart upload, then emails a 24-hour signed link. The page shows the export's state by reading the table.

New pieces:

- `POST /api/reports/{report_id}/export`
- `GET /api/reports/{report_id}/export` (status)
- the `report_exports` table
- the job `build_report_export`

Everything else already exists.

## Assumptions

These are not stated in the three files. Check them before building.

- **Primary database for app state.** The `report_exports` table lives on the primary database. The "never read from the primary" rule covers report data, meaning `report_rows`. It does not cover our own bookkeeping. If `reports.row_count` must also come from the replica, read it there. It only changes nightly.
- **Queue behaviour.** `on_final_failure` is called whenever the last attempt fails, whether by exception, timeout or worker death. This follows the `jobs.py` docstring.
- **`send_email` templates.** `send_email(user_id, template, params)` needs two new templates: `report_export_ready` and `report_export_failed`.
- **Shared filter code.** The existing rows API has a function that turns `filters` and `cols` into a replica query. Export must reuse that same function, so the CSV matches the table. Extract it if it is currently inline in the handler.

## Data model

New table `report_exports` on the primary database:

| column | meaning |
|---|---|
| `export_id` | UUID, generated by the endpoint |
| `user_id`, `report_id` | who asked, and for which report |
| `filters`, `cols` | the exact view, copied from the URL at click time |
| `status` | `queued`, `running`, `done` or `failed` |
| `job_id` | queue job id (null until enqueued) |
| `upload_id` | the current multipart upload, so a retry can abort the previous one |
| `file_key` | set once `complete_multipart` has succeeded |
| `error` | short failure reason |
| `created_at`, `updated_at` | timestamps |

Two indexes:

- **Partial unique index** on `(user_id, report_id) WHERE status IN ('queued','running')`. This enforces "one large export at a time". It sits in the database, so two simultaneous clicks cannot both succeed.
- **Lookup index** on `(user_id, report_id, created_at DESC)`, for the status read.

Rows are never deleted. They are tiny, and a cleanup job is out of scope. The bucket's 7-day rule deletes the files.

The object key is deterministic: `exports/{report_id}/{export_id}.csv`. A retry therefore writes to the same key and replaces its own earlier output. Orphans cannot accumulate.

## Steps

### 1. The user clicks Download CSV

- **Starts it:** a click on the button. The page sends `POST /api/reports/{report_id}/export?filters=...&cols=...`, copying `filters` and `cols` from the current page URL.
- **Data moves:** only the query string. The server stores nothing about the view today, so the URL is the only source.
- **State:** none.
- **On failure:** if the request fails or the network drops, the button shows an error and the user can click again. Nothing has been created yet.

### 2. The server checks permission and chooses a path

- **Starts it:** step 1.
- **Data moves:**
  - Check `report.view` on the report's workspace, exactly as the rows API does. Return 403 otherwise, before anything else happens.
  - Read `reports.row_count` for the report.
  - If it is 10,000 or fewer, go to step 3. If it is above 10,000, go to step 4.
- **State:** none written. This is a read only.
- **On failure:**
  - No permission returns 403.
  - A missing report returns 404.
  - A database error returns 500, and no export is created.
  - `row_count` is the unfiltered total and is refreshed nightly. A filtered view of a big report still takes the large path. That is intended, because the rule is by `row_count`. The count can be stale only around the nightly rebuild.

### 3. Small path: stream the CSV in the response

- **Starts it:** step 2 with `row_count <= 10,000`.
- **Data moves:**
  1. Send headers `Content-Type: text/csv` and `Content-Disposition: attachment; filename=report-{id}.csv`.
  2. Write the header row from `cols`, in the URL's column order.
  3. Loop over the shared replica query with keyset paging: `row_id > after ORDER BY row_id LIMIT 500`. Write each page to the response as it arrives, and start the next page from the last `row_id`.
  4. Use a real CSV writer so commas, quotes and newlines are escaped.
  - At most about 20 queries run. Memory stays at one page.
  - Reads come from the **read replica only**.
- **State:** none. No job, no table row, no stored file.
- **On failure:**
  - If a query fails mid-stream, abort the connection. Do not end the response normally, so the browser reports a failed download instead of saving a truncated file as if it were complete. The user clicks again.
  - The 60-second request limit is far above the expected time for 10,000 rows. If a stale `row_count` made the real count much larger, the server would kill the request and the download would fail the same way.

### 4. Large path: create the export, or return the existing one

- **Starts it:** step 2 with `row_count > 10,000`.
- **Data moves:**
  1. Generate `export_id`.
  2. `INSERT` into `report_exports` with status `queued`, the user, the report, `filters` and `cols`.
  3. If the insert hits the partial unique index, a queued or running export already exists for this user and report. Do not start another. Select that row and return it with HTTP 200, including its `filters` and `cols` so the page can show which view it is for. This covers double-clicks and clicks from a second tab.
  4. Otherwise go to step 5.
- **State:** the new `report_exports` row, on the primary database. It is the single source of truth for status.
- **On failure:** if the insert fails for any reason other than the unique conflict, return 500. No row exists, so nothing is stuck.

### 5. Enqueue the job and answer straight away

- **Starts it:** step 4 created a new row.
- **Data moves:**
  1. Call `enqueue("build_report_export", {"export_id": ...})`. The payload is only the id. The view is read from the table, so the payload is far under the 64 KB limit.
  2. Save the returned `job_id` on the row.
  3. Return HTTP 202 with `{export_id, status: "queued"}`.
  - The page shows "Queued" and starts polling (step 11).
- **State:** `job_id` on the row.
- **On failure:**
  - If `enqueue` raises, set the row to `failed` (error: "could not queue") and return 500. The user can click again, because `failed` does not hold the unique slot.
  - If the process dies between the insert and the enqueue, a row sits at `queued` with no `job_id` and blocks new exports. Handle this at the next click, in step 4. If the existing row is `queued`, has a null `job_id` and is older than 2 minutes, enqueue it again and save the new `job_id`. This is safe because the job is idempotent (step 6). It needs no cleanup job.

### 6. The job starts an attempt

- **Starts it:** the queue calls `build_report_export(ctx, payload)` for attempt 1, 2 or 3. The queue keeps no progress between attempts, so every attempt starts from the top.
- **Data moves:**
  1. Load the row by `export_id`.
  2. If `status = 'done'`, return at once. The queue delivers at least once, so a duplicate run must do nothing.
  3. If `status = 'failed'`, return.
  4. Re-check `report.view` for the row's user. If it is gone, go to the fail routine in step 10 with the reason "permission removed", and return normally so the queue does not retry.
  5. Set `status = 'running'`.
  6. If `file_key` is already set, a previous attempt built the file and only the email failed. Skip to step 9.
  7. If `upload_id` is set, a previous attempt left an unfinished upload. Call `abort_multipart(upload_id)` and ignore errors. Then start a fresh upload.
- **State:** `status = running`, updated in the table.
- **On failure:** an exception, timeout or worker death counts as a failed attempt. The queue retries after 60 seconds, then after 300 seconds, for 3 attempts in total.

### 7. The job builds the file and streams it to storage

- **Starts it:** step 6, when `file_key` is not yet set.
- **Data moves:**
  1. Call `start_multipart("exports", key)`. Save the returned `upload_id` on the row straight away.
  2. Keep a byte buffer. Write the CSV header row into it, using the saved `cols` order.
  3. Loop over the same shared replica query as step 3 and the rows API, using the saved `filters` and `cols`. Use keyset paging in larger pages of 5,000 rows, starting from `after = 0`. Encode each page with the CSV writer and append it to the buffer. This reads from the **read replica only**.
  4. Whenever the buffer holds at least 8 MB (above the 5 MB minimum), call `upload_part(upload_id, n, bytes)`. Number parts from 1, keep the returned etag, and empty the buffer.
  5. When the rows run out, upload whatever remains as the last part. It may be smaller than 5 MB, which is allowed. An empty result still uploads the header row.
  - **Memory:** at most one 8 MB buffer plus one page of rows at any time, far below the 512 MB limit. The whole report is never held in memory, even at 2 million rows (about 900 MB of CSV).
  - **Part count:** 900 MB at 8 MB per part is about 113 parts, well under `MAX_PARTS` (10,000).
  - **Time:** 2 million rows is about 400 page queries plus about 113 uploads. This should finish well inside the 1,800-second attempt timeout. Measure it in step 12.
  - Nothing is visible at the key during the build, so no one can download a half-written file.
- **State:**
  - `upload_id` on the row.
  - The in-flight parts in storage. Only the job's local memory holds the part numbers, etags and last `row_id`.
- **On failure:**
  - If a query or upload call raises, let the exception propagate so the queue retries. The next attempt aborts this upload (step 6) and starts again from row 1.
  - If the worker dies, the unfinished upload stays until the next attempt aborts it. If every attempt dies, the bucket's rule discards the upload after 24 hours.
  - Each attempt restarts from the beginning because the queue keeps no progress. That is acceptable at this size, and it avoids storing a resume cursor.

### 8. The job publishes the file

- **Starts it:** the last page has been uploaded.
- **Data moves:**
  1. Call `complete_multipart(upload_id, etags)`. This is the only moment the object becomes visible at the key. It replaces any earlier object at that key.
  2. Save `file_key` on the row.
- **State:** `file_key` on the row.
- **On failure:**
  - If `complete_multipart` raises, nothing is visible. The attempt fails and retries, and the next attempt aborts the old upload and rebuilds.
  - If the process dies after completing but before saving `file_key`, the next attempt rebuilds and overwrites the same key. The result is identical and the file is complete, so there is no half-written state.

### 9. The job emails the link and marks the export done

- **Starts it:** step 8 finished, or step 6 found `file_key` already set.
- **Data moves:**
  1. Call `signed_url("exports", file_key, 86_400)`. Create it now, just before sending, so the 24 hours start at send time.
  2. Call `send_email(user_id, "report_export_ready", {report name, url})`.
  3. Set `status = 'done'`.
- **State:** `status = 'done'`. The row stays as a record.
- **On failure:**
  - If the email call raises, the attempt fails. The retry skips the build because `file_key` is set, and only redoes this step with a fresh link. A slow email never costs a rebuild.
  - If the process dies after sending but before `status = 'done'`, the retry sends the email a second time. This is the only duplicate and we accept it, since the queue is at-least-once.
  - Marking `done` only after the email goes out means the page never shows "done" for a user who has no link.

### 10. Last attempt fails: `on_final_failure`

- **Starts it:** the queue calls `on_final_failure(ctx, payload, error)` once, after attempt 3 fails. The step 6 permission case also calls the same routine.
- **Data moves:**
  1. Load the row. If it is already `done`, do nothing.
  2. Set `status = 'failed'` and store a short `error`. Do this first.
  3. Best effort: call `abort_multipart(upload_id)` if set.
  4. Call `send_email(user_id, "report_export_failed", {report name})`, wrapped so an email error is logged and swallowed. The email contains no report data.
- **State:** `status = 'failed'`. `failed` no longer holds the unique slot, so the user can click again and get a fresh export.
- **On failure:** if this routine itself dies after step 2, the page still shows "failed" and the user can retry. Only the email is lost, and we accept that. Writing `failed` before anything else keeps it from ever being left as `running` forever.

### 11. The page shows the export's state

- **Starts it:**
  - The page loads.
  - A click returns 200 or 202.
  - A poll timer fires, every 5 seconds while the state is `queued` or `running`.
- **Data moves:**
  - `GET /api/reports/{report_id}/export` checks `report.view` (403 otherwise).
  - It returns the caller's most recent `report_exports` row for this report as `{export_id, status, created_at, filters, cols}`, or `null` if none.
  - The page shows queued, running, done or failed, and stops polling once the state is `done` or `failed`.
  - Because the state lives in the table, it survives a reload and shows when the user comes back later.
  - On `failed`, the button is enabled again.
  - On `done`, show "Link sent by email". The link expires after 24 hours and the file after 7 days, so the page does not link to the file itself.
- **State:** read only. The only per-viewer browser state is the poll timer.
- **On failure:** a failed poll is ignored and retried on the next tick. The table is the source of truth, so a missed poll loses nothing.

### 12. Verify before release

- **Starts it:** the code is written.
- **Checks:**
  - **Both paths.** A report with 10,000 rows takes the streaming path. A report with 10,001 rows takes the job path.
  - **Bounds and format.** A 2-million-row run stays under 512 MB of worker memory. The output equals what the page shows for the same filters and column order, with a header row.
  - **One at a time.** Two simultaneous clicks produce one row and one job.
  - **Failure injection.** Make `upload_part` fail on attempt 1, then succeed. Check that the old upload is aborted and the file is complete. Make every attempt fail. Check that the page shows "failed", the failure email arrives and no object is downloadable. Make `send_email` fail once. Check that the file is not rebuilt.
  - **Duplicate delivery.** Run a job again after it is `done`. It must do nothing.
  - **Timing.** Measure the largest report's total build time against the 1,800-second timeout. If it exceeds about half of it, raise the page size or part size, or reconsider resumable uploads.
  - **Permission.** A user without `report.view` gets 403 from both endpoints.

---

## Out of scope

Scheduled exports, formats other than CSV, changes to the table on the page, and any cleanup job. The bucket's existing 7-day rule handles old files.

## Open questions for the owner

- A second click with different filters returns the running export for the first view. This follows "one at a time per report" literally. Confirm that is wanted, or key the limit by view instead.
- Should the page offer a fresh download link on `done`, after the emailed one expires? That needs one more endpoint and a permission check each time.
