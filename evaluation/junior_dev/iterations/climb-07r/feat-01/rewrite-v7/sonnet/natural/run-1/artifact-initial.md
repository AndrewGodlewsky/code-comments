# Plan: CSV export for the reports page

## Summary

The **Download CSV** button calls one new endpoint. That endpoint reads `reports.row_count` and picks one of two paths:

- **10,000 rows or fewer:** the endpoint builds the CSV and returns it in the same response. Nothing is stored.
- **More than 10,000 rows:** the endpoint records an export in a new table, queues a background job, and returns at once. The job streams the rows into the `exports` bucket with a multipart upload. It then emails a 24-hour link. The page shows the export's state from the new table.

## Terms used in this plan

- **Page API:** the existing `GET /api/reports/{report_id}/rows`. It checks `report.view`, reads `report_rows` from the **read replica** only, and pages by keyset (`row_id > after ORDER BY row_id`).
- **Queue:** `jobs.py`. It makes at most 3 attempts, waits 60 s and then 300 s between them, and kills an attempt after 1800 s. It keeps no progress between attempts. Delivery is at least once.
- **Storage:** `storage.py`. Nothing is visible at a key until `complete_multipart` succeeds. The bucket deletes objects after 7 days and discards multipart uploads not completed within 24 hours.

## New state: the `report_exports` table

This table lives in the **primary database**. It holds export bookkeeping, not report data, so the "never read report data from the primary" rule does not apply to it. The replica is also read-only.

| Column | Meaning |
|---|---|
| `id` | UUID, generated by the endpoint. Used for the object key and the job payload. |
| `report_id`, `user_id` | Who asked for which report. |
| `filters`, `cols` | Raw strings copied from the page URL at click time. The server stores no view state, so this is the only record of what the user was looking at. |
| `status` | `queued`, `running`, `done` or `failed`. |
| `job_id`, `attempt` | The queue's job id, and the last attempt number that started (0 until the first). |
| `upload_id` | The current multipart upload id. Lets a later attempt or the failure handler discard an orphaned upload. |
| `object_key` | `reports/{report_id}/{id}.csv`, set at creation. |
| `error` | Short failure reason, shown nowhere except logs and the page's failed state. |
| `created_at`, `finished_at`, `emailed_at` | Timestamps. `emailed_at` makes the email step safe to retry on its own. |

**Index.** A partial unique index on `(report_id, user_id) WHERE status IN ('queued','running')`. The database itself enforces the rule that a user has one active large export per report, even under double-clicks and races. A second index on `(report_id, user_id, created_at DESC)` serves the page's status lookup.

## New endpoints

- `POST /api/reports/{report_id}/export` with body `{filters, cols}`, copied verbatim from the page URL. It answers `200 text/csv` (small path) or `202 JSON {export_id, status}` (large path). The page's script reads the response type and either saves the file or shows status.
- `GET /api/reports/{report_id}/export` returns the caller's most recent export for that report: `{export_id, status, created_at, finished_at}`, or 404 if none. It is read from the primary and needs `report.view`.

## Steps

### 1. User clicks Download CSV: validate and choose the path

- **Starts it:** the click. The page sends `filters` and `cols` from its current URL.
- **Data moves:**
  1. The endpoint checks `report.view` on the report's workspace, the same check the Page API uses. If it fails, return 403 and do nothing else.
  2. It parses `filters` and `cols` with the **same parsing and column-validation code the Page API uses**. Move that code to a shared function rather than copying it, so the page and the CSV can never disagree. Reject bad input with 400. Also reject a combined `filters` + `cols` over 8 KB with 400.
  3. It reads `reports.row_count` from the replica. Row count is report metadata, and this avoids any doubt about the primary rule.
  4. If `row_count <= 10000`, go to step 2. Otherwise go to step 3.
- **State kept:** none.
- **On failure:** 403 or 400 as above. If the replica is unreachable, return 503 and tell the user to try again. Never fall back to the primary.

### 2. Small path: build and return the CSV in the response

- **Starts it:** step 1 chose the small path.
- **Data moves:**
  1. Write the header row, using the requested column order.
  2. Read rows from the replica by keyset in pages of 500 (the Page API's page size). Use the same filters and `row_id > after ORDER BY row_id`, and never OFFSET.
  3. Encode each page with the shared CSV writer (step 7 uses the same function). The writer applies RFC 4180 quoting and encodes UTF-8.
  4. Return `200` with `Content-Type: text/csv` and `Content-Disposition: attachment; filename="report-{id}-{date}.csv"`.
  5. The rows are held in memory until the response is sent. That is at most 10,000 rows, roughly 4.5 MB at today's average of about 450 bytes per row. This is deliberate. Failures then return a clean error status instead of a truncated download.
  6. Stop if the loop reads more than 10,000 rows. That means `row_count` was stale, so treat the request as the large path (step 3).
  7. Also stop after 45 s, which stays under the API servers' 60 s kill. This should never trigger, since 10,000 rows is about 20 queries.
- **State kept:** none. No job runs and nothing is stored.
- **On failure:** any query error or the 45 s limit returns 503 with a retry message. The page shows the error and the user clicks again. No partial CSV is ever sent.

### 3. Large path: create or return the export record

- **Starts it:** step 1 chose the large path (or step 2 fell through).
- **Data moves:**
  1. Generate an `id`. Run `INSERT INTO report_exports (...status='queued'...) ON CONFLICT DO NOTHING` against the partial unique index, storing `filters`, `cols` and `object_key`.
  2. If a row was inserted, go to step 4.
  3. If nothing was inserted, a queued or running export already exists for this user and report. `SELECT` it and return `202 {existing export_id, status}`. No second export starts. If its filters differ from this click, the existing export still wins. State this in the UI text: "An export of this report is already in progress."
  4. If that `SELECT` finds nothing, the other export finished between the two statements. Repeat step 3.1 once.
  5. If the existing row is `queued` with no `job_id` and is older than 2 minutes, a previous request crashed between insert and enqueue. Run step 4 again for that row, with its existing id.
- **State kept:** the `report_exports` row. This is the single source of truth for "one at a time".
- **On failure:** if the database write fails, return 503. Nothing has been queued, so a retry is clean.

### 4. Enqueue the job

- **Starts it:** step 3 inserted a row, or repaired a stuck one.
- **Data moves:** call `enqueue("report_export", {"export_id": id})`. The payload is only the id (far under the 64 KB limit). The job reads filters, columns and user from the table. Store the returned `job_id` on the row. Return `202 {export_id, status: "queued"}`.
- **State kept:** `job_id` on the row.
- **On failure:**
  - If `enqueue` raises, set the row to `failed` with an error note. That frees the unique slot so the user can click again. Return 503.
  - If the process dies after the insert but before `job_id` is stored, the row sits `queued` with no job. The 2-minute repair rule in step 3.5 handles it on the user's next click.
  - If `enqueue` succeeded but saving `job_id` failed, the repair rule may queue a second job for the same id. That is safe, because step 6 makes the handler tolerate duplicates.

### 5. Page shows the export's state

- **Starts it:** (a) the endpoint returned 202, and (b) any later visit to `/reports/{report_id}`.
- **Data moves:** on page load, and every 5 seconds while the state is `queued` or `running`, the page calls `GET /api/reports/{report_id}/export`. It renders a status line: queued, running, done or failed. It stops polling at `done` or `failed`. Because the state is in the database, it survives a closed tab and a return visit. While the state is `queued` or `running`, the button is disabled and shows the status.
- **State kept:** none new. The page only reads.
- **On failure:** if a poll fails, keep the last known state and retry on the next tick. The status line is informational. The job does not depend on it.

### 6. Worker starts an attempt

- **Starts it:** the queue runs `report_export(ctx, payload)`. This happens for the first attempt and for each retry, always from the beginning.
- **Data moves:**
  1. Load the row by `payload.export_id`.
  2. If `status` is `failed`, return. If `status` is `done`, skip to step 9 (this covers duplicate delivery and email-only retries).
  3. If the row has a stored `upload_id` from an earlier attempt, call `abort_multipart(upload_id)`. Ignore errors, because the 24-hour storage rule discards stragglers anyway.
  4. Set `status='running'`, `attempt=ctx.attempt`, `started_at=now`.
  5. Call `start_multipart("exports", object_key)` and store the new `upload_id` on the row.
- **State kept:** the row (`running`, `attempt`, `upload_id`).
- **On failure:** raise. The queue retries after the backoff. Until the last attempt, the page keeps showing "running", including during the 60 s and 300 s waits.

### 7. Worker streams rows into the multipart upload

- **Starts it:** step 6 finished.
- **Data moves:**
  1. Build a small in-memory buffer holding the header row, then loop over the report.
  2. The loop reads the replica by keyset in pages of 5,000 rows using the stored `filters`, `cols` and `row_id > after ORDER BY row_id`. Never fetch the whole result. Each query is short, so the replica has no long-running cursor.
  3. Encode each page with the shared CSV writer and append it to the buffer.
  4. Whenever the buffer reaches **16 MB**, call `upload_part(upload_id, n, data)`, keep the returned etag, clear the buffer and increment `n`. This is above the 5 MB minimum and gives about 57 parts for the 900 MB report, far under `MAX_PARTS` (10,000).
  5. After the last page, upload whatever remains as the final part. The last part may be any size, and the header row guarantees at least one part, even for a filter that matches nothing.
  6. Memory stays at about one 16 MB part buffer plus one 5,000-row page (a few MB as text, more as Python objects). That is far below 512 MB at any report size.
  7. Time: the 2-million-row report is about 400 queries and 57 uploads. Measure it on a production-sized report before release. The aim is to finish in well under 15 minutes, leaving more than half of the 1800 s limit spare.
  8. Check elapsed time after each part. Past 1700 s, call `abort_multipart` and raise. A timed-out attempt is killed and cannot clean up, and a restart gets the same budget again.
- **State kept:** etags in the worker's memory only. The queue keeps no progress between attempts, so a retry starts over from row 1.
- **On failure:**
  - Any exception (replica error, upload error): try `abort_multipart`, then re-raise so the queue retries.
  - A killed attempt (timeout or dead worker) leaves an orphaned upload. The next attempt aborts it in step 6.3, and failing that, storage discards it after 24 hours.
  - Nothing is visible at `object_key` throughout, because nothing is visible until `complete_multipart`. A half-written file is never downloadable.

### 8. Worker completes the file

- **Starts it:** step 7 uploaded every part.
- **Data moves:**
  1. Call `complete_multipart(upload_id, etags)`. The object appears at `object_key` all at once.
  2. Then run `UPDATE report_exports SET status='done', finished_at=now WHERE id=? AND status='running'`.
- **State kept:** `status='done'`.
- **On failure:**
  - If `complete_multipart` fails, raise and let the queue retry.
  - If the worker dies between completing and updating the row, the object exists but the row says `running`. The retry rebuilds the whole file and replaces the object at the same key. The result is the same content, and there is still no half-written state.
  - No download link exists until step 9, so nobody can fetch the file before it is complete.

### 9. Worker emails the download link

- **Starts it:** step 8 marked the export `done`, or step 6.2 found a `done` row with `emailed_at` empty.
- **Data moves:**
  1. Skip if `emailed_at` is set.
  2. Call `signed_url("exports", object_key, 86400)`. 86,400 is the maximum, and the link works for 24 hours from this moment.
  3. Call `send_email(user_id, "report_export_ready", {report name, url, expires})`.
  4. Set `emailed_at=now`.
- **State kept:** `emailed_at`. Because the file is already built and marked done, a retry only repeats this step. It never rebuilds 900 MB for an email problem.
- **On failure:** raise so the queue retries. If every attempt fails here, step 10 leaves the export `done` (the file is good) and logs the email failure. A rare duplicate email from at-least-once delivery is accepted.

### 10. Last attempt fails: mark failed and notify

- **Starts it:** the queue calls `on_final_failure(ctx, payload, error)` once, after attempt 3 fails.
- **Data moves:**
  1. Load the row. If it is already `done`, only the email failed. Log it and stop, so the page keeps showing the good file.
  2. Otherwise set `status='failed'`, `error` (short text), `finished_at=now`. This also frees the unique slot, so the user can start a new export.
  3. If an `upload_id` is stored, call `abort_multipart`, ignoring errors.
  4. Call `send_email(user_id, "report_export_failed", {report name})`.
- **State kept:** `status='failed'`. Set it **before** sending the email, so the page is correct even if the email fails.
- **On failure:** wrap the abort and the email in try/catch and log them. The handler is not retried. If the database update itself fails, the row stays `running` and blocks new exports. Alert on this case, and consider a manual reset.

### 11. Cleanup

- **Starts it:** the bucket's lifecycle rule, with no code from us. Objects are deleted 7 days after creation, and uncompleted uploads are discarded after 24 hours.
- **Data moves:** none. The plan builds no cleanup job.
- **State kept:** `report_exports` rows stay as history.
- **On failure:** not applicable.

## Assumptions and open questions

1. **Email templates.** `report_export_ready` and `report_export_failed` are assumed to be new `send_email` templates. If template names are fixed elsewhere, adjust.
2. **`row_count` is unfiltered and nightly.** A filtered export of a big report still takes the large path. This is by design, since the brief says to decide on `row_count`. A nightly rebuild during a long export could mix old and new rows in one file. No versioning field was described, so this plan does not guard against it. Decide whether that matters.
3. **Expired files.** Links last 24 hours and the object lasts 7 days. After that, a `done` export has no file. The page still shows "done", per the four fixed states. Consider a small "expired" note on `done` exports older than 7 days. A new click already starts a fresh export, because only `queued` and `running` block.
4. **Spreadsheet formula injection.** Cells starting with `=`, `+`, `-` or `@` can run as formulas when the CSV is opened in a spreadsheet. The brief doesn't mention this. The shared CSV writer is the single place to add a guard if the team wants one.
5. **Persistent timeouts.** If the 2-million-row report ever cannot finish within 1800 s, all three attempts will time out and the export will end as failed. The step 7.7 load test is the guard.

## Test checklist

- 10,000 rows returns CSV. 10,001 rows queues a job. A stale `row_count` falls through to the large path.
- Two concurrent clicks produce one export row and one job. After `done` or `failed`, a click starts a new export.
- A user without `report.view` gets 403 on both endpoints.
- A worker killed mid-upload, then retried, leaves no object at the key until completion. The orphan upload is aborted.
- Failure on all three attempts gives status `failed` and a failure email. Failure only in the email step leaves the status `done`.
- A load test on the 2-million-row report shows peak memory under 512 MB and a runtime well under 1800 s.
