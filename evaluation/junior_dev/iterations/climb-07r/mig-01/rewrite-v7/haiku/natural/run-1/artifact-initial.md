# Move `users` from MySQL 8 to Postgres 16: migration plan

## Design decisions

- **Outbox in the source-of-truth database.** Every write to `users` also inserts an outbox row in the same transaction. While MySQL is the source of truth, the outbox is `users_outbox` in MySQL. After the switch, it is `users_outbox` in Postgres. After the commit, the write copies the row to the other database inline, best effort, with a short timeout. If that copy fails, the outbox row stays and a repair worker retries it until it succeeds. Nothing depends on Redis. `jobs.enqueue` is not used because it raises when Redis is down, and its retries end in `jobs:dead`, which nothing processes.
- **One copy rule.** Every copy into either database goes through the same function: inline apply, repair, backfill, mirror, and compare repair. The function takes a per-user lock, skips the user if a tombstone exists, inserts a missing row, and updates an existing row only if `existing.version < incoming.version`. A stale copy can never overwrite a newer row.
- **Tombstones.** The erasure path writes `user_tombstones(user_id)` in the same transaction as the hard delete. The table stores only the id, no personal data. Because the copy rule refuses tombstoned ids, a late backfill or repair cannot bring an erased user back. The per-user lock orders a copy and a delete for the same id.
- **Repair reads the primary.** The outbox row is deleted after a copy, so the copy must use the current row from the primary. A replica read could delete the outbox row after copying a stale version.
- **Write state is one flag.** `users_write_state` takes the values `legacy`, `mysql`, `paused`, `postgres`, and `postgres_only`. The write path reads it on every request. Every change of source of truth goes through `paused`, so no instance writes to the old side once the new side is authoritative.
- **Read source is a separate flag.** `users_read_source` takes `mysql` or `postgres`, and can ramp by percentage using `flags.enabled_for(name, user_id)`, so each user stays in the same bucket. A read that fails or times out on one store is retried on the other, so reads never fail.
- **Ids.** Postgres uses `GENERATED BY DEFAULT AS IDENTITY` so explicit ids from MySQL can be copied. Before Postgres becomes the source of truth, its sequence is set above MySQL's `AUTO_INCREMENT` plus a 1,000,000 margin, while writes are paused. Explicit inserts into MySQL move its counter forward, so the mirror keeps MySQL safe for rollback.
- **Backfill progress** is kept in Postgres `users_migration_state`, committed in the same transaction as the batch it describes.

## Components and state

| Item | Where | Purpose |
|---|---|---|
| `users_write_state`, `users_read_source`, `users_backfill_enabled` | `app.flags` | Phase control. Instances cache for 30 s. |
| `users`, `users_outbox`, `user_tombstones` | MySQL (`core`) | Source of truth before the switch, and the mirror and outbox after it. |
| `users`, `users_outbox`, `user_tombstones` | Postgres (`pg-core`) | Copy target before the switch; source of truth after it. |
| `users_migration_state` | Postgres | Backfill checkpoint and lease, compare-pass progress, and milestone timestamps (`pg_sot_since`, `pg_reads_full_since`, `pg_only_since`). |
| `app_flag_value{flag=...}`, `mysql_replica_lag_seconds` | Metrics | Confirm that every instance has a value, and gate the backfill. |
| Outbox age, outbox rows, `pg_apply_failures_total`, `read_fallback_total`, `compare_mismatches` | New metrics | Health and gates. |

## Checklist

### Phase 0: Prepare (no user-visible change)

- [ ] **0.1 Create the additive schema.**
  - **Starts:** a migration run.
  - **Changes:** MySQL gets `users_outbox(id, user_id, op, created_at, attempts, next_attempt_at, last_error)` and `user_tombstones(user_id PK, deleted_at)`. Postgres gets `users` (BIGINT identity id, email unique, name, plan, version INT, updated_at `timestamp(3)` in UTC), `users_outbox` (same shape), `user_tombstones`, and `users_migration_state`.
  - **State:** both databases.
  - **If it fails:** the change is additive. Nothing reads the new tables yet, so retry it.

- [ ] **0.2 Deploy the new code with `users_write_state = legacy`.**
  - **Starts:** the normal deploy, covering web instances and the worker fleet. The erasure job runs on workers, so workers must be included.
  - **Changes:** `UserRepository` contains the new logic. With `legacy`, behaviour matches today: MySQL only, no outbox, no Postgres writes. The repair worker is deployed but idle.
  - **State:** flags in `app.flags`. `users_read_source` is `mysql`.
  - **If it fails:** roll back the deploy. `legacy` is the old behaviour.

- [ ] **0.3 Verify the fleet.**
  - **Starts:** 0.2 is finished.
  - **Changes:** nothing. Check that every web and worker instance runs the new build and reports `users_write_state` in `app_flag_value`.
  - **If it fails:** an instance that is missing or on the old build blocks Phase 1. Fix it and check again.

### Phase 1: Dual writes (MySQL is the source of truth)

- [ ] **1.1 Enable dual writes.**
  - **Starts:** the operator sets `users_write_state` from `legacy` to `mysql` after 0.3 passes.
  - **Changes:** each write runs one MySQL transaction that changes `users` and inserts an outbox row. For updates, the row is read back from the primary inside that transaction to get the new version. After the commit, the write copies the row to Postgres inline, with a 200 ms timeout behind a circuit breaker. On success, the outbox row is deleted. Postgres errors never fail the request.
  - **State:** the flag, and outbox rows in MySQL.
  - **If it fails:** set the flag back to `legacy`. Existing outbox rows still drain, so nothing already written is lost. Writes made under `legacy` have no outbox row, and the backfill in 1.3 covers them.

- [ ] **1.2 Confirm every instance dual-writes.**
  - **Starts:** 1.1 is finished.
  - **Condition:** `app_flag_value{flag="users_write_state"}` reads `mysql` on every web and worker instance for at least 60 s (two refresh cycles plus margin). Outbox rows are being created, and `pg_apply_failures_total` is not climbing.
  - **If it fails:** find the instance that is not reporting `mysql`. Do not start the backfill until all instances are dual-writing.

- [ ] **1.3 Run the backfill.**
  - **Starts:** 1.2 passes, and the operator sets `users_backfill_enabled` to true. Only one backfill runs at a time.
  - **Changes:** the loop is:
    1. Take the lease. Set `lease_owner` and `lease_expires_at` (now + 60 s) in `users_migration_state` if the lease is free or expired. Renew it on every batch.
    2. Check the replica lag. If the metric is missing or above 5 s, sleep 2 s and check again. Do not read.
    3. Read `SELECT * FROM users WHERE id > :last_id ORDER BY id LIMIT 2000` from the replica.
    4. If the batch is empty, mark the backfill done and stop.
    5. In one Postgres transaction, apply the copy rule to each row, then set `last_id` to the batch's maximum id, but only if `lease_owner` is still this worker.
  - **State:** `users_migration_state` in Postgres. The checkpoint commits with the rows, so no batch is partly applied.
  - **If it fails:** a crash, lost lease, or Postgres error rolls back the batch. The next run resumes after the last committed `last_id`. Replaying a batch is harmless because the copy rule is idempotent. Reading a stale replica is also harmless, because the version rule blocks older data.

- [ ] **1.4 Keep the repair worker running.**
  - **Starts:** the worker is deployed in 0.2 and active from 1.1.
  - **Changes:** the loop claims up to 100 rows with `SELECT ... FROM users_outbox ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED` on the MySQL primary. For each row, it reads the current row from the primary. If the row exists, it applies the copy rule. If the row is gone, it writes the tombstone and deletes the row in Postgres under the per-user lock. Then it deletes the outbox row. Postgres is written before the outbox row is removed, so a crash just causes an idempotent replay.
  - **State:** the outbox in MySQL, and the target rows in Postgres.
  - **If it fails:** the attempt count goes up and the next attempt is scheduled with exponential backoff, capped at 5 minutes. Rows are never dead-lettered. An email unique-key conflict is retried, because another user's email change may not have reached Postgres yet. Alert if the oldest row is over 10 minutes old or the table has more than 10,000 rows.

### Phase 2: Verify

- [ ] **2.1 Run full comparison passes.**
  - **Starts:** 1.3 reports done, and the oldest outbox row is under 1 minute old.
  - **Changes:** a keyset scan of the replica and Postgres in id order, in batches of 2000, with the same lag pause as the backfill. Compare `(id, email, name, plan, version, updated_at)`, and flag any id that exists only in Postgres. For each mismatch, re-read the row from the MySQL primary and wait briefly. Only confirmed differences count. Repair them with the copy rule, or tombstone and delete if the primary no longer has the row. A pass is clean only when it finds zero confirmed mismatches. Repeat passes until one is clean.
  - **State:** progress and results in `users_migration_state`.
  - **If it fails:** the job resumes from its checkpoint. A mismatch that persists after repair stops the cutover and needs investigation. Mismatches caused by in-flight writes usually disappear on re-check.

### Phase 3: Reads on Postgres

- [ ] **3.1 Ramp reads to Postgres.**
  - **Starts:** the latest pass in 2.1 is clean and finished within the last 24 hours. The operator sets `users_read_source` to `postgres` at 1%, then 10%, 50%, and 100%, waiting about an hour at each step.
  - **Changes:** `UserRepository.get` reads from Postgres for the users in the current bucket. If the Postgres read errors or takes over 200 ms, the same request reads from the MySQL replica, so reads never fail. `read_fallback_total` counts the fallbacks.
  - **State:** the flag. When 100% is reached, the operator records `pg_reads_full_since`.
  - **If it fails:** if fallbacks exceed 0.1% or errors are sustained, set the ramp back to 0%. Reads stay on MySQL and no user request fails.

- [ ] **3.2 Hold reads at 100% on Postgres for at least 3 days.**
  - **Starts:** `pg_reads_full_since` is recorded.
  - **Changes:** nothing. Compare passes keep running, at least daily.
  - **State:** `pg_reads_full_since` in `users_migration_state`.
  - **If it fails:** the clock resets if the read source leaves 100%, if the hourly fallback rate goes above 0.1%, or if a comparison finds a confirmed mismatch.
  - **Gate for 4.1:** at least 72 hours have passed since `pg_reads_full_since`, and the last clean pass finished within 24 hours.

### Phase 4: Planned switch to Postgres as the source of truth

Budget: writes are paused for at most 90 s. The switch aims to flip by about 50 s and aborts if it has not flipped by 55 s.

- [ ] **4.1 Pause writes.**
  - **Starts:** the 3.2 gate is met, and the operator sets `users_write_state` to `paused`.
  - **Changes:** every write returns a retryable 503 with `Retry-After: 1`. Reads continue. Wait until `app_flag_value` reads `paused` on every web and worker instance, which takes up to about 30 s.
  - **If it fails:** if not every instance reports `paused` by 35 s, abort (4.5).

- [ ] **4.2 Let in-flight writes finish.**
  - **Starts:** 10 s after the last instance reports `paused`.
  - **Changes:** nothing. Write transactions have a hard 5 s timeout in both databases, so any write that passed the gate before the pause has ended by then.

- [ ] **4.3 Drain the MySQL outbox.**
  - **Starts:** 4.2 is finished.
  - **Changes:** the repair worker keeps running and drains `users_outbox` in MySQL to zero.
  - **If it fails:** if the outbox is not empty by 50 s after the pause started, abort (4.5). If Postgres is unavailable, the drain cannot finish, and the switch must not proceed.

- [ ] **4.4 Set the id sequence and flip.**
  - **Starts:** 4.3 is finished.
  - **Changes:** read MySQL `AUTO_INCREMENT` for `users` from `information_schema`. In Postgres, run `SELECT setval('users_id_seq', GREATEST(last_value, :auto_inc + 1000000))`. Check that `max(id)` and row counts match. Set `users_write_state` to `postgres`. Record `pg_sot_since` in `users_migration_state`. From then on, writes go to Postgres first and new ids come from `INSERT ... RETURNING id`.
  - **If it fails:** if the setval or the checks fail, or the flip has not happened by 55 s, abort (4.5).

- [ ] **4.5 Abort, if any step in Phase 4 fails.**
  - **Starts:** a Phase 4 failure or timeout.
  - **Changes:** set `users_write_state` back to `mysql`. Instances resume MySQL-first writes within about 30 s, so the pause ends by about 85 s at worst.
  - **Why no data is lost:** MySQL was still the source of truth, and any change it held that Postgres lacked is still in the outbox. The advanced Postgres sequence is harmless.

### Phase 5: Postgres is the source of truth (mirror on, rollback possible)

- [ ] **5.1 Write to Postgres first.**
  - **Starts:** 4.4 is finished.
  - **Changes:** each write runs one Postgres transaction that changes `users`, inserts a row in the Postgres outbox, and writes the tombstone for deletes. After the commit, it copies the row to MySQL inline with the copy rule. MySQL uses `GET_LOCK` for the per-user lock and a version check. On success, the outbox row is deleted.
  - **State:** Postgres `users` and `users_outbox`, and the MySQL mirror.
  - **If it fails:** the outbox row stays and the mirror worker retries it. Writes are not affected by a MySQL outage.

- [ ] **5.2 Run the mirror repair.**
  - **Starts:** 5.1 is finished.
  - **Changes:** the same repair worker runs in reverse. It drains the Postgres outbox into MySQL, reading the current row from the Postgres primary.
  - **If it fails:** backoff as in 1.4. Alert on age. Reads that fall back to MySQL can be as stale as the mirror lag, which is bounded by outbox age and alerted on. Accept this trade-off.

- [ ] **5.3 Keep verifying.**
  - **Starts:** 5.1 is finished.
  - **Changes:** run a full comparison in the Postgres-to-MySQL direction at least daily, and always before any rollback. Repair mismatches with the copy rule.

- [ ] **5.4 Hold for at least 14 days.**
  - **Starts:** `pg_sot_since` is recorded.
  - **Gate for 7.1:** at least 14 days have passed since `pg_sot_since`, the last mirror pass is clean and finished within 24 hours, the mirror outbox is empty, and the owner has signed off.

### Phase 6: Rollback to MySQL (available until 7.1)

Same budget and abort rules as Phase 4.

- [ ] **6.1 Pause writes.** Do step 4.1.
- [ ] **6.2 Let in-flight writes finish.** Do step 4.2.
- [ ] **6.3 Drain the Postgres outbox into MySQL.**
  - **Changes:** the mirror drains to zero.
  - **If it fails:** set `users_write_state` back to `postgres`. Postgres is still the source of truth, so writes resume there.
- [ ] **6.4 Check the id ranges.** Confirm that MySQL `max(id)` equals Postgres `max(id)`. MySQL's counter is already past every mirrored id, because explicit inserts advance it.
- [ ] **6.5 Flip to `mysql`.**
  - **Changes:** writes resume MySQL-first and Postgres becomes the dual-write target again. Reads stay on Postgres if it is healthy. Otherwise, set `users_read_source` to `mysql`.
  - **If it fails:** the same abort as 6.3.
- [ ] **6.6 Re-switching later** runs Phase 4 again. Its `GREATEST(...)` setval keeps the sequence above every id already used, so ids do not collide.

### Phase 7: Postgres only (point of no return)

- [ ] **7.1 Stop the mirror.**
  - **Starts:** the gates in 5.4 are met, and the mirror outbox is empty.
  - **Changes:** the operator sets `users_write_state` to `postgres_only`. This is not a change of source of truth, so no pause is needed. Writes go only to Postgres, and MySQL is frozen at this point.
  - **State:** the flag, and `pg_only_since` in `users_migration_state`.
  - **If it fails:** the flag can be set back to `postgres` until the change takes effect. After it takes effect, rollback to MySQL is no longer possible, so problems must be fixed forward.

### Phase 8: Retire MySQL

- [ ] **8.1 Export `users` for retention.**
  - **Starts:** the team's agreed period after 7.1 has passed.
  - **Changes:** export the MySQL `users` table to restricted storage. The export holds personal data, so the erasure job must cover it, or it must expire under the retention policy.
- [ ] **8.2 Remove the MySQL write path and the flags.**
  - **Changes:** deploy code without the MySQL branches. Remove the flags. Keep the `no-raw-users-sql` lint rule.
- [ ] **8.3 Drop the MySQL tables.**
  - **Changes:** drop `users`, `users_outbox`, and `user_tombstones` in MySQL. This is irreversible except through the 8.1 export. Keep `user_tombstones` in Postgres permanently, since it holds only ids.
