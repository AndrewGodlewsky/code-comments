## Review of ms-01 (junior, author haiku, natural)

Rounds: 5. Ended: teachbacks.

### What changed
- Added a Messages table (M1 to M12) that gives each HTTP call and event its direction, transport, payload, idempotency key and no-answer rule, because Q1 to Q5 all asked for these and the diagram had no transport labels.
- Labelled every diagram arrow with its message id or wait, and added the FAILED path for Cart or Inventory not answering, because the junior could not tell how the calls were made or what happened when they failed.
- Changed the refund flow so the refund is started by the M8 event and the customer email follows M9 RefundCompleted, because Order should not email a refund that Payment has not confirmed.
- Added a Retries section (3 tries with timeouts for calls made during Place order, and a backoff queue with N = 10 alerts after payment), because Q5 and Q8 asked what retry and backoff mean in practice.
- Added the statuses FAILED, PAYMENT_RECEIVED and REFUNDED and a Customer experience section, because the customer's wait and the pending page were not described (Q6).
- Made Payment handle each webhook in one transaction (insert event id and update the charge only if still PENDING), so a duplicate delivery cannot race the first one.
- Extended reconciliation (P9) to refunds and stated what happens when the provider still reports pending, because Q7 and Q8 asked what the 30-minute timer does and what happens when the provider gives no answer.
- Added the outbox explanation under decisions and the retry-queue and reservation-tombstone rows to the stores table, because Q4 and Q2 asked where these live.
- Updated the failure table: added Cart or Inventory not answering and commit not answering rows, and changed the late-success and failed-refund rows to match the new refund flow.
- Added the open question about whether the provider can stay pending past 30 minutes, which is not known from the brief.
- Added a Terms section defining idempotency key, reservation, retry queue, outbox, webhook and reconciliation, so a reader without this stack can follow the flow (Q9 to Q16 all used these terms).
- Q9: M11 and M12 replies are now described as acknowledgment only; the outcome comes only from M10 or P9, and the design does not depend on the provider's immediate reply, which the brief does not specify.
- Q10: the 30 min timer is owned by Payment, stored as reconcile_at on the charge and refund rows, and starts when the provider accepts the request, not on the first attempt. The diagram arrow moved from Order's O3 to Payment's P2 and P6. An open question covers a charge that never reaches the provider.
- Q11: M7 and M8 are now sent through Order's outbox, not through a retry queue or a bare broker call. M8 was removed from Order's retry queue, which now holds only M3, M4 and M6. The outbox was added to the Order row of the stores table. The Retries section now separates queued calls from outbox events.
- Q12: Order's M5 handling is one transaction (processed event id, PAYMENT_RECEIVED, M3 queue row), acknowledged to the broker only after commit. The diagram node and the Decisions section say so. The queue worker makes the first M3 attempt on its next minute check.
- Q13: M3 reply now carries a reason (EXPIRED, RELEASED or NOT_FOUND). A repeat M3 on a COMMITTED reservation replies COMMITTED with no change. Any REFUSED leads to the late-success branch and a full refund.
- Q14: REFUND_FAILED is set only when the provider says the refund failed (webhook or query). A timeout keeps REFUND_PENDING. The retry resends M12 with the same key and sets REFUND_PENDING. The diagram label for the failure branch was corrected from 'failed or no answer'.
- Q14: the refund webhook rule changed from 'only while REFUND_PENDING' to 'unless already REFUNDED', so a REFUNDED webhook after a failed attempt still counts and a repeat REFUNDED sends no second M9.
- Q15: the customer email is now queued in Order's outbox in the same transaction as REFUNDED, only from CANCELLED_OUT_OF_STOCK, and sent by the relay. The email system is not named in the brief and is listed as an open question with the possible double-send risk.
- Q16: Order computes the total in O2 from the frozen snapshot, and the currency comes from Cart's M1 reply. M1, M4, M8, M11 and M12 now carry currency. Tax, shipping and discounts are listed as an open question.
- Gap found while revising: the M4 charge request had no failure path after 3 tries. It now queues M4 with the same order id and the order stays AWAITING_PAYMENT. The failure table has a new row for it, and an open question covers a charge that never arrives.
- Failure branch table: updated the late-success, failed-refund, commit, duplicate-webhook and no-webhook rows to match the decisions above. Added the charge-request row.
- Diagram: the Payment box, D_REF and the M10 refund edges were relabelled to match the refund rules. The D_RES label changed from 'Reservation still ACTIVE?' to 'Commit accepted?', because the check now covers expiry and released states.
- Open questions: added the email-service and double-send question, the provider idempotency replay on refund retry, the webhook-to-attempt matching issue, and the charge that never reaches the provider.
- Retries and the M11 and M12 rows: Payment's first try of M11 and M12 is made right after the commit that writes the row, not at the next minute check. Order's queue rows still wait for the minute check. Reason: charges reach the provider without a delay (Q17).
- P1, P2 and P5 boxes in the Flow diagram: P1 writes the charge row and the M11 queue row in one transaction. P2 sends right after that commit. P5 also writes the M12 queue row. Reason: matches the Retries change (Q17).
- M10 row and P3 box: a webhook carries the echoed order id or refund key as well, and Payment matches on the stored provider id first. Charges get a provider_charge_id column. Reason: webhooks carry no order id in the brief, so the matching rule must be written down (Q18). The provider's echo behaviour is recorded as an open question, not decided.
- Unmatched webhooks: stored as unmatched, ops alerted, 200 returned so the provider stops resending. Added to the failure table. Reason: a webhook that matches nothing must have a defined outcome (Q18).
- O_PAID and new O_ODD node in the Flow diagram, with the M5 amount check and the anomaly path to M8. M8 row and failure table updated, and the anomaly rules added to Decisions. Reason: a PaymentSucceeded on a non-AWAITING_PAYMENT order or with a wrong amount must not keep money (Q19).
- P9 box, reconciliation rules in Decisions, and a reconcile_at index note in the Payment storage row. The job runs every minute, applies answers with the webhook's conditional update, and reschedules still-pending answers. Reason: the mechanism for finding due charges and refunds, and for asking again, was not written down (Q21).
- M7 row, Cart storage row and Decisions: Cart consumes M7 in one transaction, records processed event ids, deletes by line id, and acks only after commit. Cart's processing is not reported to Order. Reason: how Cart receives M7 and handles repeats or changed lines was not written down (Q20).
- Customer experience and Decisions: an unexpected M9 is recorded and alerts ops, and Order never sees REFUND_FAILED. Reason: the rule for M9 outside CANCELLED_OUT_OF_STOCK was not written down (Q22).
- Open questions: added the echo and acceptance-reply question (Q18), the not-found reconciliation question (Q21), and the Cart consumer and anomaly alerts to the alerts question. Ops has not decided these.
- M1 row and Cart storage: the reply now carries cart line ids, so Order can name the ordered lines in M7 (Q24).
- O2 box and Order storage row: order_lines snapshot now stores the cart line id (Q24).
- M7 row: carries the cart line ids from order_lines, not a loose list (Q24).
- Terms: retry queue rows are removed when their call gets its final answer, which makes 'done' and 'never deleted' consistent (Q23).
- Retries section: added the completion rule for M3, M4, M6, M11 and M12, the check before each M4 try, and the reopen of a failed refund's M12 row (Q23, Q25).
- O3 box and Decisions: Order commits AWAITING_PAYMENT before sending M4, so an outcome never meets PLACING (Q25).
- P2, P6, P7 and P8 boxes and the failed-refund failure row: a REFUND_FAILED webhook reopens the M12 row with the attempt count plus one, and the row is kept until a send is accepted, replacing the contradictory 'never deleted' wording (Q23).
- Decisions: added the M4 queue-row check and the rule that Payment returns the existing charge for a late M4 (Q25).
- M2 row, M6 row, Inventory storage row and I3 box: M2 can reply REFUSED for a RELEASED or EXPIRED record, and M6 with no record creates a RELEASED tombstone with no stock. M6 on COMMITTED changes nothing and alerts ops (Q26).
- Decisions and the Cart/Inventory failure row: a late M2 is refused and dropped by Order, and a REFUSED that reached Order before it gave up counts as FAILED (Q26).
- M5, M7, M8 and M9 rows: events are named as broker events. Decisions: consumer subscriptions, acknowledgement after commit, failure and anomaly handling, and no dead-letter queue (Q27).
- Failure table: added the 'event delivery keeps failing' row, pointing to the consumer rule (Q27).
- Open questions: added the unnamed broker and its redelivery and dead-letter settings, and added M6 COMMITTED replies and consumer delivery failures to the alerts list (Q27, Q26).
- Q28: added a recovery job in Order that fails any order still PLACING after 5 minutes, writing FAILED and the M6 release in one transaction. Reason: nothing currently moves a crashed or lost order out of PLACING, and the release is safe either way. Added to Terms, Retries, the diagram (edge from O1), the failure table, Decisions and open questions.
- Q29: added a checkout token and a one-open-order-per-cart rule to O1, the Order storage row, Customer experience and Decisions. Reason: the file did not say where the order id comes from or stop a repeated press from creating and reserving a second order. Added Terms for checkout token and open order.
- Q30: the Place order reply now always carries the order's current status, including FAILED, with the M6 release queued in the background. Polling is limited to pending statuses, which now include PLACING. Reason: the file did not say how the request ends after a FAILED outcome, or whether the page polls a FAILED order.
- Diagram: O_FAIL label now says M6 is queued in the same transaction when M2 was sent, and E_FAIL now says the reply carries status FAILED. Reason: keeps the diagram consistent with the Retries and failure text.
- Order storage row: added order id, cart id and checkout token to the orders columns. Reason: the stored fields needed for the repeat-press and recovery rules were missing.

### Holes
- Q18: The webhook carries a provider event id, type and a charge or refund id. How does Payment find the matching charge row, which is keyed by order id? Is the provider's charge id stored somewhere, and when? (author: Partly answered. Payment now stores the provider charge id (and refund id) once it is first seen, and matches each webhook by that id, or by an order id (charge) or refund key (refund) that the provider echoes back. The brief does not say whether the webhook echoes the order id, or whether the provider's acceptance reply carries the charge id, so when the provider charge id first becomes known is not known. This is an open question in the file, and an unmatched webhook is an ops case.)
- Q27: Which broker carries the events? How does each consumer (Order, Cart, Payment) subscribe, and what happens to an event that a consumer keeps failing to process? (author: The brief says only 'the shared message broker', so the product, its redelivery settings and its dead-letter support are not known. The decided part is the consumer design. Each consumer has a durable subscription: Order for M5 and M9, Cart for M7, Payment for M8. A consumer acknowledges only after its own commit. A technical failure leaves the message unacknowledged, so the broker redelivers it. After 10 failed deliveries ops is alerted, and the message is not dropped. No dead-letter queue is used, because a message moved there would stop without a retry. A logical anomaly is handled by the handler, which records it and acknowledges, and is not retried. Whether the broker keeps redelivering a message that always fails, and in what order, is unknown. It is now an open question, and the M5, M7, M8 and M9 rows, the Decisions, the failure table and the alerts list name it.)
