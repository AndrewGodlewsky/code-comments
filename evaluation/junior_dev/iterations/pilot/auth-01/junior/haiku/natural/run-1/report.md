## Review of auth-01 (junior, author haiku, natural)

Rounds: 4. Ended: teachbacks.

### What changed
- Decision 7 and sequence diagram: the 5th failing attempt returns 429 with Retry-After, not 401, so the user sees the lock immediately. Both unknown and wrong-password emails reach the same result, so existence is still not revealed. Reviewer may reverse this if a 401 on the 5th attempt is preferred.
- Decision 8 and sequence diagram: the insert-and-lock step loops until it holds a throttle row, because a concurrent successful login can delete the row while another attempt waits on it (Q1).
- Decision 8: login time checks and timestamps use clock_timestamp() read after the row lock is held, and only the database clock is used (Q3).
- Decision 7: email input longer than 254 characters gets the 401 with no database call and no throttle row, which bounds throttle row size (Q9).
- Decision 10: the old-session delete is keyed only on the cookie hash, with no owner, validity or expiry check, and zero rows is not an error (Q6).
- Decisions 12 and 13 (new): any error before COMMIT returns 503 with no cookie and no counted attempt, and GET /login shows the form without touching the database (Q4, Q7).
- Failure policy table: login row now covers any failing statement, BEGIN or COMMIT, and says the 503 is the same whatever the password result (Q4).
- Sequence diagram: the locked path's ROLLBACK is annotated as releasing the lock only, because the insert was a no-op (Q2). Protected request now joins users and returns user id and email in one UPDATE, with a branch for malformed cookies and for deleted users (Q8).
- Schema: email comment now states the 254-character cap (Q9).
- Notes: added deleted-user behaviour, throttle state transitions (stale lock cleared on the next checked attempt), unknown-email row bounds, 429 page content and Retry-After computation, browser-close behaviour of the session cookie (Q5, Q7, Q8, Q9).
- Open items: added disabled accounts as unhandled, because the brief and users table have no disabled state (Q8).
- Added decision 14 (user lookup: the exact query, the normalized input, the columns read and where the hash is stored), answering Q10. The file did not say how the email was matched.
- Decision 6 now names the sweep's scheduler (one timer per instance, every 10 minutes), a transaction-scoped advisory lock so only one instance sweeps per tick, and the database clock, answering Q11. Overlapping runs stay safe because the deletes are idempotent.
- Added the cookie format (43 base64url characters), one shared parser that checks it before any database call, and the rule that a malformed cookie is treated as no cookie on every path, answering Q12.
- Added decision 17 with starting timeout values (pool wait 2 s, throttle lock wait 2 s, statement 5 s, idle-in-transaction 10 s), stated that bcrypt has no timeout, and mapped every timeout to the existing 503 rules. Decision 8 now says the connection is held through bcrypt. The storage failure table and the protected-request and logout branches of the diagram now include timeouts, answering Q13.
- Added decision 16: one default-deny guard in front of the router, public list GET and POST /login, applied to all methods, with POST /logout handled outside it so it works with no session. Static assets are listed as an open item, answering Q14.
- Added decision 15 (one bcrypt cost factor for real and dummy hashes, and why a mismatch leaks timing) and a clearer 401/429 timing note in the notes, answering Q15. The cost value itself is not in the brief and is listed as an open item.
- Diagram lookup line now names the columns read (id and password_hash) and the normalized email, matching decision 14.
- Schema comment on sessions.user_id now flags that the type must be confirmed against users.id instead of assuming it.
- Added the cookie format and malformed-cookie rule to the cookie handling notes.
- Open items: added the unconfirmed bcrypt cost factor, the unconfirmed users.id type, the unconfirmed static-asset path, and the lock queue during a guessing burst (a real user can get a 503 for a short time).
- Storage failure table: login and protected-page rows now include timeouts, and logout includes a malformed cookie as no cookie.
- Added a Requirements section that reproduces the eight fixed requirements as R1 to R8, and changed decisions that said 'the brief' or 'requirement 4' to refer to R-numbers, so the document no longer depends on an outside brief (Q16).
- Added a Context section that states the existing system (server-rendered app, two instances, shared Postgres, users table) in the document itself (Q17).
- Decision 7 and the diagram: an empty, missing or over-254-character email now runs the dummy bcrypt comparison before the 401. Before, it skipped bcrypt, so its timing differed from every other failure. The 254-character assumption is listed as an open item.
- Decision 7: stated that the 5th failure returning 429 is an interpretation of R2 and R3 that the owner must confirm, and added it to the open items.
- Decisions 4 and 8: made the clock rule explicit. Single statements use now(), the login transaction uses clock_timestamp() after the row lock, and both are database clocks.
- Decision 6: the throttle sweep criterion now refers to the failed_at array. Added that a sweep removes only rows the protected query already rejects, so browsers see no change (Q20).
- Decision 11: separated the redirect rule (303 for success, logout and protected redirects) from direct renders (failed login 401/429 and 503). The failed login keeps the typed email (Q19).
- Decision 17: added that a protected request with no pooled connection within 2 seconds gets the 503, and that logins hold connections through bcrypt and row-lock waits. Pool size is an open item (Q18).
- Decision 14: the lowercase email rule is now attributed to the Context section and marked as not checked against the live table.
- Schema: added an index on sessions(user_id) so the ON DELETE CASCADE does not scan, and a CHECK on the length of login_throttle.email. The user_id type remains unconfirmed.
- Notes: reworded unknown-email row growth. Each row is bounded in time, but the number of rows is not bounded by the rate of distinct emails. Added the 401 form-state note and the sweep-and-browser note.
- Open items: added the 5th-failure reading, the lock queue exhausting the pool, pool size, the stack and TLS point, password length cap, storage growth from distinct emails, and the users.email lowercase and length check against the live table.
- Decision 7: the failure steps are now listed in order (append, drop entries older than 10 minutes, count including the current attempt, then lock on 5). This answers Q22.
- Decision 8 and the diagram: the row-lock step is capped at 3 passes, with a 503 if no row is held. lock_timeout is stated as per wait, with worst-case 12 s. The diagram notes the 503 path. This answers Q26.
- Decision 8 and decision 10: a failed COMMIT rolls back the throttle delete, so the failure count survives. This answers Q21.
- Decision 2: the app generates the session ID and computes its hash, the database does not generate IDs, and a primary-key collision is a login error that takes the 503 path, with no retry. This answers Q24.
- Decision 10 and the protected-request branch of the diagram: the app computes the SHA-256 of the cookie value and the hash is the lookup key compared to id_hash. The cookie-handling note says the raw value never reaches the database. This answers Q23.
- Decision 12 and the failure table: the login 503 now also covers a duplicate session ID and a row-lock pass limit reached without a held row.
- New note: protected pages. The document now says /dashboard is the landing page, that its contents and the other protected pages are not described in the material, and that this design does not change them. This answers Q25.
- New note: logout and cross-site requests. A cross-site POST to /logout carries no SameSite=Lax cookie, so it cannot end a session. Sibling subdomains are not covered. This answers Q27.
- Open items: added protected page contents (unknown) and the login retry limit values (to tune).

### Holes
- Q15: What bcrypt cost is used for real hashes, and is the dummy hash generated with the same cost? Is the 5th-failure 429 and the 401 timing also meant to match each other, or only 401 for unknown vs wrong password? (author: I do not know the bcrypt cost factor of the existing hashes; the brief does not give it. Decided: real hashes and the dummy hash must use one configured cost, and that value must equal the existing hashes' cost, because a mismatch would let timing reveal whether an email exists. On timing, the 5th-failure 429 also runs bcrypt, so it matches the 401 for unknown and wrong-password emails. The faster 429 during a lock skips bcrypt, but it only shows that an email is locked, which anyone can cause, so it is not meant to match the 401. The cost value is an open item to confirm before release.)
- Q16: What is 'the brief'? Who wrote it, and which of its requirements does this design have to satisfy (for example the 30-minute idle rule, the 12-hour limit and the 5-failures lockout)? I only have this document. (author: The brief is the requirements list given to the author for this change. Who wrote it is not recorded in the material this design was written from, so I cannot name the author. The eight requirements are now reproduced in the Requirements section as R1 to R8, and each decision that depends on one names it. The 30-minute idle rule is R6, the 12-hour limit is R6, and the 5-failure lockout is R3. Requirement 4 is R4. The document no longer needs the brief to be read.)
- Q17: What is the App built with (language, web framework, bcrypt library, database driver)? How do requests reach instance A or B, for example through a load balancer, and where does HTTPS end? The Secure cookie and the pool settings depend on this. (author: The language, web framework, bcrypt library and database driver are not in the material this design was written from, so they are not stated. The design does not depend on them, except for the pool and timeout settings in decision 17. Where TLS ends (load balancer or app) is also unknown. The design reads no forwarded headers and always sets Secure, so it does not depend on that point. These are listed in the open items.)
- Q18: How big is the connection pool, and what do protected requests do when the pool is used up by logins running bcrypt? Is that the 2-second wait followed by a 503? (author: The pool size is not known. Yes: per decision 17 and the failure table, a protected request that cannot get a pooled connection within 2 seconds gets a 503, with the cookie kept. A login holds its connection through the bcrypt step and any row-lock wait, so the pool must cover the logins and protected requests that can run at once. Pool sizing is an open item. Logins can also use up the pool during a guessing burst on one email, which would delay protected requests. This is listed as an open item with options not yet decided.)
- Q25: After a successful login, the 303 goes to /dashboard. What is /dashboard and what other protected pages exist? Does the document say what they contain or whether they change anything? (author: /dashboard is the page a successful login redirects to, as the brief names it. The material does not describe what /dashboard or the other protected pages contain, or whether any of them change data. This design does not change them; it only decides whether a request may reach them. The document now says this in the protected-pages note and lists the contents as an open item.)
