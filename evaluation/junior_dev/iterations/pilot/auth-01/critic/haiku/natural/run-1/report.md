## Review of auth-01 (critic, author haiku, natural)

Rounds: 3. Ended: cap.

### What changed
- Point 1 (idle and expiry): stated that the touch UPDATE's WHERE clause is the idle-timeout and absolute-expiry mechanism, and that unknown, idle and expired sessions all match no row. Removed the access-time cleanup DELETE from the protected-request path, so the no-row branch now only clears the cookie. The sweeper removes rows.
- Point 2 (lock expiry and counting): login now reads one database timestamp (now_ts via clock_timestamp() after the advisory lock) and uses it for the lock check, the INSERT, the window count and the lock expiry. The window is strict (failed_at > now_ts - 10 min). The count explicitly includes the just-inserted row. The lock-expiry rule now states that it depends on the 15-minute lock being longer than the 10-minute window.
- Point 3 (stale lock rows): the lock check is now locked_until > now_ts, not row existence. The success path now also deletes the login_locks row. The rule states that stale rows are harmless.
- Point 4 (bcrypt under lock and pool exhaustion): kept the per-email lock held through bcrypt, and explained why R3 requires it. Added a Load section covering hold time, a dedicated login pool isolated from the request pool, a 2-second lock_timeout, per-email queuing, and the attacker-across-emails pool saturation case. Added per-IP throttling to the open decisions. Did not adopt releasing the lock before bcrypt, because a queued attempt would then be judged without seeing the lock, which breaks R3.
- Point 5 (failure atomicity): stated that the failure INSERT, the count, the lock UPSERT and COMMIT are one transaction, and that a rollback removes all of them together. Covered the ambiguous-COMMIT case. The storage-failure section now names this explicitly.
- Point 6 (timing and enumeration): narrowed the claims. The password-judgement step is equalized by a dummy bcrypt with the same cost factor, which the app checks at startup. Locked emails return faster and are not claimed equal. The known-user success path is not claimed equal either. 503 responses are covered, and the malformed-email path was added. A load test is recommended to confirm the timing gap.
- Point 7 (cookie): spelled out that the cookie is host-only with Path=/ on both set and clear, and that the server enforces the 12-hour limit. Stated that the session ID is not rotated during a session and changes only at login. Stated that 401 and 429 leave an incoming sid untouched, and that this is intended.
- Point 8 (complexity and detail): collapsed two cleanup mechanisms into one sweeper. Assigned sweeper scheduling to each instance with jitter, and stated that duplicate runs are harmless. Added the schema, including the indexes for the window count and the sweeps. Added the row-count risk from random emails, with length validation and the per-IP open decision. Added a Requirements section listing R1 to R8 so the references are self-contained.
- Choices section updated for the changes above, with new choices for login pool isolation, the login time source, and the logging rule. Storage-failure section updated for the transaction semantics, the bcrypt-error case, and the login pool timeout. Open decisions updated: lock griefing now notes queueing, the user-disable cascade is noted, and per-IP throttling is linked to row growth.
- Reviewer point 1 (locked email queues behind bcrypt): added a locked-email fast read on the request pool, before the advisory lock, so a locked email gets 429 without touching the login pool or lock. Stated that waiters already past the fast read still queue behind in-flight verifies, and bounded per-email pool use.
- Reviewer point 2 (malformed emails not counted): kept the non-counting behavior but stated it as a deliberate reading of R3, with the reason (a malformed string is not an email address; stored addresses must be verified well formed), the lock-key argument, and a flag for reviewer confirmation.
- Reviewer point 3 (cookie clearing and Mermaid alt): the no-cookie branch in section B now sends the clear cookie, matching R7 literally; the storage error is a separate alt branch ('UPDATE fails') instead of a second else; logout with no cookie is explicitly no-DB and clears the cookie; the cookie rule states that every no-session response clears the cookie.
- Reviewer point 4 (sweeper '<=' versus 'exactly' and '40 minutes'): removed the word 'exactly'; the sweeper predicate is the complement of the validity predicate; retention is stated as deletable at rejection time, removed at the next sweep (at most about 10 minutes later plus backlog), so a row can exist up to about 40 minutes after its last valid request. Added the concrete batched DELETE statement.
- Reviewer point 5 (lock expiry prose argument): replaced the prose with a lockout invariant. INV1 states no failure is recorded between T and locked_until, with the reason (failure inserts require the lock to be inactive, and the advisory lock makes now_ts non-decreasing). INV2 gives the exact inequality (window start at least T+5 minutes, failures at or before T excluded by strict comparison), and states the lock-longer-than-window requirement. Added the database-clock monotonicity assumption.
- Reviewer point 6 (open decisions relied on for bounds): added explicit interim mitigations. A configured cap on recent login_failures rows that fails closed with 503 without recording, a per-email waiter cap of 2 per instance, and load-balancer rate limiting if available. Stated the residual many-email login-pool risk and the trade-off of the row cap. Recommended a CSRF token before launch.
- Reviewer point 7 (timing and enumeration overclaims, hashtext): narrowed the enumeration claim to account existence (R2) and listed each observable difference (locked, malformed, 503, successful login) as not claimed equal. Stated that the known-versus-unknown timing gap is a measured expectation to be confirmed by load testing. Replaced hashtext with hashtextextended (64-bit key) and explained that collisions only serialize and add negligible waits.
- Reviewer point 8 (length and duplication): consolidated the storage-failure prose into one table with a single login 503 text used on all login paths (fixing the two different login 503 texts), kept the protected 503 and logout 503 texts matching the diagram, and removed the repeated prose. Shortened the choices list to one line per choice with no restated rules. Merged the separate load and timing sections into the rules. Lock-held-through-bcrypt rationale is stated once.
- Diagram: removed Mermaid-unsafe characters and comparison symbols from message text, replaced the storage-error and Read-fails branches with explicit alt branches, added the locked-email fast read, and added a note that any pre-COMMIT error rolls back to 503. The section A failure branch and the failure table now agree.
- Kept the intent, the R1 to R8 mapping, the schema, the sweeper design, and the Mermaid sequenceDiagram format with notes, as the brief requires.
- Summary: stated why the per-email advisory lock is needed (R3 across two instances), and marked which parts are load or growth bounds that can be removed without changing R1 to R8.
- Added an 'Alternatives considered' section with a rejection reason for each simpler option: Redis, stateless cookies, row lock on login_locks, unserialized counter UPSERT, fixed window (with a concrete counterexample), users-row counter, per-email last-five-timestamps row, request-time deletion, and a single shared pool. Noted which mechanisms can be removed without changing correctness.
- Time source: separated the fast read (advisory, 429 only is authoritative) from the in-transaction now_ts, and stated why each is safe.
- Rewrote the lockout invariant as four named facts (refusal, order, recording, duration) with a short consequence, replacing the dense INV1/INV2 wording.
- Changed the failure window from strict to inclusive, so a failure exactly 10 minutes old counts. This matches 'within any 10-minute period' and fails toward the limit. Updated the sweeper and the diagram text to match.
- Waiter cap and failure-row ceiling are now part of the design: added to the sequence diagram, the storage failure table, the rules section and the configuration values. Stated the cross-instance bound (3 attempts per email per instance, 6 total for two instances). Derived the ceiling of 50,000 from pool throughput and noted it is a backstop.
- Moved the locked-email fast read from the request pool to the login pool, so a flood of locked-email attempts cannot starve protected requests. Corrected the isolation claim: protected requests are isolated from login-pool exhaustion, not from database-wide load.
- Malformed-email rule removed. Emails are no longer shape-checked, the CHECK constraint is removed, and malformed strings are processed as unknown emails. This removes the special case, the pre-deployment stored-address check, and the malformed-versus-valid timing difference. The form body limit bounds the key size.
- Retention and sweeper: rejection of a session is permanent, so deleting rejected rows is safe. Expiry uses the same `<=` condition as validity. Added a one-hour margin for failure and lock cleanup with a stated argument (login transactions last under 10 seconds). Retention is now labelled best-effort, with a derivation of the normal-load bound and an alert metric.
- Write cost on protected requests: stated that every valid request writes, that R6 requires it, that the indexed column makes the UPDATE non-HOT, and that the cost is measured in the load test. Considered and rejected throttled touches, because they would break 'every request restarts the clock'.
- Timeouts: added an 8-second per-login budget that pool waits count against, a per-statement timeout of min(2 s, remaining), and an idle_in_transaction_session_timeout of 5 s that covers bcrypt time. Stated the worst-case login transaction duration.
- Login pool of 8 is labelled a starting value, with the derivation of throughput (pool divided by verify time) and the CPU caveat that a separate pool does not isolate bcrypt CPU from protected requests.
- Enumeration and timing: replaced 'expected within noise' with concrete load-test acceptance criteria (sample size, interleaving, bootstrap confidence interval thresholds, byte-identical bodies), plus a login-flood isolation test and a protected write-cost measurement.
- Cookie behavior: added a table giving the set or clear result for each response, explaining why 401, 429 and 503 login responses keep the cookie while no-cookie protected and logout responses clear it.
- Login CSRF moved out of 'open decisions' into its own section, labelled as outside R1 to R8 and required before launch, with the attack effect stated.
- Open decisions updated: malformed-email decision removed (resolved), waiter cap and ceiling listed as interim design rather than future work, per-IP throttling kept as the open fix for many-email exhaustion.
- Diagram: rewritten to show the fast read on the login pool, the waiter cap, the ceiling check before the password decision, the 8-second budget, and the window count at or after now_ts minus 10 minutes. Removed the malformed-email branch. Kept the format (single Mermaid sequenceDiagram, notes before and after the blocks) and avoided characters that break Mermaid messages.
- Kept the design's intent, the R1 to R8 mapping and the 'left to you' choices as an explicit numbered list. Points not adopted: kept the advisory lock instead of the row lock, with the reason given, since both are safe and the advisory lock needs no per-email row. Kept the single-UPDATE protected path, since R6 requires per-request refresh; the cost is measured instead of removed.
