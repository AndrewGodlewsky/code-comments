# Migration plan: `users` from MySQL 8 to Postgres 16

Today every read and write of `users` goes through `UserRepository`: reads hit the MySQL replica, writes hit the MySQL primary, and the erasure job hard-deletes rows. We move the table to Postgres without downtime. First every write is also copied to Postgres and old rows are backfilled. Then reads move over, then the source of truth, and MySQL is dropped last. Every copy follows one version rule, and a database outbox guarantees that missed copies are repaired automatically.

All logic lives in `UserRepository`. Its callers do not change. The lint rule `no-raw-users-sql` is extended to forbid raw SQL on `users` against Postgres outside the repository too.

## Terms

- **`version`:** an existing integer column on every user row. `create()` sets it to 1. Every successful `update()` adds 1. Callers pass the version they read, and the update fails with `StaleWrite` if it has changed. The migration reuses it to decide which copy of a row is newer.
- **Version rule:** any copy into the other database (dual write, backfill, relay or repair) may only insert a missing row or replace a row whose `version` is lower than the incoming one. In Postgres this is `INSERT ... ON CONFLICT (id) DO UPDATE ... WHERE users.version < EXCLUDED.version`.
- **Source of truth (sot):** the database that takes writes first. The other database is updated by copying. MySQL stays the sot until the planned switch.
- **Dual write:** each write is also copied to the database that is not the sot.
- **Erasure job:** the GDPR background job. It is the only caller of `UserRepository.delete(user_id)`, which hard-deletes the row (about 2,000 per day).
- **Tombstone:** the record of an erased user. In Postgres it is a `users` row with the same `id`, `deleted_at` set, `email`, `name` and `plan` NULL, and `version = 2147483647` (the largest INT). Because its version beats any other copy, the version rule rejects every stale copy of an erased user from the dual write, backfill or repair, with no locks. In MySQL the equivalent is a row in `users_erased(id)`, written in the same transaction as the delete.
- **Outbox:** a table `users_outbox` in the sot database. A row `(user_id, op)` means "this user still has to be copied to the other database". It holds no row data.
- **Relay worker:** a background worker that drains the outbox.
- **Flag cache:** each app instance keeps a copy of all flags (`app.flags`) and refreshes it every 30 s, so instances can disagree for up to 30 s. Each instance exports the values it uses as the metric `app_flag_value{flag=...}`, which shows when every instance has a change.
- **Bucketed user:** a user whose bucket is under the `users_read_pg` percentage. `flags.enabled_for("users_read_pg", user_id)` hashes the id into a stable bucket, so the same user always gets the same answer.

## Flags

- `users_sot`: string, one of `mysql`, `paused`, `postgres`. It is the source of truth.
- `users_dual_write`: boolean.
- `users_read_pg`: percentage of users whose reads go to Postgres.
- `users_backfill_pause_ms`: pause between backfill batches.

## How it runs

**Why an outbox, not the job queue.** Jobs are at-least-once, but `enqueue` raises when Redis is down, and a job that fails 5 times (about 15 minutes) goes to `jobs:dead`, which nothing processes. A crash between the MySQL commit and the enqueue would also lose the repair. So, while dual write is on, every write inserts an outbox row inside the same transaction as the change, and the relay retries it forever. No manual step is needed.

**Where state lives.**

| State | Where |
|---|---|
| `users_outbox`, `users_erased` | MySQL primary. The outbox is used while MySQL is the sot. |
| `users` (with tombstones), `users_outbox`, `migration_state` | Postgres. Its outbox is used while Postgres is the sot. |

A transaction cannot span two databases, so each outbox lives in the database that takes the write. The relay reads only the outbox of the current sot. At each switch the old side's outbox must be empty first. `migration_state` holds the backfill cursor and the comparison cursor.

**Schema notes.**
- The Postgres email unique index is on `lower(email)` (or `citext`). Postgres must be no more permissive than MySQL's case-insensitive unique index, or the reverse copy would fail permanently.
- The Postgres `id` is `GENERATED BY DEFAULT AS IDENTITY`. Dual writes insert MySQL's explicit ids.

**Write path under `users_sot=mysql`.**
1. In one MySQL transaction, apply the change (a delete also writes `users_erased`). If `users_dual_write` is on, also read the resulting row back and insert an outbox row. With dual write off, no outbox row is written.
2. After commit, if dual write is on, apply that row snapshot to Postgres with the version rule and a 300 ms timeout. A delete applies the tombstone the same way. Catch every exception. A circuit breaker skips the inline attempt for 10 s after repeated failures.
3. On success, delete the outbox row. Otherwise leave it for the relay.
4. Never raise a Postgres error to the caller.

Under `users_sot=postgres` the same path runs in the opposite direction: the change and the outbox row commit in Postgres, and the copy to MySQL uses the same version rule. A MySQL copy failure never fails the request. An erasure writes the Postgres tombstone and an outbox row, and the relay applies it to MySQL (step 9).

**Relay worker.**
- It scans outbox rows older than 5 s, using `SKIP LOCKED` so several workers can run.
- For each row it re-reads the current row from the sot primary (not a replica) and applies it to the other database with the version rule. A missing row means a tombstone. So a row whose inline copy failed ends up with the latest version, even if it changed again in between.
- It deletes the outbox row on success. On failure it backs off per row (capped at 5 minutes) and moves on to the next row.
- Rows are never dead-lettered. Alerts fire when the oldest outbox row is older than 2 minutes.

**Reads.** `get()` checks `flags.enabled_for("users_read_pg", user_id)`. If false it reads the MySQL replica as today. If true it reads Postgres.
- A tombstone counts as not found, with no fallback.
- On a Postgres error it falls back to the MySQL replica, so reads never fail.
- While MySQL is the sot, a plain miss in Postgres also falls back to the replica, which covers a row whose repair is still pending. After the switch to Postgres, a miss is a real not found.

**Writes that cannot be safe.** Writes raise `WritesPaused`, which the API maps to a 503 with Retry-After, when the sot is `paused`. They do the same when the flag cache is older than 40 s, but only while dual write is on or the sot is not `mysql`. This fails closed for an instance that cannot refresh flags. It also means a flag-service outage does not affect writes before the migration starts. Every write has a 5 s deadline.

## Rollout checklist

- [ ] **1. Create the schemas.**
  - **Starts:** a migration run by hand. No app change.
  - **Changes:** adds new tables only, so the 38M-row MySQL `users` table is untouched.
    - MySQL: `users_outbox(id, user_id, op, attempts, next_attempt_at, created_at)` and `users_erased(id, erased_at)`.
    - Postgres: `users` (with the tombstone columns), `users_outbox`, `migration_state`.
  - **State:** the DDL itself.
  - **If it fails:** the DDL is idempotent (`IF NOT EXISTS`). Re-run it. Nothing reads the tables yet.

- [ ] **2. Deploy the new `UserRepository` with every flag off.** Flags are `users_sot=mysql`, `users_dual_write=false`, `users_read_pg=0`.
  - **Starts:** a normal deploy.
  - **Changes:** the code implements everything under "How it runs", plus backfill and comparison. Behaviour is identical to today, and no outbox rows are written. The relay workers start with nothing to do.
  - **State:** none new.
  - **If it fails:** roll the deploy back. No data has changed.
  - **Gate for step 3:** every running instance reports `app_flag_value{flag="users_dual_write"}`, and the number of reporters equals the instance count. This proves no old-code instance remains.

- [ ] **3. Turn on dual writes.**
  - **Starts:** set `users_dual_write=true`.
  - **Changes:** every new write is copied to Postgres by the write path. Rows already in MySQL are not copied yet.
  - **State:** `users_outbox` in MySQL.
  - **If it fails:**
    - A Postgres outage is not a failure. Outbox rows pile up and drain after recovery. If the inline attempt hurts latency, the breaker handles it.
    - If dual write must be switched off, set the flag to false. Writes made while it was off get no outbox row and are not copied. The comparison in step 5 finds and repairs them, so a clean comparison must follow before any later step.
  - **Gate for step 4:**
    - The metric shows `true` on every instance. Check after the 30 s refresh interval and repeat until it holds.
    - Then record the primary's `gtid_executed` as `G` and wait until the replica has applied `G` (`WAIT_FOR_EXECUTED_GTID_SET`). This closes the gap where a write made just before dual write started is still unreplicated. Without it, the backfill would copy the stale version and nothing would ever send the newer one.

- [ ] **4. Backfill the existing rows.**
  - **Starts:** the gate from step 3 is met. An operator starts the backfill worker, which runs outside the web instances and outside the Redis job queue. It takes `pg_try_advisory_lock`, so only one runs.
  - **Moves:** it repeats this loop (about 19,000 batches in total):
    - Check `mysql_replica_lag_seconds` (reporting jobs share the replica). If it is above 5 s, or the metric is missing, sleep 5 s and re-check.
    - Read `SELECT * FROM users WHERE id > :cursor ORDER BY id LIMIT 2000` from the replica.
    - Apply the batch to Postgres with the version rule. In the same Postgres transaction, advance the cursor with compare-and-set: `UPDATE migration_state SET cursor = :last_id WHERE name='backfill' AND cursor = :prev`.
    - Wait `users_backfill_pause_ms`.
  - Rows erased during the backfill cannot come back, because the tombstone version is higher than any copy.
  - **State:** `migration_state.backfill` in Postgres. The cursor and the batch commit atomically.
  - **If it fails:**
    - After a crash or restart, the worker reads the cursor and continues after the last completed batch.
    - A failed batch rolls back and is retried. The version rule makes any repeated batch harmless.
    - A cursor mismatch means another worker advanced it, so this one stops.
  - **Done when:** the select returns no rows and the cursor equals the final id.

- [ ] **5. Full comparison, with automatic repair.**
  - **Starts:** step 4 is finished and the outbox is empty. A comparison worker starts. It is also rerun nightly later.
  - **Moves:**
    - It walks ids in chunks of 10,000, hashes every column of every row on both sides, and records the cursor in `migration_state.compare`.
    - It reads the replica and pauses at lag above 5 s like the backfill. It then re-checks any differing row against the MySQL primary and Postgres.
    - A mismatch counts only if it persists and the id has no pending outbox row. The cases that count are: a row missing from Postgres or with a different value; a Postgres row missing from MySQL that is not a tombstone; a tombstone whose id still exists in MySQL.
    - Each confirmed mismatch gets a repair outbox row.
  - **State:** `migration_state.compare` and the repair outbox rows.
  - **If it fails:** the pass restarts from its cursor. Any confirmed mismatch means the pass is not clean. Wait for the repairs, then run a new full pass.
  - **Gate for step 6:** one complete pass with zero confirmed mismatches, and no relay backlog.

- [ ] **6. Move reads to Postgres.**
  - **Starts:** the gate from step 5. An operator raises `users_read_pg` through 1%, 10%, 50% and 100%. Hold each level for at least 30 minutes, and proceed only while error rate, latency and the comparison are healthy.
  - **Moves:** bucketed users read Postgres, with the fallbacks described under "Reads".
  - **State:** the flag only.
  - **If it fails:** set `users_read_pg` to 0. This takes effect within 30 s and needs no pause.

- [ ] **7. Soak at 100% reads for at least 3 days.**
  - **Starts:** `users_read_pg` is 100% on every instance (checked with the metric). The 3 days run from that moment.
  - **Changes:** nothing. The nightly comparison and the outbox alerts keep running.
  - **If it fails:** any drop below 100%, or any confirmed mismatch, resets the 3-day clock.

- [ ] **8. Planned switch of the source of truth to Postgres. Writes are paused for at most 90 s.**
  - **Starts:** step 7 is finished, the outbox is empty, and an operator runs the switch. T0 is the moment the flag is set.
  - **Moves, in order:**
    1. At T0 set `users_sot=paused`. Each instance returns a retryable 503 on writes as soon as it refreshes (at most 30 s), or once its cache is older than 40 s if it cannot refresh. Reads continue. The erasure job's calls fail and are retried by the job, whose retries span about 15 minutes.
    2. The switch continues only when all of these hold by T0+45:
       - Every instance reports `paused` in `app_flag_value`.
       - 5 s have passed since the last confirmation. A write that started before its instance saw `paused` is allowed to finish, and every write has a 5 s deadline, so after 5 s none is in flight.
       - The MySQL outbox is empty, which includes the copies of those last in-flight writes.
       - The version of the 10,000 most recently updated rows matches in both stores.
    3. Set the Postgres identity sequence with `setval` to `GREATEST(MySQL AUTO_INCREMENT counter (read with information_schema_stats_expiry=0), max(Postgres id)) + 100000`. Ids assigned after the switch then never collide with any id MySQL ever issued.
    4. Set `users_sot=postgres`. Every instance has already stopped writing to MySQL, so there is no split-brain. The last instance sees the flag by T0+75, which keeps the pause under 90 s.
  - **State:** the flag, plus the sequence value in Postgres.
  - **If it fails:** if the gates are not met by T0+45, set `users_sot=mysql` (abort). The last instance sees it by T0+75, so the pause is still under 90 s. Investigate, then try again later.

- [ ] **9. Soak with Postgres as source of truth for at least 14 days, with reverse sync.**
  - **Starts:** the end of step 8.
  - **Changes:** writes commit to Postgres first, and a MySQL failure never fails the request. The relay copies every change to MySQL with the version rule. `create()` takes the id from the Postgres sequence, and the copy to MySQL carries it explicitly, which keeps MySQL's AUTO_INCREMENT counter ahead.
  - **Erasures:** the Postgres tombstone is written first. The relay then deletes the MySQL row and writes `users_erased` in one transaction. A reverse upsert does a locking read of `users_erased` before inserting the row, so it cannot race the erasure and bring the user back. Deadlocks are retried.
  - **State:** the Postgres outbox, plus the MySQL tables, which now trail Postgres by a few seconds.
  - **If it fails:** use the rollback below.
  - **Rollback to MySQL.** Allowed at any time before step 10.
    1. If the cause is read behaviour, set `users_read_pg=0` first.
    2. Run the step 8 pause protocol in reverse: set `paused`, wait for every instance, and wait for the Postgres outbox to be empty so every Postgres write is in MySQL.
    3. Check the MySQL AUTO_INCREMENT counter is above `max(id)` and fix it if not.
    4. Set `users_sot=mysql` by T0+45, with the same abort rule. Forward dual write continues, and no write is lost.
    5. The 14 days restart when the sot next moves to Postgres.
    - **Limit:** the only writes at risk are those still in the Postgres outbox. This requires Postgres to be readable or restorable during the rollback, so it needs its normal HA and backup setup.

- [ ] **10. Switch to Postgres-only writes. It cannot be undone cheaply.**
  - **Starts:** at least 14 days after step 8, and all of these hold: the relay backlog has been empty throughout; a last comparison has zero mismatches; a MySQL backup is saved.
  - **Moves:**
    1. Remove the MySQL fallback in the read path (code deploy).
    2. Set `users_dual_write=false`. Writes now go only to Postgres. MySQL is no longer updated.
  - **State:** the flag.
  - **If it fails:** from here, going back to MySQL needs a fresh reverse backfill.

- [ ] **11. Retire MySQL.**
  - **Starts:** after step 10, plus a hold period of your choice (suggested 7 days). First rename the table (`RENAME TABLE users TO users_retired`), then drop it.
  - **Moves:** after the drop, remove the MySQL code, the relay and the outbox, and the flags (`users_sot`, `users_dual_write`, `users_read_pg`). Tombstones can stay.
  - **State:** none.
  - **If it fails:** rename the table back during the hold period.
