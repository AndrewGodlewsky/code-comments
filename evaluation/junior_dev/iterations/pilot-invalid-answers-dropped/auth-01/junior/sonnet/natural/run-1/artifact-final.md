# Login with server-side sessions: design

## Requirements this design must meet

The rest of this document cites these by number.

1. Login is `POST /login` with email and password. Emails are matched in lowercase.
2. An unknown email and a wrong password get the identical response: HTTP 401 and the login page showing "Invalid email or password". Nothing may reveal whether an account exists.
3. Brute-force limit: once an email has 5 failed attempts within any 10-minute period, refuse logins for that email for 15 minutes with HTTP 429, without checking the password. A successful login clears that email's failure count.
4. On success, always issue a brand-new random session ID, even if the browser already sent one, and destroy the session the incoming cookie pointed to. Then redirect to `/dashboard`.
5. The cookie carries only the opaque session ID, flagged HttpOnly, Secure and SameSite=Lax. No user data goes in the cookie.
6. A session ends after 30 minutes with no requests (every request restarts that clock) or 12 hours after login, whichever comes first.
7. Every protected request checks the session on the server. If it is missing, unknown or expired, clear the cookie and redirect to `/login`.
8. Logout is `POST /logout`. Destroy the session on the server before replying, then clear the cookie and redirect to `/login`. It behaves the same when there is no session.

Context: a server-rendered app (HTML pages and form posts), two identical instances behind a load balancer with no sticky sessions, and one Postgres database whose `users` table has `id`, `email` (lowercase, unique) and `password_hash` (bcrypt). Every page except `/login` is protected. Sign-up and password reset are out of scope.

Assumption: browsers reach the app over HTTPS (TLS may end at the load balancer). `Secure` and the `__Host-` cookie prefix only work over HTTPS, so the deployment must provide it. This document does not design that, or the load balancer's balancing method (any method works, because no state lives in an instance).

## Summary of choices

| Question | Choice |
|---|---|
| Where sessions and failure counts live | One Redis instance shared by both app instances. New infrastructure, justified below. |
| Session ID | 32 bytes from a CSPRNG, base64url encoded (43 characters), generated by the app. Redis keys use the SHA-256 of the ID written as 64 lowercase hex characters, so a Redis read does not yield usable cookies. |
| How expiry is checked and recorded | The session record stores `created_at` and `abs_expires_at`. The Redis TTL is always set to `min(30 min, abs_expires_at - now)` and is reset on every request. The CHECK script also compares `abs_expires_at` to the Redis clock. |
| How abandoned sessions are removed | Redis TTL removes them. There is no sweeper job. |
| When storage fails | Fail closed with HTTP 503 and a generic "temporarily unavailable" page. See "Storage failure behavior". |
| Cookie | `__Host-sid=<id>; Path=/; HttpOnly; Secure; SameSite=Lax`, with no `Domain` attribute and no `Max-Age`/`Expires`, so it is a browser-session cookie. The server decides when a session ends. |

## Why Redis

Sessions and failure counters must be visible to both instances immediately, because there are no sticky sessions. Process memory fails that test. The two realistic options are Postgres, which we already run, and Redis.

- **Redis (chosen).**
  - Every protected request must restart the 30-minute idle clock. That is a write per request, and Redis does it in one cheap call.
  - Key expiry is built in, so abandoned sessions and stale failure counters clean themselves up. Postgres would need a cleanup job.
  - Lua scripts make "check the lock, then record the attempt" and "check the session, then slide the TTL" atomic across both instances.
- **Postgres (rejected, still viable).** It needs no new infrastructure, but it adds a row update to every page view and a purge job. If the team decides a new service is not worth it for this app, the same design works with a `sessions` table and a `login_failures` table. In that case the TTL becomes an `expires_at` column and a periodic delete.
- **Cost of the choice.**
  - One more service to run and monitor. Use a managed instance with a replica or restart policy.
  - Turn on AOF with `appendfsync everysec`, so a Redis restart does not sign everyone out. Losing about a second of state is acceptable.
  - Set `maxmemory-policy noeviction`. Redis then returns errors when full instead of silently dropping sessions, and the app handles those errors by failing closed. Memory use is small: one short record per active session.

## How the app talks to Redis

Three operations are Lua scripts, because each must read and write atomically. Each script is one Redis call, and all times inside them come from `TIME` (one clock, Redis's, so the two instances never disagree).

| Script | App passes in | Returns to the app |
|---|---|---|
| **GATE** (login rate limit) | the email hash, and a fresh random attempt nonce (16 random bytes as 32 hex characters, generated by the app for each request) | `OK`, or `LOCKED` plus whole seconds remaining on the lock (see "Login gate") |
| **CREATE** (make a session) | the session-key hash, `user_id` | `OK`. The app, not the script, generates the random ID before calling, so it already knows the ID to put in the cookie. |
| **CHECK** (validate and slide a session) | the session-key hash | `MISSING`, or the `user_id` |

- **Key names.** The app passes only the hashes. Each script builds its own key names by adding the fixed prefixes from the "State in Redis" table (`sess:`, `lf:`, `lock:`) to the hash it receives. Scripts are written so they touch only keys derived from their inputs.
- **Loading.** Each app instance loads the three scripts at startup with `SCRIPT LOAD` and runs them with `EVALSHA`; if Redis answers `NOSCRIPT` (for example after a restart), the app reloads and retries once. If the reload or the retry fails, that is an ordinary Redis error and is handled as in "Storage failure behavior".
- **Script problems.** Redis runs a script to completion or not at all, so a script that errors or is killed for running too long leaves no half-written state. The app sees an error and treats it as an ordinary Redis error. Any reply that is not one of the values in the table above (for example an unknown word from GATE) is also treated as a Redis error: 503, fail closed. The app never guesses.
- **CREATE and an existing ID.** CREATE refuses to overwrite: if `sess:{hash}` already exists it returns an error, and the app treats it as a Redis error (503, user can retry and gets a new random ID). With 256 random bits this is not expected to happen.

Everything else is a plain single command: `DEL lf:...` (clear failures after success), `DEL sess:...` (delete the old session in login, and the session in logout and deleted-user cleanup).

## State in Redis

`{sha256(x)}` below means the lowercase hex SHA-256 of `x`.

| Key | Type | Content | TTL |
|---|---|---|---|
| `sess:{sha256(id)}` | hash | `user_id`, `created_at`, `abs_expires_at` (epoch ms) | `min(1800 s, abs_expires_at - now)`, reset on every request |
| `lf:{sha256(email)}` | sorted set | one entry per login attempt: member = the attempt nonce passed to GATE, score = Redis time in ms | 10 min, refreshed on each attempt |
| `lock:{sha256(email)}` | string | `1` | 15 min, set once and never extended |

Notes on these keys:

- **Why a nonce member.** A sorted set holds each member once, so two attempts in the same millisecond must have different members or they would count as one. The random nonce makes every member unique. The score alone carries the time, which is used to drop entries older than 10 minutes.
- **Email normalisation.** The submitted email is trimmed and lowercased. If the result is longer than 254 characters (the longest valid email), it is cut to its first 254 characters, and only that cut string is used as the gate key. The cut string is never used to look up a user. Because a longer string cannot match any stored email, the app skips the Postgres lookup and treats the attempt as an unknown email (see "Reading the login form"). The cut is not a refusal: the attempt is gated and counted like any other, so the response does not reveal the length rule. Known and unknown emails get keys the same way.
- All times come from the Redis clock, so the two app instances cannot disagree about expiry.
- To clear the cookie, send the same name, path and flags with `Max-Age=0`.
- **Valid-looking cookie.** The cookie value is only used if it is exactly 43 base64url characters. Anything else (absent, empty, overlong, garbage) is treated as "no cookie": no Redis call is made for it. This one rule applies everywhere a cookie is read: protected requests, login ("carried a cookie") and logout.

## Rules not shown on the arrows

**Reading the login form (requirement 1).** Before the gate, the app reads the `email` and `password` form fields. A missing field is treated as an empty string. There is no separate "bad request" response and no validation step before the gate, because a distinct response would be one more thing that differs by input. So a submission with an empty or missing field goes through the gate, is counted as an attempt under the hash of its (possibly empty) email, and ends in 401 like any other failed login. In detail:
- An empty email, or an email over 254 characters, cannot match a user: the app skips the Postgres lookup and runs the dummy bcrypt comparison.
- An empty password with a real email is looked up normally; bcrypt rejects it, so it is 401.
- The empty-email key can be locked by anyone. This is harmless, since no account has an empty email.
- The web server's request-body size limit (an implementer setting) bounds the password length; a body over the limit is rejected by the web server before the app runs, with whatever response the server gives. The password is not trimmed or changed in any way.
- Methods and paths this document does not mention (a `GET /logout`, say, or an unknown URL) get the framework's default response, and are not designed here. Unknown URLs still count as protected: they go through CHECK first.

**Login gate (requirement 3).** The GATE script runs before the password is checked. It counts *attempts*, recorded before the password is known to be right or wrong:
1. If `lock:{email}` exists, return LOCKED with the lock's remaining seconds.
2. Drop entries older than 10 minutes from `lf:{email}`.
3. If the set already holds 5 or more entries, set `lock:{email}` for 15 minutes (`SET NX EX 900`) and return LOCKED with 900 seconds (or the lock's remaining time if another instance set it first).
4. Otherwise add this attempt to the set (member = the nonce, score = now in ms), refresh its 10-minute TTL and return OK.

"Remaining seconds" is the lock's remaining time (read inside the script with `PTTL`, so it is Redis's clock whichever instance set the lock) in milliseconds divided by 1000 and rounded up to a whole number, minimum 1. The app copies it into `Retry-After`.

Any Redis error inside GATE, including a failed write of the lock, is a Redis failure at the gate: 503, password not checked.

What this means in practice:

- **Threshold.** The first 5 attempts in a 10-minute window pass the gate and are checked normally. If all 5 had wrong passwords, each gets 401. The 6th attempt finds 5 entries, starts the lock and gets 429. Every later attempt gets 429 until the lock expires. So 5 wrong passwords are allowed and the 6th attempt is refused.
- **Why record up front.** Because the count and the add happen in one atomic script, parallel guesses cannot all slip past a check-then-increment: at most 5 attempts per window ever reach the password check.
- **Successful login.** A correct-password attempt is also recorded by the gate. After the password check passes, the app runs `DEL lf:{email}`, which removes that attempt and all earlier failures. A successful login can never begin while locked, because the gate refuses first. Two races are accepted. (a) A success also erases failures from a concurrent attacker on the same email; the attacker still needs the right password. (b) Another instance may start a lock between this request's GATE and its `DEL lf`. This request still succeeds, since it already passed the gate. `DEL lf` does not touch the lock key, so the lock stays and later attempts get 429 until it expires.
- **After a lock.** The lock lasts 15 minutes. The old entries are older than 10 minutes by then and are dropped, so the email starts clean.
- **Where it applies.** Limits apply to every email string, whether or not the account exists. This stops lockout from revealing which accounts exist.
- **Crashes mid-attempt.** An attempt that crashes after the gate stays counted. That errs toward locking.

**No account enumeration (requirement 2).**
- An unknown email and a wrong password both return 401 with the same page and the same "Invalid email or password" text. The 401 response sets no cookie.
- For an unknown email (including an empty or over-long one), the app still runs a bcrypt comparison against a fixed dummy hash (a valid bcrypt hash, at the same cost as the real ones, generated once), so response time does not distinguish the two cases. The cost value is the cost of the existing hashes in `users`; the implementer reads it from them.
- Lockout returns a generic 429 page with `Retry-After` set to the lock's remaining seconds (900 when the lock has just started). It is the same for any email.
- The 401 and 429 pages are the login form again with a message above it, and the submitted email is kept in the email field. The password field is always empty. The 401 message is "Invalid email or password". The 429 message is "Too many sign-in attempts. Please try again later." The 503 login message is in "Storage failure behavior".
- `GET /login` shows the same form with no message and an empty email field.
- There is no CSRF token on `POST /login`: it needs no existing session, so there is nothing for a forged request to ride on, and "login CSRF" (forcing a victim into an attacker's account) is not covered here. This is an accepted gap, noted for the reviewer.

**Session fixation (requirement 4).** The app discards the incoming cookie's session after a successful password check. The order matters:
1. Run `DEL lf:{email}`. If it fails, return 503 (no session created).
2. Generate a fresh random ID and run CREATE with it.
3. If the request carried a valid-looking cookie, run `DEL` on the old session. If this delete fails, try to delete the new session as well (best effort) and return 503. A login never succeeds with the old session left alive. If that cleanup also fails, the new session stays in Redis until its idle TTL expires; this is harmless, because its ID was never sent to anyone.
4. Reply with `302 /dashboard` and `Set-Cookie` for the new ID.

If the new session was created but the browser never receives the 302 (network drop), nobody knows the new ID, so it is never used and expires by its 30-minute idle TTL. The old session is already gone, so the user simply sees the login page next time and logs in again.

**Session creation (CREATE script).** It writes `created_at = now` and `abs_expires_at = now + 12 h`, then sets the TTL to 30 minutes. The ID is random, never derived from user data and never reused.

**Protected request check (requirements 6 and 7).** A protected route is every route except `GET /login`, `POST /login` and `POST /logout`. `/dashboard` and the other pages are ordinary app pages whose content is outside this design; all that matters here is that each loads the user row for the signed-in `user_id`. The CHECK script does the whole check atomically, including the `abs_expires_at` comparison, on the Redis clock:
1. Look up `sess:{sha256(id)}`. If it is missing, return MISSING.
2. If `now >= abs_expires_at`, delete the session and return MISSING.
3. Otherwise set the TTL to `min(1800, abs_expires_at - now)` and return the `user_id`.

What this means in practice:

- **Idle limit.** The 30-minute idle limit is enforced by the Redis TTL, so an expired session is simply absent.
- **12-hour limit.** The 12-hour cap is enforced by the clamped TTL and, redundantly, by the explicit comparison.
- **Every request counts.** Every protected request goes through CHECK, so every request restarts the idle clock. The TTL never extends beyond the absolute deadline.
- **Unauthenticated requests.** No cookie, a malformed cookie, an unknown ID and an expired ID all lead to the same result: `Set-Cookie` that clears the cookie, then `302 /login`. The login page does not say why. This includes the 12-hour limit: the user sees the plain login page with no message.
- **Deleted users.** After CHECK succeeds, the app loads the user row from Postgres for the page. If the row no longer exists, the app treats the request as unauthenticated: it runs `DEL` on the session (best effort; a later request would find the user missing again), clears the cookie and replies `302 /login`. If Postgres itself fails on this lookup, the app replies with the same 503 page and kept cookie as a Redis failure on a protected request. The session is checked only for existence of the user row; a password change does not end other sessions (password reset is out of scope).
- **Which routes call CHECK.** Every route except `GET /login`, `POST /login` and `POST /logout`. Those three never call CHECK. A signed-in user who opens `/login` just sees the login page; nothing redirects them to `/dashboard`. If they submit it, the fixation rule above replaces their session.

**Logout (requirement 8).** `POST /logout` runs `DEL sess:{sha256(id)}` if a valid-looking cookie was sent. Deleting a key that does not exist is not an error. The reply is always the cookie-clearing `Set-Cookie` plus `302 /login`, whether or not a session existed. Because the cookie is `SameSite=Lax`, a cross-site POST to `/logout` or any other form post does not carry it, which covers cross-site request forgery for this scope.

**Cookie contents (requirement 5).** The cookie holds only the opaque ID. Nothing about the user is in it.

**Closing the browser.** The cookie has no expiry, so most browsers delete it when closed. The server session may still be alive for up to 30 minutes idle, but without the cookie nobody can reach it, so the user must log in again; it then ages out by TTL. This is chosen so that a shared computer does not stay signed in. Browsers that restore the previous session may keep the cookie; the server limits (requirement 6) still apply either way.

## Storage failure behavior

All of these fail closed. Redis errors never grant access, skip the rate limit or log anyone out by accident. A "Redis error" includes a failed script load, a failed retry after `NOSCRIPT`, a script that errors or times out, and an unrecognised script reply.

| Situation | What happens |
|---|---|
| Redis fails during GATE (including writing the lock) | HTTP 503, generic page: "Sign-in is temporarily unavailable. Please try again in a few minutes." It shows the login form with the email kept. The password is not checked and no session is created. |
| Redis fails after the password was correct (clearing failures, creating the session, or deleting the old session) | 503, same page, no cookie. The user can retry. |
| Redis or Postgres fails on a protected request (session check or user lookup) | 503 error page with the generic text "This page is temporarily unavailable. Please try again." The cookie is **not** cleared and there is no redirect to `/login`, because the session may still be valid. |
| Redis fails during logout | 503 page saying logout could not be completed, and the cookie is kept. We do not claim the user is signed out when the server-side session may still exist. The user can retry. |
| Postgres fails during login | Same 503 page as the Redis login failure. The failed lookup is not counted as a bad credential and does not return 401. (The attempt was already recorded by the gate, so it still counts toward the limit.) |

All 503 responses are logged with the error, not with the email or the session ID.

## Left to the implementer

This document fixes behaviour, not code. It does not choose the language or framework, the crypto and Redis libraries, the bcrypt cost (use the cost of the existing hashes), connection settings for Redis and Postgres, the load balancer's balancing method or TLS setup, the request-body size limit, the responses for methods and URLs it does not mention, the page layouts beyond the messages above, or any message about the 12-hour limit (an expired session just redirects to the login page).

```mermaid

    actor B as Browser
    participant A as App (either instance)
    participant R as Redis
    participant P as Postgres

    Note over B,P: Login (POST /login)
    B->>A: POST /login (email, password, optional old sid cookie)
    A->>A: missing field = empty string, trim and lowercase email, cut to 254 chars for the gate key, make random attempt nonce
    A->>R: GATE script (email hash, nonce): locked? else record this attempt in lf set (member = nonce)
    alt Redis error or unrecognised reply
        R--xA: error
        A-->>B: 503 sign-in unavailable, no cookie
    else Locked, or 5 attempts already in last 10 min
        R-->>A: LOCKED + remaining seconds, rounded up (sets 15 min lock if not yet set)
        A-->>B: 429 login page, Retry-After remaining seconds, password not checked
    else Allowed
        R-->>A: OK
        A->>P: SELECT id, password_hash FROM users WHERE email = ? (skipped if email is empty or over 254 chars)
        P-->>A: row, or no row
        A->>A: bcrypt compare (dummy hash if no row)
        alt Password correct
            A->>R: DEL lf for email (clears all failures incl. this attempt)
            A->>A: generate new 32 byte random id
            A->>R: CREATE script (hash of new id, user_id; TTL 30 min, abs expiry 12 h)
            opt Request carried a valid-looking old sid
                A->>R: DEL old session
            end
            A-->>B: 302 /dashboard, Set-Cookie __Host-sid new id (HttpOnly Secure SameSite=Lax)
        else Unknown email or wrong password
            Note over A,R: nothing more to record, the gate already counted this attempt
            A-->>B: 401 login page "Invalid email or password" (identical for both cases)
        end
    end
    Note over A,B: Any Redis or Postgres error after the gate: 503, no cookie, user can retry (see Storage failure behavior)

    Note over B,P: Protected request (every page except GET/POST /login and POST /logout)
    B->>A: GET /dashboard (Cookie sid)
    A->>R: CHECK script (sha256 sid): exists, now < abs expiry, then set TTL to min(30 min, time to abs expiry)
    alt Session valid
        R-->>A: user_id (idle clock restarted)
        A->>P: load user for the page
        alt User row exists
            P-->>A: user row
            A-->>B: 200 page
        else User row deleted
            P-->>A: no row
            A->>R: DEL session (best effort)
            A-->>B: 302 /login, Set-Cookie clears __Host-sid
        else Postgres error
            P--xA: error
            A-->>B: 503 temporary error page, cookie kept
        end
    else Missing, malformed, unknown or expired
        R-->>A: MISSING (expired absolute sessions are deleted)
        A-->>B: 302 /login, Set-Cookie clears __Host-sid
    else Redis error
        R--xA: error
        A-->>B: 503 temporary error page, cookie kept
    end

    Note over B,P: Logout (POST /logout)
    B->>A: POST /logout (Cookie sid, or none)

    end
    alt Redis error on delete
        R--xA: error

        A-->>B: 302 /login, Set-Cookie clears __Host-sid
    end
```

## Out of scope

Sign-up, password reset, remember-me, concurrent-session limits, and an admin "sign out everywhere" tool are not covered. A per-user session index would be needed for "sign out everywhere" and is not part of this design.
